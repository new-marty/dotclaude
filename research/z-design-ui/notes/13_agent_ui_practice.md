# 13 コーディングエージェントに良い UI を作らせる実践(2025〜2026 の公式ガイダンスと実装例)

調査日: 2026-10-26。`05_ai_ui_skills.md`(スキルの一覧と AI slop の兆候)と `01_goodlinks_taste.md`(趣味の収集)は読んだうえで、そこに無いものだけを書く。
印: [F]=本文を自分で取得して読んだ、[S]=検索結果の要約のみ、【弱】=裏付けが薄い、【推論】=私の推論。
注意: 01 で「403 で未取得」だった Money Forward Design の記事は、note.com 版(https://note.com/mfdesign/n/n51eb399cefc0)で本文を取得できた。NestUI(https://note.com/canary_inc/n/n538adfe8daee)も本文を取得できた。

## 結論

1. 公式の最新ガイダンス(Anthropic のモデル別ページ)は、「一般的な禁止(クリームを使うな、ミニマルに)」は別の固定パレットに移るだけで効かず、効くのは「具体的な代替を指定する」か「作る前に 4 方向を理由つきで出させて人に選ばせ、選んだ 1 つだけ作る」の 2 つだと明記している [F]。
2. 品質を動かす構造は共通して「作る側と評価する側を分け、評価側はスクリーンショットを実ブラウザで見る」。Anthropic 自身の実験では、自己採点は甘くなり、独立した評価者を懐疑的に調整するほうが容易だった [F]。
3. 先に置くのはトークンと制約(DESIGN.md、機械可読ルール、コンポーネント必須)。ただし制約が強すぎると無難になる、と実践者が指摘している [F]。
4. 反復の効果は測られているが、定量の根拠は限られる。VLM 批評者を入れた 3 周で最大 +17.8%(WebDev Arena 由来の依頼、論文)[F 要旨]。Anthropic のブログは定性のみで数値なし [F]。
5. 判断の理由は「作る前に書かせ、ブリーフの項目に紐づけ、後から盲検の批評者がその主張を画面で確かめる」形にしないと後付けになる【推論】。直接これを検証した資料は見つからなかった。

## 1. 公式ガイダンス

### Anthropic

- 診断は一貫して「分布への収束」。"Safe design choices that work universally and offend no one dominate web training data." [F: https://www.claude.com/blog/improving-frontend-design-through-skills]
- ブログの手順: 既定が収束する場所を特定する → デザインの目標を、フロントエンドエンジニアが書くコードに対応づける → 「ちょうどよい高度」で書く(hex 直書きでも曖昧な方向でもない)→ 次元(タイポ、テーマ)を個別に試してから 1 つのスキルに統合 → 反収束の注意を明示する(Space Grotesk に落ち着く例)。スキル本体は約 400 トークン。効果は定性のスクリーンショット比較のみで、数値は無い [F]。
- cookbook(https://github.com/anthropics/claude-cookbooks/blob/main/coding/prompting_for_frontend_aesthetics.ipynb、raw JSON を取得)の戦略は 3 つ: 次元ごとに誘導する、インスピレーション源(IDE テーマ、文化的な美学)を示す、既定を名指しで避けさせる。一つの次元だけ分離して指定することもできる(タイポ専用プロンプトには「選んだフォントをコードの前に宣言せよ」がある)[F]。05 の「禁止リストは次の既定値になる」を、公式側も cookbook 内で認めている(Space Grotesk)。
- 最重要の新しい情報。モデル別ページ(Opus 4.8 https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8 、Sonnet 5 https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5 の "Design and frontend defaults")[F]:
  - モデルには一貫した既定の見た目がある(Opus 4.8 は暖かいクリーム地 #F4F1EA 前後、セリフ見出し、斜体の強調、テラコッタ/アンバーの差し色)。エディトリアルや飲食には合うが、ダッシュボード、開発ツール、フィンテック、医療、業務アプリには不向き。
  - 「クリームを使うな」「clean and minimal に」のような一般的指示は、別の固定パレットに移るだけ。
  - 効く 2 つ: (1) 具体的な代替を指定する(色の範囲、角丸 4px で統一、書体、構造、ボタンのホバー 160ms など、粒度の高い例文が載っている)。(2) 作る前に選択肢を出させる: `Before building, propose 4 distinct visual directions tailored to this brief (each as: bg hex / accent hex / typeface — one-line rationale). Ask the user to pick one, then implement only that direction.` Sonnet 5 では temperature が使えないため、これが方向を変える推奨手段。
  - Opus 4.8 は旧モデルより反 slop の長いプロンプトが要らず、短い `<frontend_aesthetics>` で足りる。つまりモデルが変わると必要なプロンプト量も変わる。
- Claude Code のベストプラクティス(https://code.claude.com/docs/en/best-practices)[F]: 「見た目の変更は視覚で検証する」として、`[スクショ貼付] この設計を実装して。結果のスクリーンショットを撮って元と比較し、違いを列挙して直して` を、Before(「ダッシュボードをよくして」)と対比している。検証の強さの段階は、プロンプト内 → `/goal`(別の評価者が毎ターン再確認)→ Stop フック(通るまでターンを終えさせない)→ 別のサブエージェントによる反証。「証拠(スクリーンショット)を出させる」。レビュアーは「指摘を探せと言われれば、健全でも何か出す」ので、正しさと要件に関わるものだけ報告させる、とも書いている。
- Claude Design(https://support.claude.com/en/articles/14604416-get-started-with-claude-design)[F]: 組織のデザインシステムを継承し、「出力を見せる前に自分でデザインシステムと照合して直す」。方向に迷ったら 2〜3 案を頼む(比較のほうが推測より速い)。コメントは部品レベル、構造の変更はチャット、と使い分け。Claude Code へは `/design-sync` と「スクショからでなく既存の作業を引き継ぐ」ハンドオフ。

### OpenAI

- GPT-5 の cookbook(https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_frontend)[F]: スタック(Next.js、Tailwind、shadcn/ui、Radix、Lucide、Motion)を指定して誘導する。既存アプリのスクリーンショットを画像入力にして「同じテーマで」と頼むと雰囲気を合わせる。一行で全体のテーマを変えられる。「本番にはレビューと反復が要る」。デザインシステムのスニペットは無い。
- GPT-5.4 の記事(https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)[F]。手順は次のとおり:
  1. 推論は low から始める(単純なサイトでは low/medium のほうが強い。野心的な設計で上げる)。
  2. 先にデザインシステムと制約を決める(H1 は 1 つ、書体 2 つ、差し色 1 色、ファーストビューの CTA 1 つ)。
  3. スクリーンショットやムードボードを参照として渡す(レイアウトのリズム、型のスケール、余白、画像の扱いを読み取らせる)。
  4. 最終素材の前にムードボードや複数のビジュアル案を作らせる。
  5. コンテンツ計画(ヒーロー、補足画像、詳細、社会的証明、最終 CTA)を書かせる。
  6. トークン(背景、面、主文字、弱文字、差し色)と型の役割を定義する。
  7. プレースホルダでなく実コピーと製品文脈を使う。
  8. Playwright で複数ビューポートとフローを見て、参照 UI と比較させる。
  - frontend-skill の作法: 作る前に「ビジュアル仮説(visual thesis)」「コンテンツ計画」「操作のアイデア 2〜3」を書かせる。検査問答: ブランドは最初の画面で明確か、強い視覚的アンカーが 1 つあるか、各セクションの仕事は 1 つか、装飾の影を外しても上質か。アプリ画面は Linear 的な抑制を既定にし、カードは操作の容れ物にだけ使う。ダッシュボードの文言は宣伝調でなく「最終同期」のような方向づけ。
- 実装上の含意【推論】: OpenAI の「ビジュアル仮説を先に書く」は、判断を作る前に言語化させる点で Anthropic の「4 方向を理由つきで先に出す」と同型。

### Google

- DESIGN.md の公式リポジトリ(google-labs-code/design.md の README を `gh api` で取得)[F]: YAML のトークン(正)と Markdown の散文(「なぜ」と使い方)の 2 層。`npx @google/design.md lint`(参照切れ、WCAG コントラスト)と `diff`(トークンとプローズの回帰)。仕様は alpha。05 に既出のため詳細は繰り返さない。
- Stitch のプロンプトガイド(https://discuss.ai.google.dev/t/stitch-prompt-guide/83844)と周辺ブログ [S 【弱】]: 広く始めて画面ごとに掘る。形容詞でムードを決める。design.md は毎回の生成に読まれ、具体値と意味のあるトークン名が効き、ブランド哲学の長文は効かない、という第三者の主張がある。Stitch は design.md なしだと独自の色を作りボタンの階層を誤った、というレビューもある [S 【弱】]。Prompted Variants(2025-10)で案を出し分けられる [S]。
- Gemini 3 系の公式な UI プロンプトガイドは見つからなかった。出てきたのは第三者の動画要約と、思考レベルを High にすると複雑なレイアウトに効くという Banani の記事 [S 【弱】]。

## 2. 実践者のデザインハーネス

### Money Forward Design(https://note.com/mfdesign/n/n51eb399cefc0)[F]

「何を読ませ、どの順で作らせ、どう検証させるか」を仕組み化している。
- 知識を 3 層で渡す: PROTOTYPE.md(常に守る最小の基本ルール: コンポーネントの必須利用、色と余白はトークンのみ、空・エラーを含む状態の設計、参照の索引)→ SKILL(領域別)→ リファレンス(1 ファイル 1 トピック)。
- 実装エージェント(ui-designer)とレビューエージェント(design-reviewer)を分け、1 画面 1 サブエージェントで並列に作る。画面単位のレビューで差し戻し、最後に画面横断レビュー(遷移とデータ設計の矛盾)。
- 合否は「必ず直すべき違反」の件数だけで決める。修正ループには上限があり、超えたら残件リスト付きで人間に返す(AI 同士の往復のコスト肥大を防ぐ)。
- 実装中に新パターンやスキルと実コードのずれに気づいたら、リファレンスへの追記を人に提案し、承認された知見だけが戻る。
- 効果: CRUD を網羅した数ページ分のプロトタイプが 1 日、大半の機能が 1 週間。フロント実装の約 80% が自動生成(記事の主張で、第三者の測定ではない)。指示の方式が「部分ごとの修正の繰り返し」から「全体を大まかに作ってレビューで精密化」へ変わった。
- 同社の別記事(https://note.com/mfdesign/n/ndbf39b29d5c4)は、AI 利用がレビュー観点の洗い出しとアクセシビリティ確認に限られ、手順の詳細は無い。01 にあった「別のモデルに反論させる」「提案と判断を別々に記録」は、この 2 本の本文には書かれていない(kgsi の紹介文由来で、元記事での裏付けは取れなかった)。

### NestUI(カナリー、https://note.com/canary_inc/n/n538adfe8daee)[F]

- 1 枚の DESIGN.md は原則と具体値が混ざり、同じルールが重複し、禁則を足し続けると CLAUDE.md のように肥大する。そこで「答える問いごとに正本を 1 つ決める」: 値=トークン JSON、判断=ガイドライン文書、部品の組み方=部品ごとの仕様、ページ骨格=HTML 10 パターン。各文書が答える問いを索引に 1 行で書く。
- 発散(生成)時は設計原則、禁則、ページ構成、用字用語、ブランド指針を毎回読み、部品選択は必要なときだけ読む。収束(レビュー)時は観点ごとに読むファイルを絞る。
- レビューで得た知見は、その画面だけの判断か共通ルールかを人が仕分け、昇格・降格を提案として出して人が承認する。運用状況: 問いごとの分割と読み分けは運用中、知見を戻す仕組みは部分運用。定量の検証は書かれていない。分割後の 3 か月はメンテナーだけが参照ファイルを更新し、出力が安定してから公開、約 1 か月後に他メンバーの PR が出るようになった。

### 「デザインハーネス」論(note.com/fugusaka、https://note.com/fugusaka/n/n592aefe37c84)[F、要約取得]

- 4 層: 制約(AI とツールが読める形で)/文脈(DESIGN.md)/検証/フィードバック(違反時に理由と代替を返す)。
- 機械可読ルール(rules.json)は少数から始める。「99 個はいらない。5 個でいい」。禁止例: 特定の文字色クラス、特定の影クラス、独自 px の増加、勝手な新色、`<button>` の直書き。DESIGN.md の原則も 5 つ程度。
- 検出対象はルール違反、スキーマ不整合、ドリフト(角丸のばらつき、カードの影の差、余白の崩れ)。CI は比喩として使われるだけで、組み込み方は書かれていない。
- 制約が強すぎると出力が無難になり個性が消える。だから禁止だけでなく理由と例外条件も書く。
- 注意: 取得は内容を絞った要約経由。CodeZine の連載(https://codezine.jp/article/detail/29615 、「AI生成UIをCIで守る」)は bot 対策(Security check)で本文を取れず、検索要約の「制約・検証・フィードバックでエージェントを包む。生成された画面を公開してよいかの判定だけが目視に残っている」しか確認できていない [S 【弱】]。

## 3. 測れている効果

| 手段 | 根拠 | 効果の大きさ |
|---|---|---|
| 作る側と評価側の分離+Playwright での採点 | Anthropic Engineering "Harness design for long-running apps"(https://www.anthropic.com/engineering/harness-design-long-running-apps)[F] | 5〜15 周で評価点が上昇後に頭打ち。最初の周でも無指示のベースラインを上回る(基準自体が既定から引き離す)。最良は最終周と限らず、中間を選ぶこともあった。数値の比較表は無い |
| VLM 批評者の構造化フィードバック | arXiv 2604.05839(要旨)[F] | WebDev Arena の依頼で 3 周、最大 +17.8%。LoRA に蒸留すると利得の 25% |
| 反復編集+実行フィードバック | arXiv 1D-Bench 2602.18548(要旨)[F] | 描画成功率が上がり、視覚の類似度も「しばしば」上がる。RL による編集は「限定的で不安定」 |
| 反復して見た目を最適化 | UI2Code^N arXiv 2511.08195(要旨)[F] | 反復で性能が一貫して向上。ただし UI→コード(参照画像あり)の設定で、ゼロから創るデザインの質ではない |
| 改善の対象を 1 つに絞る | RubSE arXiv 2608.24138(要旨)[F] | 局所修正が他の領域を壊す(視覚の修復結合)。ルーブリックで優先対象を 1 つ選び履歴を持たせると、素朴な自己改善より安定 |
| 過去の指示を毎回批評して再確認 | FronTalk arXiv 2601.04203(要旨)[F] | 多ターンで既存機能を上書きして壊す。批評で忘却がほぼゼロになり、性能 56.0%→65.3% |
| 参照画像+キャプションの併用 | MT-Web2Code arXiv 2608.03474 の検索要約 [S 【弱】] | キャプションは、モデルによっては逆に約 4.5 点下げた(視覚の構造から逸れる)。画像だけのほうが良い場合がある |
| 参照画像 vs テキスト仕様の直接比較 | 該当する対照実験は見つからなかった | 不明 |

- 自己評価は甘い。Anthropic: "agents reliably skew positive when grading their own work"。独立した評価者を懐疑的に調整するほうが現実的。評価側にも few-shot で較正した詳細な採点基準が要り、それでドリフトが減った [F]。
- 基準の文言が出力を引っ張る。"the best designs are museum quality" という一文が特定の見た目への収束を起こした [F]。
- 設計の好みは人によって割れる。DesignPref(arXiv 2511.20513、デザイナー 20 人が同じ 600 UI を評価)の一致度は平均 κ=0.25 [S]。批評者の点を絶対視できない根拠になる。
- Design Arena の公開された研究は見つからなかった(リーダーボードの存在を論文が引用しているだけ)[S]。

## 4. 効く手順(根拠つき)

1. **作る前に、ブリーフから方向を 3〜4 案、理由つきで出させ、人または別の批評者が 1 つ選び、それだけを作る。** 根拠: Anthropic モデル別ページの推奨(一般的な禁止は別の固定パレットに移るだけ)[F]、Claude Design の「複数案の比較は推測より速い」[F]、OpenAI のムードボード+ビジュアル仮説 [F]。
2. **既定の見た目が合わない領域(業務アプリ、開発ツール、医療など)では、具体的な代替を指定する。** 色の範囲、角丸、書体、間隔、ホバーの時間まで。根拠: Anthropic Opus 4.8/Sonnet 5 のページ(モデルは明示仕様に精密に従う)[F]。
3. **トークンと制約を最初に置き、少数の機械可読ルールから始める。** 5 個から。根拠: MF の「色と余白はトークンのみ、コンポーネント必須」[F]、fugusaka の「5 個でいい」[F]、OpenAI の「トークン→型の役割」[F]。ただし制約が強すぎると無難になる(fugusaka の注意)ので、理由と例外も書く。
4. **作る側と、スクリーンショットを見る批評者を分け、批評者に採点基準(例: 一貫性、独自性、仕上げ、機能性)を与える。** 評価は実ブラウザ(Playwright)で、複数ビューポートで。根拠: Anthropic の実験 [F]、論文 2604.05839 [F]、Claude Code のベストプラクティス(証拠を出させる、別コンテキストのレビュー)[F]。盲検にするかは 05 の jury を参照。
5. **修正ループの上限と、合否基準を先に決める。** MF は「必ず直す違反の件数」だけで合否を決め、上限を超えたら人に返す [F]。Anthropic の実験は 5〜15 周で頭打ちと報告 [F]。最終周が最良とは限らないので、各周のスクリーンショットを残して選べるようにする【推論】。
6. **1 周で直す対象を絞る。** RubSE の知見(局所修正が他を壊す、優先対象 1 つ+履歴)[F 要旨]。FronTalk の知見から、過去に確定した要素は毎周で再確認する [F 要旨]。
7. **実データ・実コピー・状態(空、読み込み中、エラー、権限不足)で見る。** 根拠: MF(状態を設計対象に含める)[F]、OpenAI(実コピー)[F]、Figma(確定前に例外ケースを詰める)[F 薄い]。
8. **人のフィードバックは言葉でなく要素に固定して渡す。** Agentation の構造化出力、crit の DOM コメント [F]。効果の測定は無いが、「推測させない」点で筋は通る【推論】。
9. **レビューで得た知見は、人が仕分けてから正本に戻す。** NestUI(その画面だけの判断/共通ルール、昇格は提案→承認)[F]、MF(追記提案→承認)[F]。

## 5. 効かない/逆効果

- **一般的な禁止・形容詞**(「クリームを使うな」「clean and minimal に」)。別の固定パレットに移るだけ(Anthropic 公式)[F]。
- **禁止リストの継ぎ足し。** 次の既定値になる(05)。NestUI は CLAUDE.md のように肥大すると明言 [F]。
- **強い制約だけ。** 出力が無難になり個性が消える(fugusaka)[F]。
- **自己採点だけに頼る。** 甘くなる [F]。
- **「museum quality」のような誘導的な基準語。** 特定の見た目に収束させる [F]。
- **反復の無制限化。** 頭打ちがある。AI 同士の往復はコストが膨らむ(MF は上限を設けた)[F]。レビュアーに「指摘を探せ」とだけ言うと健全でも何か出し、過剰な作り込みを招く(Claude Code の docs)[F]。
- **画像に説明文(キャプション)を足せば良いとは限らない。** モデルによっては悪化 [S 【弱】]。
- **レビュー全体を一度に直させる。** 局所修正が他を壊す(RubSE)[F 要旨]。
- **モデルを替えても同じ長いプロンプトを使い続ける。** Opus 4.8 は旧モデルより短い指示で足りる [F]。古い長文は過剰になりうる。

## 6. 判断の理由を、後付けにせずに残す

直接検証した資料は見つからなかった。使える部品と、そこからの推論を分けて書く。

- 部品(根拠あり): (a) Anthropic の推奨プロンプトは「各案を `bg hex / accent hex / typeface — one-line rationale` で出し、人が選び、選んだものだけを作る」[F]。つまり理由は選択の前に出る。(b) OpenAI は作る前に visual thesis とコンテンツ計画を書かせる [F]。(c) Claude Code は「計画してから実装し、計画に照らして検証する」「計画に対する差分レビューを別サブエージェントでやる」[F]。(d) DESIGN.md は値と理由の散文を同じファイルに持つ(Google)[F]。(e) Anthropic の評価実験では、自己評価が甘いことと、独立評価者が懐疑的に動くことが確認されている [F]。
- 後付けの危険を指摘する資料: CRONOS(OSS)は「エージェントに説明させると事後の合理化になる」と述べ、検索・ツール呼び出し・捨てた仮説を実行中に記録する設計を採る [S 【弱】、ベンダー主張]。
- プラットフォーム側の制約: 推論そのものの再現を応答に求めると `reasoning_extraction` で拒否されうる。短い説明と行動の要約は可 [F: Sonnet 5.5 のページ]。判断の記録は「内部の推論」でなく「選択・代替・根拠」を書かせる形にするのが安全。
- 【推論】以上から、後付けになりにくい運用は次の形。
  1. ブリーフに項目番号を振る(目的、利用者、状況、禁止、必須の状態)。
  2. 作る前に、決める事柄(方向、書体、情報の密度、主要な操作の位置)ごとに「選択/捨てた代替/根拠となるブリーフの項目番号」を書かせ、ファイルに残す(DESIGN.md か決定記録)。作った後に書かせない。
  3. 実装後、盲検の批評者にはスクリーンショットと「主張の一覧」(各決定が画面でどう表れているはずか)を渡し、画面が主張を満たすかを判定させる。理由の文を評価させず、画面で確かめられる主張に落とす。
  4. 理由がブリーフの項目に結びつかない決定は、「好み」として別に印を付ける(隠さない)。
  5. 実装中に決定を変えたら、変更履歴として追記し、書き換えない。
  この運用が実際に後付けを減らすかは測られていない。
