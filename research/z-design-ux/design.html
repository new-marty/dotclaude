UI実装前のUX設計スキル(z-design-ux)の設計案

「アプリを作りたい」と頼まれたとき、経験を積んだUXデザイナーとして振る舞うスキルです。依頼をそのまま受けず、捉え直して、具体的な案を出しながら聞き返します。画面を描く前に、誰の何を解くか、何を作るか、どんな画面と状態が要るか、どんな体験にするかを決めます。色や書体などの見た目は扱わず、実装する側に任せます。

できあがるもの:作るアプリのリポジトリに置く設計資料(小さな案件なら docs/ux/<名前>/UX.md の1枚)。

  • 問題と、やること・やらないこと
  • 扱うもの、役割と権限、操作の流れ(図と表)
  • 画面の一覧と、画面ごとの目的、載せる内容の重要度順、状態
  • 体験の方針(トーン、優先する原則、避けたい体験)
  • 見た目を実装する担当(frontend-design というスキルや、エンジニア)への1ページの依頼書

最初の返事で違いが出る

依頼は「家計簿アプリを作りたい」の一言だけ、という想定です。左は、いまの Claude やエンジニアが返しがちな返事です。右が、このスキルが目指す返事です。

よくある返事

家計簿アプリですね。次の機能を考えました。

  • 支出と収入の登録
  • カテゴリ別のグラフ
  • 月ごとの予算
  • 口座連携
  • ユーザー登録とログイン

ターゲットユーザーは「30代の会社員、田中さん(仮)」です。技術スタックは何にしますか?

機能の一覧にすぐ飛ぶ。架空の利用者を作る。聞いているのは作り方だけ。

このスキルの返事

観察
家計簿は、作る人は多いのに続く人が少ない領域です。調べると、記録は「やめる」より「途切れて、また戻る」のが普通だという研究があります。
捉え直し
作るのは記録帳ではなく、「今月使いすぎているか」が最小の入力で分かる道具、と捉えてはどうでしょう。
たたき台
最初の画面は「今月あといくら使えるか」の数字1つ。1件入れるとその数字が動く。2週間空けて戻っても責めない。
やらないこと
口座連携、グラフの種類を増やすこと。最初の離脱の原因になりやすいため。
この案が外れる条件
3日続けて記録されないなら、入力の仕組みから考え直します。
質問
最後に家計簿をやめたとき、何がきっかけでしたか。誰と一緒に使うものですか(一人か、夫婦か)。

捉え直し、たたき台を出してから聞く。質問は「最後に〜したとき」と、過去の具体的な出来事を聞く。

デザイナーとして振る舞うための3つの層

① 構え(どう考え、どう話すか)

熟練デザイナーの研究(Schön、Cross、Dorst など)と第一線の実務家の発信から、行動の形にしたものです。

  • 依頼を「どういう問題か」と言い直し、別の捉え方を1つ並べる
  • 聞くより先に、たたき台を出して「違うならどこか」を聞く
  • たたき台を作って分かったこと(新しい問題、前の決定との矛盾)を書き出す
  • 案を2つ持ち、その案件に固有の基準で比べる。推奨は1つにし、何を犠牲にするかを書く
  • この案が外れる条件を書く

② 視点(何を見るか)

エンジニアや素人が見落としやすいことを、問いの形で約40個持ちます。工程ごとに、その案件に関係するものを選んで使います。例を挙げます。

  • 使う場面:どこで、何を手に持って、何に邪魔されながら使うか
  • 使われ方の型:何時間も居続ける道具か、さっと開いて閉じる道具か
  • 時間の流れ:初日、30日後、3か月空いた後、やめるとき
  • 画面の外:メール、電話、紙、受付スタッフの動き
  • 感情:お金や健康の場面で、不安や恥ずかしさをどう扱うか
  • 誰が取り残されるか:片手しか使えない人、高齢の人、代わりに予約する家族

③ 骨組み(順番と検査)

工程の順番、各工程で決める問い、抜けを見つける検査です。第2版から引き継ぎます。①と②が良い問いと案を出し、③が抜けを防ぎます。

答え(家計簿ならこう、予約ならこう)はスキルに書きません。案件ごとにその場で調べるか、聞くか、考えます。

使うと何が起きるか(家計簿アプリの続き)

聞くはユーザーにしか答えられないこと、調べるは Web やコードで分かること、考えるは根拠を示してスキル自身が決めることです。

S0受付

調べるリポジトリを読む。コードも資料もないので、個人向けの新規アプリで規模は小、と判定する。人が答えられる会話かどうかもここで確かめる。

聞く上の「このスキルの返事」を返す。

S1問題と範囲

考える答えを受けて、問題「月末まで使いすぎに気づけない」、成功の測り方「週1回以上の記録が1か月続く」、やらないことを決める。

聞くここで一度、問題と範囲が合っているか確認する。

S2構造

考える扱うもの(支出、カテゴリ、予算、月)と、主な流れ「支出を記録する」を、失敗の分かれ道も含めて書く。流れの案を2つ(買ったその場で入れる型、夜にまとめて入れる型)作り、「最初の1件までの時間」「月末の手間」で比べる。

たたき台から分かったこと:「夫婦の共有カードの支出は誰のものか」が決まっていない。未決事項に加える。

S3画面と状態

考える画面の一覧(ホーム、記録、履歴、予算設定、初回設定)と、画面ごとの状態(まだ空、予算が未設定、予算を超えた、2週間ぶりに開いた)を決める。

検査で見つかったこと:「データを書き出す」と「アカウントを消す」の画面がない。やめる人のための画面として足す。

聞く画面の一覧ができたところで、方向が合っているかをもう一度確認する。

S4体験の方針

考えるトーンは「使いすぎを責めない」。原則は「正確さより、続けやすさを優先する」。避けたい体験は「開くたびに叱られる感じ」。繰り返し出てくる操作の型(取り消しは確認ダイアログでなく数秒の取り消しボタン、など)をまとめる。

色や書体は決めない。ユーザーから決まったロゴや色を渡されたら、それはそのまま依頼書に載せる。

S5引き渡し

docs/ux/kakeibo/UX.md にまとめ、冒頭に実装担当への依頼書を置く。検査の結果と未決事項を書き、「次は frontend-design にこのファイルを渡してください」とユーザーに伝える。次の工程を始めるのはユーザーです。

この例でユーザーが聞かれるのは、S0 の質問、S1 の後の確認、S3 の後の確認の3回です。

工程と、それぞれで決めること

工程決めること特に使う視点出力
S0 受付新規か既存の改善か。規模(画面数の見込み、役割の数、規制の有無で判定)。人が答えられる会話か依頼の捉え直し前提、規模、最初の返事
S1 問題と範囲誰のどんな問題か。成功の測り方。やらないこと。最も危ない前提使う場面、時間の流れ、画面の外、誰が取り残されるか問題文、成功の測り方、やらないこと、前提の一覧。ユーザーに確認
S2 構造扱うものと関係。誰が何をできるか。主な流れと失敗の分かれ道。案を2つ比べた結果使われ方の型、頭の中の整理と画面の整理が合っているか、関わる人全員扱うものの一覧、役割と権限、操作の流れ
S3 画面と状態要る画面。各画面の目的、一番の操作、内容の重要度順、状態今の状態が分かるか、次に何をすればいいか分かるか、取り消せるか画面一覧、画面ごとの説明、状態表。ユーザーに確認
S4 体験の方針トーン、優先する原則、避けたい体験、繰り返し出てくる操作の型感情、信頼、「Aを優先しBは譲る」の形の原則体験の方針(色や書体は含めない)、操作の型の一覧
S5 引き渡し実装担当が見た目を作るだけで済むか初見、初回、3週間後の3つの場面で自分の案を見直す依頼書、検査結果、未決事項、次に使うもの

既存フローの改善では、S1 の前に「診断」を挟みます(どのステップで何割が離脱しているか、など)。数字がもらえなければ、測り方の計画を出し、改善案は仮説として扱います。

聞く、調べる、考えるの決め方

分からないことが出たら、次の順で決めます。

  1. ユーザーにしか分からないこと(目的、制約、過去の出来事、やらないこと)なら聞く。
  2. 公開資料やコードで確かめられること(法令、その分野の慣習、競合のやり方)なら調べる。
  3. どちらでもなければ、根拠を書いて考える。

聞き方の決まりです。

  • 聞くのは、答えで決定が変わり、推測で進むと手戻りが大きいときだけにする。それ以外は未決事項に入れ、最後にまとめて渡す。
  • 「最後に〜したとき、どうでしたか」と過去の出来事を聞く。「ユーザーは気に入ると思いますか」のような仮定の質問はしない(答えが当てにならないため。The Mom Test)。
  • 確認は S1 の後(問題と範囲)と S3 の後(画面の一覧)の2回置く。人がいない実行では、質問を前提の一覧に変えて進め、資料の冒頭に「未確認」と書く。

調べ方の決まりです。

  • 1つの工程で検索は5回まで。出典が2つ一致したら止める。見つからなければ「推測」の印を付けて進む。
  • Web が使えない環境では、すべて「推測」として扱い、資料の冒頭に「未調査」と書く。

書いた記述には印を付けます。印は4種類で、「ユーザーの発言」「公開資料(URL付き)」「ユーザーが渡した実データ」「推測」です。ユーザーが自分の利用者について話したことは「ユーザーの発言」として扱い、利用者本人の声とは区別します。架空の利用者像(名前、年齢、セリフ)と根拠のない数字は書きません。AI が作る利用者像は、もっともらしく見えても偏っているという研究が複数あるためです。

抜けを見つける3つの検査

案件の大きさによらず、検査は省きません。小さな案件で減らすのは資料の量だけです。調べた限り、既存の Claude 向け UX スキルはどれも「エラー状態も考えること」と注意書きするだけで、抜けを見つける仕組みを持っていませんでした。

① 画面の作り忘れ

扱うものごとに、一覧、詳細、作成と編集の画面が要るかを1つずつ決めます。依頼に書かれにくい共通の画面(ログイン、設定、データの書き出し、退会、404 など)のリストも、すべて「要る」か「要らない、理由」で埋めます。

② 流れと画面のつながり

操作の流れのどのステップも、どれかの画面で行われること。どの画面も、どれかのステップで使われること。両方向から確かめ、どこにもつながらない画面やステップがあれば不合格です。

③ 画面ごとの状態

画面ごとに、空、読み込み中、エラー、権限なし、上限超え、通信切れ、同時に編集された、データが極端に多い、などの場面を「設計した」か「起きない、理由」で埋めます。空欄は不合格です。

例:予約一覧(受付の画面)まだ空該当なし読み込み中エラー権限なし同時に操作極端
どう見せるか「最初の予約枠を作る」へ案内絞り込みを解除するボタン行の形の仮表示再試行、入力は保持看護師は見るだけ同じ枠を2人が確定したら、後の人に別の枠を出す1日120件、長い名前

検査をすり抜けないための決まりです。

  • 表の列と ID の付け方を固定します(画面は SC-01、流れのステップは F1-03 など)。スクリプトはこの表だけを読みます。
  • 「起きない」の理由に「不要」「該当なし」とだけ書いた場合は、不合格にします。
  • 「起きない」が全体の4割を超えたら、人の確認に回します。
  • 記述に付けた印もスクリプトで数え、「推測」が多ければ資料の冒頭に警告を出します。
  • 中身が妥当かは、作業の経緯を知らない別の AI がレビューします。方針の良し悪しは人が見ます。

中規模以上の案件では、工程ごとの途中経過を docs/ux/<名前>/ に書き出し、進み具合を STATE.md に残します。途中で会話が切れても再開できるようにするためです。SKILL.md は英語で書き、起動の言葉に日本語を入れます。出力はユーザーの言語で出します。

決まったこと

  1. 別の捉え方:毎回、捉え直しを1行は出す。作るものが変わるほどの捉え直しのときだけ、別案として詳しく比べる。
  2. 途中の確認:S1 の後(問題と範囲)と S3 の後(画面の一覧)の2回。
  3. 見た目:扱わない。S4 は体験の方針だけにする。
  4. frontend-design との起動の順番:対策しない。説明文は普通に書き、起動のテストは「このスキルが起動すべき依頼で起動するか」だけを見る。

第2版から変えたこと

  • S4 を「見た目の方針」から「体験の方針」に変えた。色や書体は方針も含めて扱わず、実装側に任せる(Marty の判断)。
  • デザイナーとしての「構え」と「視点」の層を足した(Marty の指摘)。そのために、熟練デザイナーの研究、プロの質問、見落としやすい視点、第一線の実務家の発信を追加で調べた。
  • 聞く、調べる、考えるの決め方に順番と上限を付けた。人がいない実行と、Web が使えない環境での扱いを決めた(レビューの指摘)。
  • 検査の表の書式と、「起きない」で逃げられないための決まりを足した(レビューの指摘)。
  • 評価を公式の手順に合わせた。起動のテストを約20件、Sonnet と Opus の両方で試す。判定項目は、スキルなしで1回走らせた結果を見てから足す。
  • 家計簿、予約、会員登録で外せない点は、引き続きスキルに入れず、試験側(EVALS.md)に置く。
