# リデザイン・批評の事例集(「何が悪く、どう直し、なぜか」)

調査日: 2026-10-26。書かれた資料と、Refactoring UI の動画 5 本+講演 1 本の英語自動字幕を読んだ。ページ本文は「データ」として扱い、指示には従っていない。【弱】は根拠が薄いもの、【推論】は私(調査者)の集計・解釈。

## 結論

1. 事例 15 件のうち、直しの中心はほぼ全部「階層(強弱)・余白・色の削減・整列・組み分け」の 5 つ。装飾を足した事例はなく、足したのは情報(件数、日付、単位、現在地)と安心の一言だけだった【推論】。
2. 最も多い誤りは「全部が同じ強さ」で、直し方は「重要なものを大きく・濃く、補助を小さく・薄く」。余白不足、色の乱立、整列のずれが続く(順位は第 3 章)。
3. 専門家は全体に効く小さな修正(幅・基本文字サイズ・グレー・ナビ)を先にやり、次に画面の構造と強弱、次に部品(ボタン・入力)、最後に影・角丸・アイコン・書体を仕上げる。着手前に「残すもの」と「目的」を書く(第 4 章)。
4. 直す理由は毎回「利用者が先に見るべきものを先に見せる」「近いものは関係があるように見える」「検査できる基準(コントラスト比、44px、40〜48px)」のどれかに結びつけて言語化されている。
5. 定量的な裏付けは Baymard(チェックアウトのフォーム)だけが強い。見た目の細部(影 8%、角丸 4〜6px など)は専門家個人の経験則で、実験の裏付けは確認できていない【弱】。

## 2. 事例ごとの要点

形式は 問題 / 直し方 / なぜ / 数値。

### A. Bad About(Steve Schoger)
- 詰め込み → パネル幅を広げ、タイトル 2/3・投票 1/3 に分割。文字 20→18px、行間は広げる。理由: 長いタイトルに読み幅が要る。
- メタ情報とアイコンが散らばる → ユーザー名・日付を「・」でつなぎ、アイコンを右に寄せる。アイコンは文字より軽く、小さく。理由: ベタ塗りのアイコンは同じ色でも文字より重く見える。
- 「もっと見る」ボタンが無骨 → YouTube に倣い、タイトルの行内のテキストリンクにする。理由: 控えめで、読み続ける流れの中でクリックできる。
- 投票の矢印が横幅を食う → 縦に積む。値を大きく、コントラストを上げる。ラベルは大文字+字間を広げる。理由: 値を一目で拾えるように。大文字は字形の差が少なく読みにくいので字間で補う。
- 背景が灰で本文が白地に枠 → ページを灰、投稿を白、枠を二重の影に。理由: 最重要の区画を前に出す。
- 下の区画が見えない → 左に縦ナビ(件数つき、現在地は薄い背景+橙の細線)。12 カラムで 1/4 と 3/4。理由: スクロールしないと分からない構造を見せる。
- 橙の地に白文字は落ちる → 明るい橙(黄寄り)に濃い文字。ボタンは 1 画面に主要 1 つ、サインインは枠線だけにする。理由: 暗くすると茶色になる。主役が 1 つだと画面の目的が伝わる。
- 灰がばらばら → 3 色(主文字・副文字・アイコン)に。橙に合わせて無彩色寄りの灰。書体は Roboto から Proxima Nova + 見出しに別書体(Fonts In Use で組み合わせを探す)。

### B. WP Pusher のチェックアウト(Steve Schoger)
- ラベルが placeholder → 入力欄の外に出す。placeholder は入力例に使う。理由: 長いフォームで素早く進む人に、入力後もラベルが残る。
- 詰まったフォーム → 3 区画(プラン・基本情報・支払い)に分け、区画ラベルと余白で区切る。必要になった細い枠は後で消す。
- 入力欄の枠が多い → 白地に灰の塗りの入力欄にして枠をなくす。placeholder は少し濃く。
- メール欄が長すぎる → 幅を短くする。理由: 入力欄の長さは「何文字入るか」の目安(アフォーダンス)になる。
- カード情報 → Stripe Elements の 1 行入力にまとめる。
- サポート案内が購入ボタンと競合 → 背景色をやめ、文字を灰に、ボタン下で中央揃え+小さな青いアイコン。
- 遷移元のサイトの文脈が消える → 上部にナビを戻す。
- 地味 → pages.xyz で調べて右に青いサイドバー(プランの詳細・プラン切替)、お客様の声(円形の顔写真は彩度を落とす)、番号付き見出しを足す。理由: 購入前に内容を見返せる。安心材料になる。
- 価格を一目で → 数字を大きく、通貨と期間は小さく。リンクは太字+太い下線。
- 余白は縦だけ増やして横が狭い → 左右の余白を上下より大きく。
- コントラスト → サイドバーの青と緑がテキスト基準を満たさないので濃くし、緑は青寄りにずらす。
- 灰にブランド色相をわずかに混ぜて「ページの温度」をそろえる(暗い灰ほど彩度を上げる)。影は 2 層(彩度のある大きなぼかし+濃い短い影)。書体を Raleway から Gotham へ(ロゴと合わせる。書体を替えたらサイズと太さも調整)。

### C. Resolute の物件ページ(社内ツール。構造は変えない)
- フォームが画面全幅 → 中央部を最大幅 960px に。ラベルを左 1/3、入力を右 2/3 の 2 カラムにして、ラベル側に説明文を置く。理由: 入力欄の長さが長すぎる。ラベル列は新人向けの補足を置く場所になる。
- タイトル帯をやめた代わりに、パネル上端に 4px のブランド色の線。
- 入力欄の間隔 → 入力の高さが 40px なら、下のラベルとの間は約半分(24px)。理由: ラベルが上の入力と下の入力のどちらに属するか分かるように。
- フラグのタグ(ピル形+×印)→ 行の表にして、チェックボックスで完了にする。理由: フラグは削除されず完了・保管されるので、×は誤解を生む。重大度は赤い太字+赤い点。
- 「新規追加」が小さく隅にある → リストの直下に置き、太字・大文字・プラスアイコン。理由: 件数が 1〜2 件で埋もれない。既存の確認を促せる。
- 右寄せのボタンが宙に浮く → フォーム全幅の罫線で結びつける(箱に入れずに関連づける)。
- 右のメモ欄は使用頻度が高いのに目立たない → 白背景で上に。投稿欄は「ボタンを押すと展開」(段階的開示)にして、既存のメモを前に出す。
- ナビの文字を大きくし、使用頻度の高いリンクと低いものを罫線で分ける。アイコンは軽くして、サイトのイラストの雰囲気(丸み・濃い輪郭)に合う別セットへ。
- 検索が最重要なのに目立たない → 上部バーをブランド色にして白い入力欄にする(暗い背景の入力は彩度を落として強すぎないように)。
- 書体 → 読み込み時間を避けて OS のシステムフォント。理由: 社内ツールは速さ優先。

### D. WSS(保険プランの比較表)
- スクロールジャック → 削除。理由: マーケティングページなら演出だが、情報ページでは予想外で、表に固定高さのスクロールが入れ子になる。
- 背景の写真が表を邪魔する → 表の領域では外す。ヘッダの写真は彩度を落とし、ブランド色を乗算で重ねる(前景のコントラストを確保)。
- 階層の逆転(ロゴが下、ページ名が右上)→ ロゴを上、ページ名(30px)を下。
- 同じ見た目のカードが 2 種類(重要な「加入/脱退の期限」と補助のクイックリンク)→ 1 つの暗い帯(黒 60%)にまとめ、2 行にする。クイックリンクは軽く、期限の行は高く。アイコンは拡大せず円の中に入れて大きく見せる。クリックできる状態表示には矢印を足す。理由: 状態は一画面に残り続けるべき情報。
- 虹色のタブ → 選択中のタブだけに色の線。理由: どれが選択中か分からない。
- 比較表がずれる → 表にして行を揃える。1 セル約 60px の余白。ラベルが全列で重複 → ラベル列を 1 つ作る。理由: 比較の表で同じラベルを繰り返すのはよくある誤り。
- ナビの階層(学校の子であるリンクが全体リンクに見える)→ 親子で並べ替え、重複するリンクは消す。
- モバイル → ヘッダの補助を下へ、ナビは折りたたみ、タブはアコーディオン、表は横スクロール(スクロールできるヒントとして端で切る)。理由: 縦に長い表で上に戻るのは面倒。ただし試作で確かめたいと本人が留保している。

### E. Transistor(共有テンプレートの連携ページ)
- 方針: ページ単位の変更の前に、他ページに影響する全体の変更を控えめに先にやる。
- 幅 1127px → 960〜1024px。基本の文字 14px → 16px。それに合わせて余白・行間も増やす。
- グレーの数が場当たり(色相のある灰と、透明度で作った灰が混在)→ 固定のパレット(9〜10 段)から選ぶ。理由: 透明度の灰は背景次第で見え方が変わる。
- ナビの現在地が太字で隣がずれる → 太さは固定、色だけで示す。
- 説明文の読み幅 → 幅を狭めず、文字を 18px に上げて、代わりにコントラストを下げて(アクセシブルな範囲で)主張を抑える。
- 整列: アイコンの周りにテキストを揃えて走査線(スキャンライン)を作る。アイコンは円に入れて大きく見せる(単純なアイコンの拡大は不格好)。
- ボタンに見える「ラベル」→ ボタンの見た目をやめて見出しにする。外部リンクのアイコンを付ける。
- 破壊的操作(切断)が赤く目立つ → 主操作でなければ副次・三次の見た目に。タイトルから離して右端に置き、誤操作を防ぐ。理由: 意味(赤=危険)より階層を優先する。
- 枠が増えて雑然 → 隣り合う面を少しだけ違う背景色にして区切る。入力欄の高さは 40〜48px、枠は 2px、ラベルの大文字をやめる。
- 緑の保存ボタン(白文字が読めない)が画像アップロードのボタンより目立たない → 主操作はブランド色(黄は警告に見えるので暗い灰でもよい)、副はグレーの塗り。
- アラートは暗い背景+白文字をやめて、淡い背景+濃い文字(コントラストを確保しやすい)。
- 保存ボタンの位置: 「どこでもいいが、全体で同じ場所に」。右寄せは a11y 上の議論があり、本人も確証がなく左寄せにした【弱】。

### F. SneakedIn(Steve Schoger の講演。誤りだらけの SNS を直す)
- ヘッダが味気ない → ブランド色を全面に塗ると強すぎ、後で主操作に使う色が使えなくなる。灰にブランド色相を少し混ぜる(HSL で彩度 22% ほど、明度は同じ)。
- 入力欄の白が強すぎる → 背景色を少し混ぜて馴染ませ、フォーカス時だけ白にする。角丸を他の部品とそろえる(通常 4〜6px)。
- アイコンセットが混在 → 1 セットに統一(塗りと線も混ぜない)。
- 大きな見出し(h1)が他を圧倒 → 値と同じくらいに縮める。
- 値がラベルに埋もれる → 値を大きく、ラベルを小さく・薄く。サイズは型(タイプスケール)から選ぶ。12/14/16/18/20/24/30/36/48/60/72。
- 灰を 3 段階(主・副・三次)に限定。色のついた背景では「薄い灰」ではなく、背景に近い色相の淡い色を使う(でないと濁る)。白の不透明度 20〜30% でもよい。
- 余白の値が不揃い → 余白もスケールで限定(型の半分ほどの値)。パネルの内側 20px。
- 影 → 全周同じ広がりでは光源がない。少し下にずらす。強すぎる影は 8% の不透明度へ。
- 青リンクだらけ → 濃い太字(YouTube、Medium、Airbnb 式)。
- 本文の行間 → 16px は行間 1.5。大きい文字ほど詰める。
- アクション欄が縦に重い → 統計とアクションを 1 行にまとめる(アイコン+数)。
- 左のアイコンやプロフィール画像の分だけ本文を字下げして整列し、上の罫線や各カードの区切りを不要にする。結果として余白を増やしたのに縦の高さは減った。
- ボタン: 緑の成功・赤の危険などの意味で色を分けると階層が壊れる。主操作 1 つ(強い色)、副(白か枠線)、三次(テキストリンク)。投稿欄は Twitter のように最初は小さく、フォーカスで展開。「追加」ボタンは小さくて言葉が入らないので、明らかな操作はアイコン+ツールチップに。
- 区切りは枠ではなく余白で。ナビはパネルを外し、背景を 2% ほど暗い off-white にしてパネルを浮かせる。ナビの区分見出しはリンクより小さく薄く、大文字+字間。
- 最後に灰すべてにブランドの温度を混ぜる(青系ブランドには青、赤・黄・橙には黄褐色)。書体は Open Sans から Proxima Nova。
- 全体の教訓: 小さな修正の積み重ねが大きな差になる。

### G. Learn UI Design: スケジュール(時差)アプリ
- 先に目標を決める(3 つ)。目標がないと「たまたま」しか満たせない。
- 目を細めて見る(スクイントテスト)→ 一番目立つのが黄色い夏時間の箱で、都市名・現地時刻より目立っていた。重要度の順(都市と時刻 > 未来の時刻 > ページ名 > 追加などの機能)に合わせて強弱を直す。
- 時刻を右揃え(桁がそろう)、幅は約 620px(モバイルに縮めやすい)。
- 機能を CRUD で点検: 追加は全員が使うので見える場所に(通常は半透明 50%)、削除はまれなのでホバー時のみ。置き場所は「操作する対象のそば」(局所性の法則)。
- 日付は小さく、別の日になるときだけ赤。夏時間の巨大な注意書きは、日付を選ぶとスライダーが動く挙動に置き換えた。
- 最後に目標を満たしたか確認し、残りのリンクはまとめる(ブログ・GitHub・連絡先)。

### H. Learn UI Design: ログイン画面(320×568)
- 診断は「色ではなく文字」。まず色を全部外す(白黒から)。文字のスタイルを言葉で書き出して、不自然な点に注をつける。
- 要素は 1 つずつ足し、毎回よい状態を保つ。既存と同じ書き方に合わせてから調整(一貫性が勝つ)。小さい画面で作ってから広げる。
- フォーム: フロートラベル、ラベル 12pt・不透明度 70%、入力値 100%。文字サイズは 12 / 14 / 16(間を飛ばして役割を分ける)。チェックボックスは入力欄と同じ高さ、規約の文字は 1 段小さく。
- 背景画像が切れる → 左上・右上の色をサンプルしてグラデーションで埋め、境界をぼかす。ヘッダ文字が読めない → 同系色の暗い層(黒 100% を「オーバーレイ」90%)を敷く。

### I. Erik Kennedy の 7 ルール(診断の型)
- 光は空から来る(上が明るく下が暗い。凹みは入力欄、凸はボタンとカード)。白黒から作る。余白を 2 倍にする(行間 2 倍、メニュー項目の上下は文字高の 2 倍、リスト間 25px)。画像の上の文字は暗いオーバーレイ(35% など)・ぼかし・下端のフェード(0〜約 20% の黒)。強弱は「上げる」と「下げる」を組み合わせる(大きさ・色・太さ・大文字・斜体・字間・余白の 7 つ)。ホバーで大きさや太さを変えるとレイアウトが動くので色で変える。良い書体を使う。うまいものを真似る。

### J. Refactoring UI 書籍の抜粋
- ラベルは最後の手段: 意味が自明なら外す(メール、電話、価格)/「在庫: 12」は「残り 12」に溶かす/比べる画面では小さく・薄く/仕様表のように探される場合はラベルのほうを強く。理由: 「ラベル: 値」は全部が同じ強さになり階層が作れない。
- 色パレット: 生成ツールの 5 色では足りない。灰 8〜10 段、主色 5〜10 段、アクセントは必要なら複数。ベースを 500 に置き、暗い端(900)は文字用、明るい端(100)は淡い背景用に決め、中間(700・300 → 800・600・400・200)の順で埋める。「lighten/darken で場当たり的に作らず、固定の段階から選ぶ」。段を増やし続けると色の体系がなくなる。

### K. Linear の UI 刷新(企業の事例)
- 範囲を限る: 見た目の刷新に絞り、ナビの仕組みの変更は後回し(リスクと範囲の拡大を避ける)。ビュー(リスト、ボード等)ごとに全部試す。
- 色: テーマの生成を HSL から LCH へ(明度が知覚的に一様)。テーマの変数を 98 個 → 3 個(ベース・アクセント・コントラスト)。クロムの青の影響を弱めて無彩色寄りに。明るいモードは文字とアイコンを濃く、暗いモードは明るく。
- 見出しだけ Inter Display、他は Inter。約 6 週間・少人数、フィーチャーフラグで並べて比較。段階: ストレステスト → 挙動の定義 → サイドバー刷新 → 非公開ベータ → GA。

### L〜N. ダッシュボードの刷新 3 件
- L Spike.sh: 青いサイドバーが一覧表より目立つ → 彩度を下げる。表の文字が全て中央揃い → 文字は左、数値は右(Material の指針)。ほぼ全ての表が同じに見える → 最重要の「インシデント」表だけ別の強弱に。ボタンとタグが見分けにくい → ステータスのタグに色、操作ボタンはステータスの色に。行の補助操作はホバー時のみ。ステータスタグは本番で 5 回以上調整。
- M OJS: 間隔とサイズの不統一 → 16px のグリッド。焦点がない → 主パネルを白、背景を灰。サイドバーと本文をコントラストで分け、ボタンは最終・主操作、リンクは作業の流れ(モーダルを開く)に使い分け。文字を大きく、Noto Sans(多言語で字形がそろう)。効果の数値は未提示。
- N Data School: 書体・色・サイズ・整列の不統一、期間・通貨・比較(前年比)・傾向(スパークライン)の欠落、全部が同じ重み → 最大値だけに色。詰まった配置 → 余白と灰の区画。16 の修正を列挙しているが、効果の数値は出ていない。

## 4. 専門家の着手順

事例から見える共通の順序。括弧内は根拠。

1. 範囲と残すものを決める(Resolute「構造は変えない」、Transistor「共有テンプレートを壊さない」、Linear「ナビの仕組みは後回し」、Rachel How「ブランドの識別性は残す」)。
2. 目的と利用者のすること・重要度を書く(Learn UI の目標 3 つと重要度の順、How の支払いの手順)。目を細めて、最初に見えるものと重要度を突き合わせる(スクイントテスト)。
3. 全体に効く小さな修正(幅の上限、基本の文字サイズ、灰のパレット、ナビの現在地の示し方)を、他ページへの影響を考えながら先にやる(Transistor)。
4. 構造と整列: 不要な動き・演出を外す(D)、情報を組み分けして位置を決める(A、D)、12 カラムなどで整列、本文を字下げして走査線を作る(F)。
5. 強弱: サイズ → 色 → 太さで階層を作り、補助を下げる。ラベルを外すか薄くする(J、F)。
6. 部品: ボタンの主従、入力欄の高さ・幅・ラベル、タグ・テーブル・状態表示(C、E、L)。
7. 仕上げ: 影・角丸・枠の整理、アイコンの統一、灰へのブランド色相の混入、書体の変更(A、B、F)。書体を最後に直す人が多い(A、B、F)が、Waterworth は早い段階で 1 つにそろえる。どちらも「階層を直す前に書体を整える」点は同じ【推論】。
8. 検査: コントラスト比を実測(B)、暗い/明るい、モバイル、長い文字列など実データの端(D、P)。目標を満たしたか再確認(G)。
9. 詰まったら参考を探す(pages.xyz、Fonts In Use、Dribbble、Mobbin、実在製品。G・B・A・I の Rule 7)。

矛盾・使い分け:
- 色: Erik は白黒から、Steve は先に灰を決めてブランド色を一点に入れる。どちらも「色は最後か、少なく」。
- 右寄せの保存ボタン: Steve 自身が確証なし。「どこでもよいが全体で同じ位置」まで言える【弱】。
- ボタンの大きさ: Rachel How は高さ 44px 以上、Steve は入力・ボタンで 40〜48px。矛盾はなく、タッチ対象なら 44px 以上にすれば両方を満たす【推論】。
