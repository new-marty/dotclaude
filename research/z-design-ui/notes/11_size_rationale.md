# 11 大きさの決め方と理由の書き方(文字・間隔・部品・アイコン・タッチ領域)

調査日: 2026-10-26。03(視覚の基礎)・07(判断規則)の続き。03/07 で読了した値(DADS の本文 16px 以上、Carbon の行高さ、WCAG 2.5.8 の 24px、Apple 44pt など)は繰り返さず、「その値がなぜその値か」と「どう決めるか」を掘った。
表記: 読了=本文を取得して確認。検索のみ=検索結果の要約だけ。【弱】=二次情報・ブログ・ベンダー記事。【推論】=調査者の推論・計算。数値の計算は末尾付近の「計算メモ」に残した。

## 結論(5行)

1. 一次資料で「比率から導いた」と言えるのは Tim Brown の modular scale と Utopia だけ。Tailwind・Material 3・Apple・Carbon の実際の表は、式か手調整で、段ごとの比は 1.06〜1.43 でばらつく。小さい側は刻みを細かく、大きい側は粗くする形で共通する【推論】。
2. 「この大きさにした理由」は 4 種類に分けて書ける: 基準(本文)から出した / 基準からの比で出した / 外部の下限(WCAG・DADS・OS)で止めた / 測った値(Parhi の 9.2mm など)。理由のない値は 4 種のどれにも入らないので、入れない。
3. 大きさは文字サイズ単独で決めず、字間・行高・太さ・アイコン・タッチ領域を一組で決める。小さいほど字間を開き行高を相対的に広く、大きいほど詰める(Apple・Inter・DADS・Tailwind が同じ向き)。日本語は JLREQ の「行間は 0.5〜1 字」から逆算すると DADS の 170% と合う。
4. 間隔は「関係の強さ」で選ぶ(DADS: 近い=関連、遠い=別)。内側の余白 ≤ 外側の余白の規則は、一次資料では明文化を見つけられなかった(取得できたのは Nathan Curtis 系の二次引用のみ)。
5. タッチ領域の根拠は、物理量(Parhi 9.2/9.6mm、Google 48dp≈9mm、Microsoft 9mm/7mm)と OS の最小値(Apple 44pt、visionOS 60pt)と法規の下限(WCAG 24px)で別々。混ぜず、「最小」と「推奨」を分けて書く。

## 1. 型スケール: 比率か、手調整か

### 事実
- **Tim Brown(A List Apart)**: modular scale は「開始値と比を決め、掛けて大きく、割って小さくする数列」。本文から始める(書体を先に選び、その書体が一番きれいに見える大きさを基準にする。例は Minion 18px)。比は意味で選ぶ(例は黄金比 1:1.618。記事の主題が活版の伝統だから)。もう一つの「大事な数」(例: 見出し 190px)を第二の起点にして、2 本の数列を重ねることもできる。数列に載らない値は、足し引きで作って「計算メモ」をコメントに残す(例: 3.56+16=19.56)。15px のように数列にない即興値も使っており、「数列は規則でなく示唆。数学は経験ある目の代わりにならない」と本人が書く。読了。https://alistapart.com/article/more-meaningful-typography/
- **Utopia**: 画面幅 320px で 1.2、1500px で 1.333 の 2 本の比を決め、間はブラウザが補間する。理由は「スマホは横幅が狭く文字の差を控えめにしたい、大画面は差を大きくできる」。ブレークポイントごとの手設定は恣意的になるのを避けるため。読了。https://utopia.fyi/blog/designing-with-fluid-type-scales/ 。計算機の既定値は 360px/18px/1.2 → 1240px/20px/1.25、上 5 段・下 2 段。生成式は `clamp(最小rem, rem+vw, 最大rem)`。読了(URL パラメータとフォームからの読み取り)。https://utopia.fyi/type/calculator/
- **Carbon**: 式で作る。12px から始め、4 段ごとに増分が 2→4→6…px と増える(Xn = Xn-1 + (INT[(n−2)/4]+1)×2)。結果は 12/14/16/18/20/24/28/32/36/42/48/54/60/68/76/84/92px。読了。https://carbondesignsystem.com/elements/typography/overview/ 。productive は基準 14px・見出し固定、expressive は基準 16px・見出しがブレークポイントで変わる(fluid)。理由は「製品画面は密でコンテナ内に収める必要があり、固定が必須。Web ページは幅が大きく変わるので流動」。見出しは本文とペア(heading-01 は body-01、heading-02 は body-02)。読了。https://carbondesignsystem.com/elements/typography/type-sets/
- **Tailwind**: 12/14/16/18/20/24/30/36/48/60/72/96/128px。行高は `text-sm` 20px(1.43)から `text-4xl` 40px(1.11)まで段ごとに別、`text-5xl` 以上は 1。読了。https://tailwindcss.com/docs/font-size
- **Material 3**(material-web のトークン): 11/12/14/16/22/24/28/32/36/45/57px(label-small 0.6875rem 〜 display-large 3.5625rem)。title-large が 22px で、body-large 16px の次にいきなり跳ぶ。読了。https://raw.githubusercontent.com/material-components/material-web/main/tokens/versions/v0_192/_md-sys-typescale.scss
- **Apple Dynamic Type(iOS、標準サイズ)**: 11/12/13/15/16/17/20/22/28/34pt。本文 17pt。読了。https://developer.apple.com/design/human-interface-guidelines/typography(JSON 版 https://developer.apple.com/tutorials/data/design/human-interface-guidelines/typography.json)
- **Fluent 2(web)**: 10/12/14/16/20/24/28/32/40/68px。読了。https://fluent2.microsoft.design/typography
- **Refactoring UI が手調整を勧めるか**: 原典は取れず、二次要約が割れている(「比は端数になり小さい UI には粗い、手で選べ」と「1.25 比で 12/14/16/20/24/30/36」の両方がある)。検索のみ【弱】。確定しない。

### 読み取れること【推論】
- 手調整の表を段ごとの比にすると(計算メモ参照): Apple 本文付近は 1.06〜1.18、見出しは 1.27〜1.33。Material は 1.09〜1.38。Tailwind は 1.11〜1.33。Carbon の見出し(14→20→28→32→42→54)は 1.14〜1.43。どれも一定の比ではなく、「本文付近は 1〜2px 刻み(密に使い分けたい)、見出し側は大きく跳ぶ(階層を見せたい)」という形。
- Brown 自身が「数列は示唆」と言うので、ratio 派と手調整派は対立せず、「比で候補を出し、画面で丸める」が一次資料の立場に最も近い。
- 多くの製品 UI が 1.125〜1.25 の範囲に収まる理由は、一次資料では説明が見つからなかった。「1.2 や 1.25 は段差が明確」「Material 3 の 1.125 は多画面に対して釣り合う」という記述は二次のまとめにある(検索のみ【弱】。https://www.30secondsofcode.org/css/s/typographic-scale-basics ほか)。

### 段数はいくつか
- 一次資料の実数: Carbon productive の本文 + 見出し系は 14 / 16 / 20 / 28 / 32 / 42 / 54 の 7 見出し + 本文・ラベル数種。M3 は 15 トークン、Apple は 11 スタイル、Fluent 2 は 16 スタイル(うち太さ違いを除くと 10 サイズ)。DADS Standard は 16〜45px の 11 サイズ。
- NN/g(読了): 大きさの階層は小・中・大の 3 段まで、最大の要素は 2 つまで、web の目安は本文 14〜16px・小見出し 18〜22px・見出し最大 32px。https://www.nngroup.com/articles/visual-hierarchy-ux-definition/ (数値の出典は記事内で示されず、経験則としての記述。【弱】寄り)
- 【推論】段数は「画面の中で同時に見える階層の数」で決まる。一つの画面で同時に使うのは 3〜4 サイズに収まることが多く、残りは別の文脈(表、法的表記、マーケ)の分。
- **段差の下限**: 「1 段上は前より 50% 以上大きく、近接させるなら 35% 以上」という Vevo のブランド規定が検索に出た(検索のみ【弱】)。製品 UI の標準(Tailwind 本文付近の 14→16→18 は 12〜14%)とは真逆の慣習で、サイズ差だけに頼らず太さ・色・間隔を併用する前提の差だと読める【推論】。一次の実験データは見つからなかった。

## 2. 強調: 大きさ・太さ・色

- **一つずつ使う**: Butterick は太字とイタリックを併用しない、強調は短く、全部を強調すれば何も強調されない。太字(bold)より半太字(semibold)は読みやすいが対比は弱く、重い太さ(black など)は大きい字向け。大きさは強調手段として扱っていない。読了。https://practicaltypography.com/bold-or-italic.html
- **NN/g**: 階層は値(明暗)と彩度の対比から生まれる。コントラストの変化は最大 3 種まで(「全部が対比なら何も目立たない」)。太字は軽い・標準の文章に対して目立つ。見出しと中身は間隔を詰めて関係を示す。スクイント(ぼかし)テストで意図しない焦点を見つける(Spotify の例で 5px・10px のぼかしで階層が残り、20px で想定外の焦点が出た)。読了。https://www.nngroup.com/articles/visual-hierarchy-ux-definition/
- **Apple**: 軽い太さ(Ultralight/Thin/Light)は小さい字で見えにくいので避ける。Regular/Medium/Semibold/Bold を使う。薄い太さのカスタムフォントは推奨サイズより大きくする。強調の既定は Semibold(Body の emphasized は Semibold、Large Title・Title 1・2 は Bold)。読了(typography JSON)。
- **DADS**: 太さは N(400)と B(700)の 2 水準だけを定義。読了。https://design.digital.go.jp/dads/foundations/typography/ 。Carbon は heading-01 のみ 600、heading-03〜05 は 400(大きいが Regular)、heading-06/07 と fluid の大見出しは Light 300(54px)。「大きくなるほど太さを軽くする」。読了。type-sets。
- **Refactoring UI の「大きさ・太さ・色のうち 1〜2 本」**: 二次要約のみ。「二次的な情報は小さくするより色を薄くする方が読みやすさを損なわない」という趣旨が検索に出る(検索のみ【弱】)。
- 【推論】強調の道具の使い分け: 同じ階層内の比較は太さ、階層をまたぐ比較は大きさ、状態・優先度は色。1 要素に 3 つ重ねない。

## 3. 小さいほど開く・大きいほど詰める(字間・行高・光学サイズ)

### 字間(tracking)
- **Inter の dynamic metrics**: `tracking = a + b·e^(c·z)`(em 単位、z=光学サイズ)。a=−0.0223、b=0.185、c=−0.1745。16px は −0.011em(npm の inter-metrics の例と一致)。式から計算すると 11px は +0.005em、12px はほぼ 0、14px は −0.006em、32px は −0.022em【推論(計算)】。読了。https://d.rsms.me/inter-website/v3/dynmetrics/ 。行高の式はページ内容から取れなかった。公式の別ページ(rsms.me/inter/dynamic-metrics)は 404。
- **Apple SF Pro の tracking 表(iOS)**: 6pt +41、10pt +12、12pt 0、14pt −11、17pt −26(−0.43pt)、20pt −23、24pt +3、28pt +14、34pt +12、48pt +8、64pt +4、80pt 以上 0(単位は 1/1000 em)。17pt 付近で最も詰め、24pt 以降は Display 書体に切り替わるため正に戻って 80pt で 0 に収束する【推論: 光学サイズの切替】。読了。typography JSON。Apple は「動的な光学サイズでは Text/Display を使い分ける必要がない」と書く(同)。
- **Material 3**: body-large +0.5px(0.03125rem)、body-medium +0.25px、body-small +0.4px、label-small +0.5px、display-large −0.25px、見出し系 0。小さい字ほど開く方向。読了(トークン)。
- **Carbon**: heading-01(14px)は +0.16px、他の見出しは 0、fluid-display-03/04(60・92px)は −0.64px。本文・ラベルの値は今回読んでいない。読了(見出しのみ)。
- **DADS(日本語)**: 26px 以下は字間 2%、28〜36px は 1%、45px は 0、Display(48〜64px)・Dense・Mono は 0、Oneline は 2%。読了。https://design.digital.go.jp/dads/foundations/typography/ 。向きは Inter と同じ(小さいほど開き、大きいほど 0 に近づく)。ただし DADS が 2% を選んだ理由は記述がない。
- **JLREQ**: 本文はベタ組みが既定で最も読みやすい。アキ組み・詰め組みは見出し・キャプション用。読了。https://www.w3.org/TR/jlreq/ §2.1.3。→ DADS の本文 2% は JLREQ のベタ組みとずれる。UI の画面文字は印刷より小さくて粗いので開けるという説明は書かれていない【推論】。
- 【推論】欧文の tracking は「サイズが小さいと文字間の相対的な空きが足りなくなる」ので開き、大きいと空きが多すぎるので詰める、という光学上の補正。表記の大小に関わらず単位は em(サイズに比例)で持つ。

### 光学サイズ
- Apple は連続可変の光学サイズ(Text と Display を一つに統合)をシステムフォントで提供。Inter は text〜display の光学サイズ軸を持つ。具体的な切替しきい値は取得できなかった(Inter は読了ページに数値なし)。

### 行高
- **サイズが大きいほど相対行高は小さい**: Tailwind(16px で 1.5、24px で 1.33、36px で 1.11、48px 以上で 1.0)、DADS(16px/170%、18px/160%、20〜32px/150%、36〜45px/140%、Display/140%)。DADS は理由を明記: 「見出しなど文字が大きくなるものは、本文より行間を狭めたほうが可読性が維持される」。読了。
- Apple: 17/22(1.29)、34/41(1.21)、11/13(1.18)。読了。
- **Butterick**: 点サイズの 120〜145%(例 135%)。字体で見かけの大きさが違うので、小さく見える書体は少なめ、大きく見える書体は多め。読了。https://practicaltypography.com/line-spacing.html 。本文の web 推奨は 15〜25px(画面は印刷より離れて読み、ピクセル数が少ないので大きめ)。見出しを本文の 2 倍にするのは過大とする。読了。https://practicaltypography.com/point-size.html
- **日本語(JLREQ)**: 行間(行送りでなくすきま)は「0.5 字〜1 字」の間。行長が短ければ 0.5 字、35 字を超えるなら 1 字に近く。1 字を超えると逆に読みにくくなる。西洋組版の標準行間は 1/3 字。行長の最大は横組み 40 字、縦組み 52 字。読了。https://www.w3.org/TR/jlreq/ §2.4。行間の「字」は字面の大きさ基準なので、行送り(行高)は 1.5〜2.0 倍になる【推論(計算)】。DADS の本文 170% は行間 0.7 字、見出し 140% は行間 0.4 字に当たり、本文は JLREQ の範囲に入る。DADS の Dense(120〜130%、行間 0.2〜0.3 字)と見出し 140% は JLREQ の下限 0.5 字を下回る。JLREQ は印刷の本文を対象とし、「画面や web の文字サイズは扱わない」と範囲外を明記している(§1.3)。
- 紙の本文サイズは 9pt が一般、専門書を除く最小は 8pt(§2.4)。画面の 14〜16px との直接比較は、閲覧距離が違うため意味が薄い【推論】。
- SmartHR(07 で読了): 基準 16px、段落 1.5、見出し 1.25、ラベル(ボタン等)1。

## 4. 数字の大きさ(ヒーロー数字)

- 一次資料で「ヒーロー数字は本文の何倍」を定めたものは見つからなかった。検索に出る KPI ダッシュボード記事は「36〜72pt、主数字はラベルの 2〜3 倍」を経験則として挙げる(検索のみ【弱】、ベンダー・ブログ。https://vizmasters.substack.com/p/big-ass-numbers-bans-why-they-belong ほか)。「一番大きい要素は 2 つまで」(NN/g 読了、上)と整合する。
- 【推論】ヒーロー数字を作るときは、別系統で決めずに型スケールの最上段近くから選び、ラベルを本文の最小サイズ(日本語は 14px)に置いて比を結果として書く。比そのものを根拠にしない。
- Carbon は expressive の display(54〜92px、Light 300、字間 −0.64px)を数字に限らず大きい表示用に用意している。大きい数字は Light(300)、字間は詰める(Carbon fluid-display-03/04)。読了。type-sets。
- 値が更新される数字は tabular(07 で読了済み)。大きいほど桁揺れが目立つので、大きい数字ほど tabular を優先する【推論】。

## 5. 間隔: 4/8 の倍数と関係の強さ

### 事実
- **DADS**: 基準 8px、段数は 3〜5 段。トークンは任意。「近い要素は関連、遠い要素は別」。例のスケール: 8px(1×)、24px(3×)、64px(8×)。見出しは階層が上がるほど周囲の余白も大きく、余白は見出しの文字サイズに合わせる。キャプションを画像に近づけないと、画像と本文のどちらに属すのか曖昧になる。読了。https://design.digital.go.jp/dads/foundations/spacing/
- **Carbon**: 2・4・8 の倍数(`spacing-01`=2px、02=4、03=8、04=12、05=16、06=24、07=32、08=40、09=48、10=64、11=80、12=96、13=160)。「2x Grid と型スケールに合う」。スケール外は避け、ブレークポイントで 1 段以上跳んでよい。内側と外側の関係を定める規則はこのページにない。読了。https://carbondesignsystem.com/elements/spacing/overview/
- **SmartHR**: 基準 16px。0 / 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64px。選び方の規則は書かれていない。旧セマンティック名(XS〜XXL)は廃止。読了。https://smarthr.design/products/design-tokens/spacing/
- **Material**: 8dp グリッド、アイコンや文字は 4dp(03 で検索のみ)。
- **なぜ 4/8 の倍数か**: 画面密度(1x/1.5x/2x/3x)で割り切れて端数ピクセルを避ける、という理由が通説。一次資料では DADS・Carbon・SmartHR のいずれも理由を書いていない(「基準は 8px」と述べるのみ)。Google の a11y ページは「48dp は画面によらず約 9mm」と書き、dp が物理量に対応する前提を示す(読了、下記)。【推論】4/8 は物理的な必然でなく、割り切れる数と「選択肢を減らす」ための約束。Tailwind が 4px 刻み、SmartHR が 20px を持つなど、実装は 8 の倍数に固執していない。
- **内側 ≤ 外側の規則**: 取得を試みた Nathan Curtis の記事(Space in Design Systems)は 403 で読めなかった。DADS の近接規則(関連=近い)から導くなら: 部品の内側余白(padding)よりも、隣の部品との外側余白(gap)を同じか大きくしないと、境界が曖昧になる【推論】。DADS の例(8px と 24px、64px)は 3 倍・8 倍の比。比そのものに根拠は書かれていない。
- **部品内のパディング**: DADS は「padding の具体値は規定しない」と明記(読了)。Carbon のボタンは左 16px(`spacing-05`)、アイコン間 32px、右 64px(アイコンなし)、境界から 16px 以内に何も置かない、複数のアイコン付きボタンが並ぶ場合を考慮した最小値(読了、https://carbondesignsystem.com/components/button/style/ )。

## 6. 部品の高さ(コントロール高さ)と密度

- **Carbon ボタン**: 24 / 32 / 40 / 48 / 64 / 80px。ラベル 14px(`body-compact-01`)、expressive は 16px。アイコン 16px(expressive は 20px)。隣り合うサイズの混在は不可。読了。https://carbondesignsystem.com/components/button/style/ 。32px の高さは 14px×1.43 の行高 20px + 上下 6px と読めるが、Carbon はその計算を書いていない【推論】。
- **Carbon データテーブル**: 24/32/40/48/64(07 で読了)。
- **Material の密度**: 密度ステップ 1 つで部品の高さが 4dp 減る。パディングは変えない(寸法だけ変える)。密度を上げると自動のタッチ領域が無効になる(MDC Web の記述)。MDC Web の標準ボタン高さは 36px。検索のみ【弱】。https://m2.material.io/blog/material-density-web 、https://cdn.jsdelivr.net/npm/@material/density@14.0.0/README.md 。Material 3 の公式の高さ(40dp ボタンなど)は、m3.material.io が JS 描画で本文を取れず未確認。
- **Fluent(UWP)**: 標準は 40×40 epx のターゲットに揃え、コンパクトは 32×32 epx。検索のみ【弱】。https://learn.microsoft.com/pl-pl/windows/apps/design/input/guidelines-for-targeting
- **Apple visionOS ボタン**: Mini 28 / Small 32 / Regular 44 / Large 52 / XL 64pt。クリック領域は 60×60pt、ボタン中心間は 60pt 以上。読了。https://developer.apple.com/tutorials/data/design/human-interface-guidelines/buttons.json
- 【推論】高さの根拠は「行高 + 上下パディング(4 の倍数)」で組み立てられる。例: 14px 本文の行高 20 + 上下 10 = 40、行高 20 + 上下 6 = 32、16px 本文の行高 24 + 上下 12 = 48。数値をトークンの倍数に載せ、タッチ領域の最小値(次節)は見た目の高さとは別に当たり判定で満たす。

## 7. アイコン

- **Carbon**: アイコンは 16 / 20 / 24 / 32px。16px と 20px は IBM Plex の 14px・16px と釣り合うよう最適化。アイコンと文字の比は変えない。操作できるアイコンは 44px 以上のターゲット(例: 22px のアイコンを 48px のターゲットの中央に)。読了。https://carbondesignsystem.com/elements/icons/usage/
- **行高に合わせる**: 検索結果の要約では、Alaska Air の Auro は「アイコンを文字の行高に合わせる」、Cengage の react-magma は「20px のアイコンは 14px・行高 20px の文字向け」、One Line は「20px のアイコンは 14/16px の文字、16px のアイコンは 12px の文字」と述べる。検索のみ【弱】。https://auro.alaskaair.com/icons/guidelines 、https://react-magma.cengage.com/version/3.0.0/design-intro/icons/ 、https://design-system-beta.one-line.com/foundations/icons/usage
- **線の太さ**: Lucide は線幅 2px(24px グリッド)を既定とし、小さいサイズでは太く、大きいサイズでは細くする、という趣旨が検索に出た(例: ≤16px で 2.25px、≥32px で 1.5px)。検索のみ【弱】で数値は未確認(Lucide の公式ガイドの URL は 404、原典を読めていない)。Cloudscape も「サイズに応じて線幅を調整」。https://cloudscape.design/foundation/visual-foundation/iconography/ 。
- 【推論】文字とアイコンの「重さ」を揃える考え方: アイコンの線幅 ≈ 文字の縦画の太さ(Regular の縦画は字高の約 1/10)。16px のアイコンの 1.5px の線は 14〜16px の Regular の縦画に近い。実測の裏づけは取れていない。

## 8. タッチ領域と測定値

- **Parhi, Karlson, Bederson(MobileHCI 2006)**: 片手の親指での操作。単発タスクは 9.2mm、連続タスクは 9.6mm 四方で十分とする。5 サイズを比較(3.8 / 5.8 / 7.7 / 9.6 / 11.5mm、連続タスクは 5.8〜13.4mm)。9.6mm と 11.5mm の間で誤差率に有意差はなく、速度は 11.5mm で上がる。被験者の親指の長さ 99〜125mm(平均 115mm)。実際のタップ位置の分布は目標の中心から偏る。著者は、ボタンなど標準部品の寸法が 2.64mm(ラジオボタン)〜4.8mm と小さいと指摘。読了(論文 PDF を pdftotext にかけて抜粋を確認)。http://www.cs.umd.edu/hcil/trs/2006-11/2006-11.pdf 、書誌 https://hcil.umd.edu/?p=2840 。被験者数と端末の画面サイズは今回の抜粋では確認していない。
- **WCAG 2.5.5 AAA(44×44 CSS px)**: 理由は「手の震え・器用さの低下、指は画面を隠す、タッチは粗い入力、頻繁に使う・元に戻せない・端にある・連続操作の部品では特に大きく」。44 を選んだ理由は書かれていない。CSS px の視角で 44px は約 0.94°【推論(計算)】。読了。https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html
- **WCAG 2.5.8 AA(24×24 CSS px)**: 24 を選んだ理由は書かれていない。間隔の例外: 24px の円が他のターゲットと交差しなければ小さくてもよい。理由は「タッチシステムは最も近い部品を探す推測を使うので、十分な間隔は大きなターゲットと同じように機能する」。MIT のフィンガーチップ論文と Parhi が参考リンクに挙がるだけで、数値は書かれない。読了。https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html
- **Google(Android)**: 48×48dp で、画面サイズによらず約 9mm。タッチ画面の対象は 7〜10mm が推奨。ターゲット同士は 8dp 以上離す。見た目 24dp のアイコンの周囲にパディングを足して 48dp にする。理由は「確実な操作と情報密度の釣り合い」。読了。https://support.google.com/accessibility/android/answer/7101858
- **Apple**: ボタンのクリック領域は 44×44pt 以上、visionOS は 60×60pt。44 の根拠は書かれていない。読了(buttons JSON)。
- **Microsoft(Windows Phone)**: 9mm が理想、7mm が最小、行動間の間隔 2mm という引用が検索に出る(7・9mm は MS の資料、2mm は第三者ブログ)。検索のみ【弱】。https://learn.microsoft.com/zh-cn/archive/blogs/wpukcoe/designing-touch-targets 、https://blogs.windows.com/windowsdeveloper/2010/12/07/4-of-10-make-sure-your-finger-can-hit-the-target-and-text-is-legible/ 。指先の寸法(MIT Touch Lab の指腹 10〜14mm、指先 8〜10mm)は二次引用のみで、元の Dandekar ら(2003)の論文は寸法を確認できなかった。検索のみ【弱】。
- **物理量への換算**【推論(計算)】: 24 CSS px = 96dpi 基準で約 6.4mm。iPhone の 1pt は初期機種の 163ppi で約 0.156mm なので 44pt≈6.9mm。ここは機種で変わるので概算。Google の 48dp≈9mm は dp の定義(160dpi 基準)からの値。つまり Apple 44pt と WCAG 24px は物理的に 7mm 前後以下で、Parhi の 9.2mm、Google の 9mm より小さい。「最小」と「推奨」を別の欄にする根拠になる。
- 【推論】見た目の大きさとタッチ領域は別物。アイコン 24px・見た目 32px のボタンでも、当たり判定は 44〜48px に広げられる(Carbon の例: 22px を 48px の中央、Google の例: 24dp を 48dp に)。隣接する当たり判定が重ならないよう、間隔は 8dp 以上(Google)。

## 9. 閲覧距離・デバイス

- **Microsoft(Xbox / TV、10 フィート)**: 画面から約 10 フィート(約 3m)に座る前提。Xbox は 1080p 固定で、XAML は 200%、HTML は 150% に拡大。本文・読むもの 15 epx 以上、補足 12 epx 以上、操作部品の高さ 32 epx 以上(200% で 64px 相当)。端から 5% は本質的な UI を置かない(上下 27 epx、左右 48 epx)。情報量は PC でなくスマホ並みに。端から端まで 6 クリック以内。読了。https://learn.microsoft.com/en-us/windows/apps/design/devices/designing-for-tv (アーカイブ文書、ROBOTS: NOINDEX)
- Apple の最小サイズ(07 で読了): iOS 11pt、macOS 10pt、tvOS 23pt(既定 29pt)、visionOS 12pt。今回 typography JSON で再確認した値は tvOS 29/23pt。読了。
- Fire TV の「テキストは 28px 以上(1080p)」「22px 未満は読めない」は検索に出た第三者ブログの引用で、Amazon の原典を読めていない。検索のみ【弱】。
- **壁掛けディスプレイ・ダッシュボード**: 一次資料は見つからなかった。【推論】視角で考える。読む距離が 3 倍になれば、同じ視角を保つにはおよそ 3 倍の大きさが要る(Butterick の「画面は印刷より遠くから読む」と同じ理屈。https://practicaltypography.com/point-size.html 読了)。具体の係数は実測が必要。
- 【推論】PC のマウス操作用の部品は 24〜32px で足りるが、同じ UI をタッチ(44〜48px)と TV(32 epx×2)に使うなら、部品の高さは 1 つの値でなく環境ごとに切り替えるトークンにする。

## 10. レスポンシブ・流動的な文字(clamp / Utopia)

- 理由: 2 本の型スケール(小画面 1.2、大画面 1.333)を決めて補間する(Utopia)。画面幅ごとの手設定より恣意が少ない。読了(上記)。
- **アクセシビリティの落とし穴**: 文字サイズを vw だけで決めると、ズームしても大きくならず WCAG 1.4.4(200% まで拡大)を満たさないことがある(Adrian Roselli の指摘を Smashing が引用)。対策は rem と vw を併用すること。web.dev の助言として、max()/clamp() で上限をかけると 1.4.4 の失敗になりうるのでズームで試す。検索のみ【弱】(原典 Roselli、web.dev は未読)。https://smashingmagazine.com/2023/11/addressing-accessibility-concerns-fluid-type 。
- 「最大が最小の 2.5 倍まで」という通説は今回の検索では裏づけが取れなかった。
- Carbon は本文を固定、見出しだけを流動にする(読了)。【推論】本文の可読性は閲覧環境の標準サイズを維持し、流動にする価値があるのは見出しや表示用の大きい文字。

## 大きさの決め方の手順(エージェント向け)

1. **環境を決める**: 入力(マウス / タッチ / リモコン)、閲覧距離(手元 / 机 / 壁・TV)、言語(日本語を含むか)、密度(毎日使う業務 / 読み物)。出典: 07 の密度規則、本ノート §8・§9。
2. **基準を 1 つ決める**: 本文サイズ。日本語は 16px(Standard)か 14px(Dense、業務画面。DADS)、欧文の業務画面は 14px(Carbon productive)。ここが他の全部の起点になり、理由は「最小値の規定(DADS・WCAG)と画面の密度」と書く。
3. **型スケールを置く**: 比(1.125〜1.333)から候補を出し、本文付近は 1〜2px 刻み、見出し側は大きい跳びに丸める。使う段は同時に見える階層の数に絞る(3〜4 段、最大の要素は 2 つまで)。既存プロジェクトにあるならそれを使う。
4. **字間・行高・太さを段ごとに決める**: 小さいほど字間を開き(em で持つ)、大きいほど詰める。行高は小さいほど広く(日本語本文 1.7、見出し 1.4〜1.5 → DADS)、大きいほど狭く。太さは 400/600 の 2〜3 水準、大きい表示は 300 も可(Carbon)。強調は太さ・色・大きさのうち 1〜2 本。
5. **間隔の基準単位と段を決める**: 4 または 8 の倍数から 5〜9 段(DADS は 3〜5 段、Carbon は 13 段)。関連が強い要素 = 小さい段、弱い = 大きい段。内側余白 ≤ 外側余白の規則を自分に課す【推論】。
6. **部品の高さを組み立てる**: 高さ = 行高 + 上下パディング(間隔の段から)。密度モードは高さを 4〜8px 単位で増減し、パディングは変えない(Material)か、行高を変える(DADS)。
7. **アイコンの大きさを決める**: 隣の文字の行高に合わせる(16px/20px/24px)。線の太さは文字の太さと揃える。
8. **タッチ領域を別に満たす**: 見た目と別に当たり判定を 44〜48px 以上に広げる。隣接は 8px 以上空ける。最小 24px は WCAG の下限としてだけ使う。
9. **理由を書く**: 各値に、基準・比・下限・測定値の 4 種類のどれかを 1 行で書く。どれも言えない値は表にある値に丸める。
10. **検証**: 複数幅(320px を含む)、200% ズーム、スクイントテスト(ぼかして階層が残るか)、日本語の長文・短文。

## 理由の書き方の例

形: 「[値]。[何から導いたか]。[どの下限・実測に当たるか]。[外すとどうなるか]」。

- 「本文 16px。DADS の本文・UI の基準値 16px 以上(14px 未満は原則不可)に合わせた。業務画面の密な表のみ 14px(DADS Dense)。」
- 「見出し 1 段目 24px / 行高 150% / 字間 2%。本文 16px から約 1.5 倍(1.25 の 2 段上 ≒ 1.56 に丸め)。24px 以下の字間は DADS が 2%。行高は大きいほど狭める(DADS)。」
- 「ヒーロー数字 48px、Light。画面内で最大の要素は 1 つに絞る(NN/g)。ラベルは 14px で、比 3.4 倍は結果であり根拠ではない。tabular-nums で桁揺れを防ぐ。」
- 「段間余白 24px、項目間 8px。DADS の例の 3×と 1×(基準 8px)。キャプションは画像に 8px で寄せ、本文との間に 24px を置いて、どちらに属すかを間隔で示す。」
- 「ボタン高さ 40px。14px 本文の行高 20px + 上下 10px。見た目は 40px、当たり判定は 48px に広げる(Google 48dp≈9mm、Parhi 9.2mm)。隣接ボタンの間隔は 8px 以上。」
- 「アイコン 16px。隣の 14px 本文(行高 20px)と釣り合う大きさ(Carbon は 16/20px を 14/16px の文字に合わせて最適化)。タッチ領域は 44px まで余白で広げる。」
- 悪い例: 「余白を 20px にした(見た目のバランスのため)」。→ 「20px はスケールの 16 と 24 の間。どちらの隣接関係(同じグループ / 別グループ)に当たるかで 16 か 24 に直す」。
- Tim Brown 式の「計算メモ」: 数列外の値を足し引きで作るときは、`/* 21.18 = 27.72 − 6.55 */` のように計算をコメントに残す。手調整した値も同様に「どの値から何px動かしたか」を残す。
