# 理由のある UI を作るための知識

色・配置・大きさ・動き・文言のすべてに「なぜそうしたか」を答えられる UI を作るために、調べた知識を手順の形にまとめた。個々の原則を引くための一覧は [principles.md](principles.md) にある。画面やフロー、状態をどう決めるか(UX)は [z-design-ux](../../skills/z-design-ux/SKILL.md) の範囲なので扱わず、決まった画面をどう描くかから始める。出典と細かい数値は `notes/` の各ノートにあり、各節の末尾にノート番号を書いた。

## 結論

デザインの「魂」とは、画面のどの選択を指しても「なぜ」の答えがあり、その答えが**題材・利用者・制約**のどれかに行き着くことだ。逆に、反射で置いた既定値、実データを知らないまま作った画面、全部が同じ重さの画面には作者がいない。対策は避けるべき見た目の禁止リストではない。決める順番と、各決定の根拠の書き方を固定することだ(12、13)。

決める順番は「画面の仕事 → 内容 → 内容の端 → 配置 → 大きさ → 色 → 面と線 → 動き → 文言 → 見せ場」で、どの段も上の段の答えから導く。各段の値には、慣習・課題・頻度・基準(下限や測定値)のどれから出したかを一行で添える。「見やすい」「モダン」「バランスが良い」は理由として書かない(10、11、12)。

エージェントとして作るときは、作る前に方向を3〜4案、理由つきで出して選び、決定と根拠を作る前に書く。作った後は、意図を知らない別の目にスクリーンショットだけで確かめさせる。理由を作った後に書くと、後付けの言い訳になる(13)。

## 1. 魂の正体と、抜ける原因

意図は一足飛びに画面へ降りない。主題(一文)、原則(判断の問い)、個々の決定の三段で降りる。主題は形容詞を使わず、状況で書く。「誰が、いつどこで、何をしようとして、何が一番大事か、そのために何を犠牲にするか」。原則は SmartHR のように「〜していないか」という問いの形にすると、迷ったときに取捨選択に使える。freee は一般原則(シンプルに、利用者中心に)を書かず、製品ごとに設計者へ「なぜこの設計か」を聞いて原則にしている(12)。

魂が抜ける原因は三つに絞れる。一つ目は、内面化したパターンを反射で置くこと(Apple は WWDC18 でこれを意図的な設計の最大の敵と呼んだ)。二つ目は、実在の内容・単位・制約を知らずに作ること。三つ目は、原則が言葉になっていないこと。最後の確認として、ロゴと固有名を隠して他の製品に差し替えても成り立つ画面は、題材から導けていない(12)。

Marty が共有した動画も同じことを言っている。宿の予約なら利用者の意図は「探す」なので、検索欄が出発点になる。背景に画像を敷いた見出しは見た目を変えるが、機能は何も増やさない。意図が広がったときだけ機能を広げる(15)。

## 2. 決める順番と、各段の決め方

### 2.1 画面の仕事と内容

画面の仕事を、利用者の課題として一文で書く。二文要るなら画面を分けるか、副次を下の層に落とす。次に内容を洗い出し、「これが無いと仕事が終わらないか」で第1層・第2層・第3層に分ける。層は位置を決める前に決める(10)。Lumen では、「何を見せるか」を決める前に形(リングか棒か)を選んだ画面が毎回指摘された。数字だけの羅列、同じ情報の二重表示、行き先のないボタンも同じだ(08)。

### 2.2 内容の端

実データの最悪の形を先に考える。長い名前は切り詰める。明るい画像の上のアイコンには円を敷いてコントラストを保証する。空、読み込み中、エラー、権限なしの状態も描く(15、04)。デモ用の整ったデータで作った画面は、実データで崩れる。

### 2.3 配置

置き場所の根拠は課題・頻度・慣習から立て、視線の癖には頼らない。F パターンは NN/g 自身が「避けたい失敗型」として扱っていて、配置の根拠にはならない。Z パターンとグーテンベルク図には実証が乏しい。使える実測は二つで、注視の 80% が左半分に集まり、閲覧時間の約 57% がファーストビューに集まる(NN/g、120人・13万注視)。なので Web では主役を左上に置く。モバイルでは主要な内容と操作を中央に、副次を上下の端に置く。「親指が届くから下」は、Hoober 本人が到達ゾーンの図を撤回しているので理由にしない。下にタブバーを置く理由は iOS の慣習と書く(10)。

ボタンの並びに実験の決着はないので、その OS の慣習に従う。Apple は肯定が右、Windows は肯定が左だ。破壊的な操作は既定にせず、主操作から離し、取り消しを出す点は各社で一致する。ナビは最上位が5つ以下で頻繁に切り替えるなら常に見せる。隠したナビは使われにくい(NN/g の179人の実験)(10)。

まとまりは近さで作り、組の内側の余白を組の外側より小さくする。Mizko は 4 の倍数、Malewicz はカードの中を 12〜16px、カードの間や外周を 24〜32px にしている(17)。区切りの手段は「余白 → 薄い線 → 背景や枠」の順に強くなり、必要になるまで強い手段を使わない(07)。ただし Lumen では、カードの背景がない平らな配置が「背景色がないと見にくい」と言われた。線が濃すぎても指摘された(08)。

### 2.4 大きさ

基準を一つ決め、そこからすべてを出す。基準は本文の大きさで、日本語の読み物は 16px、日本語の業務画面は 14px(デジタル庁デザインシステムの Dense)、欧文の業務画面は 14px(Carbon)。デジタル庁デザインシステムは日本語の 14px 未満を原則禁止にしている。見出しは 1.125〜1.333 の比から候補を出し、本文の近くは 1〜2px 刻み、見出し側は大きく跳ばす。一つの画面で同時に使う大きさは3〜4段、最大の要素は2つまでにする(11、17)。見出しは字間を -2〜-3%、行間を 110〜120% に詰める(16)。

大きさは文字だけで決めず、字間・行高・太さ・アイコン・タッチ領域を一組で決める。小さい字ほど字間を開いて行高を広く、大きい字ほど詰めて狭くする。この向きは Apple、Inter、デジタル庁で共通する。日本語の行高は本文 1.7、見出し 1.4〜1.5 で、日本語組版の要件(JLREQ)の「行間は 0.5〜1 字」から計算しても本文 170% は範囲内に入る。間隔は 4 か 8 の倍数から選び、関係が強いものほど小さい段を使う。タッチ領域は見た目と別に 44〜48px を確保する。WCAG の 24px は下限としてだけ使う(11)。

各値の理由は四種類のどれかで書く。基準から出した、基準からの比で出した、外部の下限(WCAG・デジタル庁・OS)で止めた、測った値(指先の実験の 9.2mm など)を使った、のどれかだ。どれにも入らない値は、表にある値に丸める(11)。

### 2.5 色

色は意味を運ぶ道具で、飾りではない。まず画面の面・線・文字をすべて中立の階段で作り、階層ができてから色を足す。主操作の色は一つに固定し、「この色は押せる」と学習させる。主ボタンは1画面に1つにする。純粋な黒と白は避け、グレーには一つの色相を混ぜる(18)。状態色(成功・警告・危険・情報)は、必ずアイコンや文言と組にする。色だけで意味を運ぶと、男性の約12人に1人には伝わらない。データの色は変数の種類で選び、強調したい1〜2系列だけ濃くして、残りはグレーにする(09)。

色相を心理効果で選ぶ根拠は弱い。赤の効果の研究はメタ分析(Gnambs 2020)で、出版バイアスを補正すると証拠がなくなった。色相は既存の資産、競合との区別、利用者の慣習、コントラストの取りやすさで決め、理由もそう書く。「信頼感のある青」は理由にならない。OKLCH などの知覚的な色空間は段のコントラストを予測しやすくする道具にすぎず、合否は WCAG 2 の比(文字 4.5:1、部品 3:1)で測る(09)。

### 2.6 面と線

影・線・塗り・角丸は、それぞれ「これは独立した物だ」という印になる。役割で使い分け、全部の塊に同じ影と角丸を付けない。影を弱めたら、押せる範囲が分かるように薄い線を足す。角が鋭すぎれば少し丸める(15)。入れ子の角丸は外側を内側と余白の和にする(01、03)。

### 2.7 動き

動きは明快さか機能を足すときだけ付ける。何度も使う操作とキーボード操作には付けない。付けるなら 300ms 未満の ease-out で、押下で少し縮める程度にする。メニューの出現や検索欄の展開のような段階的開示は、動きで「どこから来たか」を示す。スクロールを乗っ取る演出はほぼ使わない。動きを減らす設定の人には動かさない(02、03、07、15)。

### 2.8 文言

文言は設計の材料だ。機能を説明する文を足すより、動詞で操作を名指す。ボタンは「追加」だけで終えず、「カードを追加」と具体的に書く。エラーは何が起きてどう直すかを書く。迷いやすい制約だけを、入力の前に見せる(01、07、15)。

### 2.9 データと状態を見せる

数字・グラフ・状態を見せる画面では、目的から型を選ぶ。比べるなら棒で原点は0、推移なら線で、月次のような離散データは補間しない。構成比は区分が少ないときだけ円やドーナツにして、合計を中央に置く。数字には比較の相手(前月比、目標、基準線)を添え、単位と最小・最大を図の内側に出す。凡例より直接ラベル、飾りは足さない。これらはデジタル庁のダッシュボードガイドブック、Few、Datawrapper、Carbon などの一次資料で一致している(21)。

色はカテゴリ・連続・発散・強調の役割で選び、意味のためだけに使う。色を担当するのは小さな面積(状態のチップ、点、リング、差分の数字)で、文字と大きな面は中立のまま静かに保つ。Marty が「好き」と答えた beautifului.dev、エージェント UI の Git の時系列、Copilot Money は、どれもこの作り方をしている(21)。

Lumen の規則のうち、横棒の禁止とドーナツの優先は、比較には棒を推す一次資料と食い違う。指摘のきっかけは 8px の細すぎる棒だったので、構成比は 5〜7 区分のドーナツに収め、合計を中央に置き、それを超える区分や順位の比較は棒を使わず値付きの一覧にする。目盛りと単位は値を読ませるグラフに必ず付け、「基準線の上か下か」「増えたか減ったか」だけを答えるグラフ(Copilot Money の主役のグラフ)は、基準線と差の数字で足りるので省いてよい。この2点と前段の好みの結論は、2026-10-27 に Marty が実物の画面を見て「この案でよい」と確認した(08、21)。

### 2.10 見せ場を一つ

画面ごとに最重要の一点を決め、ほかを弱める。慣習には従い、外すときは意図して一点だけ外す(小さな動きや独自の機能)。迷ったら飾りを一つ外す(12、15)。

### 2.11 確かめる

ぼかして見て、主役とまとまりが残るか(スクイントテスト)を確かめる。幅 320px、200% ズーム、日本語の長文と短文、空とエラーの状態も見る。機械で測れるもの(コントラスト、タッチ領域、フォーカス)はスクリプトで測る。自動検査が拾えるのはアクセシビリティの問題の約57%なので、通っても完成とは書かない(04、11)。

## 3. 理由の書き方

型は「目標 → 利用者・文脈 → 検討した案 → 選択 → 失うもの・確かめ方」。研究(QOC)、批評の実務(Discussing Design)、Stripe や Linear の公開記事がこの要素に収束する。配置なら「〔画面の仕事〕のために〔要素〕を〔位置〕に置く。理由は〔課題/頻度/慣習/実測〕。〔代案〕は〔失うもの〕のため採らない」と書く(10、12)。

> 異常件数を左上の大きな数値にした。毎朝最初に確認する値で、左上は注視が集中する(NN/g)。今回だけ異常な値は色で強調し、ふだんは色を使わない。強調しすぎると何も目立たなくなる(Few)。

重要でない決定は一行でよい。慣習に従った決定は「慣習に従う」と書けば理由になる。理由が題材・利用者・制約のどれにも結びつかない決定は、「好み」として印を付けて隠さない(12、13)。

## 4. Marty に見せる前に通す問い

Lumen の判断の記録に残る Marty の指摘を頻度順に並べると、最初に問われるのは美しさではない。見せる前に、次の順で自分に問う(08)。

1. 見えるか。背景と文字のコントラスト、細すぎる線、潰れた小さな区分。("hard to see")
2. スケールは分かるか。軸、単位、最小と最大、基準線。("there is no scale.")
3. この数字は何の判断に効くか。比べる相手はあるか。("not useful data")
4. 同じものは同じ見た目と同じ位置か。("no consisitency")
5. スクロールしないと届かない操作はないか。横スクロールはないか。
6. 同じ情報を二度出していないか。
7. 提案文や機能の説明文が紛れていないか。("Never have suggestions in this app")
8. 全部の箇所を直したか。("did you check all places?")

Marty の好みは、この知識の上に載る差し替え可能な層として扱う。GoodLinks と X に手で保存したデザイン、beautifului.dev の実測、Lumen の記録から分かっているのは次のとおり(01、06、08、14)。

- アプリはライト。ダークは見にくい。暗い地に1色を光らせる見た目は、動画やランディングページに限って保存している。
- 地は白か極薄のグレーで、ほとんど見えない 1px の線で区切る。影はほぼ使わない。ただしカードの背景がない平らな配置は「見にくい」と言われた。
- 色は意味にだけ使う(完了は緑、削除は赤、選択と送信は青)。主役のアクセントは1色。
- 書体は Inter と Noto Sans JP(Lumen は Geist)。
- 文字は小さめで、行を詰めた一覧性の高い画面を好む。日本語では 14px を下限にする。
- 大きな数字には意味を添える。説明文は減らす。
- 実在の参照25件で「好き」だったのは、データや状態を意味のある色で密度高く見せる画面(beautifului.dev、エージェント UI の Git の時系列、Copilot Money)。情報の少ないミニマルなランディングページや、イラストと遊びの多い見た目は「違う」で、整った普通の SaaS の画面は「ふつう」止まりだった。Copilot Money は暗い地でも「好き」だったので、好みの軸は明暗より情報の見せ方にある(21)。
- Lumen の暖かい紙色は、X と GoodLinks の保存では1件しか裏づけがない。Lumen 固有の選択として扱い、ほかの道具に広げるときは確かめる。

規則を使うときは、規則と一緒に理由も見る。理由が当てはまらない画面には規則も当てはまらない(08)。

## 5. 直す順番と、よくある誤り

既存の画面を直すとき、熟練者の手順は事例をまたいでほぼ同じだ(20)。

1. 範囲と残すものを決める(構造やブランドの識別性を残すか)。
2. 目的と、利用者がこの画面ですることを書き、重要度の順に並べる。ぼかして見て、最初に目に入るものと重要度を突き合わせる。
3. 全体に効く小さな修正を先にやる。最大幅、本文の大きさ、グレーの段階、ナビの現在地の示し方。
4. 構造と揃え。不要な演出を外し、組み分けして位置を決め、揃える。
5. 主従。大きさ、色、太さの順で階層を作り、補助を下げる。ラベルは外すか薄くする。
6. 部品。ボタンの主従、入力欄の高さと幅、表、状態表示。
7. 仕上げ。影・角丸・線の整理、アイコンの統一、グレーへのブランド色相の混入、書体。
8. 確かめる。コントラストの実測、モバイル、実データの端。

リデザインの事例15件で直された誤りは、多い順に「全部が同じ重さで主従がない」「余白が詰まっているか、ばらばら」「色やグレーが多すぎる」「揃っていない」「主操作が1つに決まっていない」だった。装飾を足して直した事例はなく、足したのは情報(件数、日付、単位、現在地)と安心させる一言だけだった(20)。Malewicz は自分の画面を見直す順として、余白 → 書体 → 色 → アイコンを挙げている(17)。

## 6. エージェントとしての作り方

1. 作る前に、ブリーフから方向を3〜4案、背景色・アクセント色・書体と一行の理由つきで出し、人か別の批評者が一つ選ぶ。一般的な禁止(「クリームを使うな」「ミニマルに」)は別の固定パレットに移るだけで効かないと、Anthropic の公式ガイドが書いている(13)。
2. トークン(色・文字・余白・角丸・影・動き)を先に書き出し、以降はそこからだけ選ぶ。機械で守らせるルールは5個程度から始める。強すぎる制約は出力を無難にする(13)。
3. 決める事柄ごとに「選択 / 捨てた案 / 根拠となるブリーフの項目」を、作る前にファイルに書く(13)。
4. 作った後は、意図を知らない別のエージェントにスクリーンショットだけを渡し、決定ごとの「画面でこう見えるはず」という主張を確かめさせる。自己採点は甘くなる(Anthropic の実験)(05、13)。
5. 直す対象は一周に一つに絞り、修正の周回に上限を置く。上限を超えたら残った問題を付けて人に返す(マネーフォワードのデザインハーネス)。周回は5〜15で頭打ちになる(13)。
6. 人の指摘は言葉ではなく画面の要素に結びつけて受け取り、共通の規則に戻すのは人が承認してから(13)。

## 7. まだ分からないこと

- 根拠を書く運用が品質を上げるという実証はない。後付けを防ぐ手順(作る前に書く、画面で確かめる)は推論で組んだ(12、13)。
- 参照画像を渡す方法と言葉で仕様を渡す方法、複数案から選ぶ方法と一発で作る方法の対照実験は、コーディングエージェントでは見つからなかった(13)。
- 「内側の余白 ≤ 外側の余白」、4 と 8 の倍数、Apple 44pt の根拠は、どの公式文書にも書かれていない(11)。
- 日本語 UI に特有の AI っぽさを扱った資料は見つからなかった(05)。
- YouTube の字幕の一部は回数制限で取れなかった。Rachel How、Jesse Showalter、Kevin Powell、DesignCourse などの未読の動画は 16、17 の Gaps にある。
- 書籍(Refactoring UI、Practical UI、ノンデザイナーズ・デザインブック など)の本文は、無料の章と二次要約でしか読めていない(18、19)。
