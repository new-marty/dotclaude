# Authoring a high-quality Agent Skill (SKILL.md + references/) for upstream UX design in dotclaude

Read on 2026-10-20. All URLs fetched that day; docs change, so re-check numbers (esp. Claude Code listing caps) before relying on them. Local paths were read from /Users/gary/dev/dotclaude (HEAD efe3b28) and ~/.claude/skills/synced/.../skill-creator.

## 1. Official format rules: structure, frontmatter, limits, progressive disclosure

### Takeaway
A skill is a directory with SKILL.md (frontmatter + body) and optional scripts/, references/, assets/. Hard limits: name <=64 chars, description <=1024 chars (spec) and, in Claude Code, description+when_to_use truncated at 1,536 chars in the listing. Body under 500 lines; references one level deep from SKILL.md; TOC for long reference files.

### Cited Findings
- Directory layout: `SKILL.md` required; optional `scripts/`, `references/`, `assets/` (templates, images, data) — [agentskills.io spec](https://agentskills.io/specification)
- `name`: 1-64 chars, lowercase letters/digits/hyphens, no leading/trailing hyphen, no `--`, must match the directory name; Anthropic docs add: no XML tags, no reserved words "anthropic"/"claude" — [spec](https://agentskills.io/specification); [Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- `description`: non-empty, max 1024 chars, no XML tags, must say what the skill does AND when to use it; must be written in third person because it is injected into the system prompt ("Processes Excel files", not "I can help you...") — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude Code frontmatter: all fields optional, only `description` recommended. Fields include `name`, `description`, `when_to_use` (extra trigger phrases/examples, appended to description), `argument-hint`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `hooks`, `paths` (globs limiting auto-loading), `metadata`, `license`, `compatibility` (<=500 chars). Unknown fields are ignored. If the YAML does not parse the skill loads with no metadata (the `/name` still works but Claude cannot match the description) — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- Combined `description` + `when_to_use` is truncated at 1,536 chars in the skill listing (configurable via `skillListingMaxDescChars`); "put the key use case first". The listing budget scales at 1% of the context window; when many skills exist, descriptions are dropped starting with the least-invoked skills (names always stay) — [Claude Code docs, Troubleshooting](https://code.claude.com/docs/en/skills)
- Once invoked, the rendered SKILL.md stays in the conversation; after auto-compaction only the first 5,000 tokens of each invoked skill are re-attached (25,000 combined budget), so put the most important instructions near the top — [Claude Code docs](https://code.claude.com/docs/en/skills)
- Three loading levels: metadata ~100 tokens/skill always loaded; SKILL.md body "under 5k tokens" on trigger; bundled files only when read (scripts run without entering context) — [Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview); [spec](https://agentskills.io/specification)
- Body "under 500 lines for optimal performance"; split into separate files when approaching it — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Keep references one level deep from SKILL.md: when a referenced file links to another, Claude may `head -100` it and read incompletely — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Reference files over 100 lines should start with a table of contents (best practices); the skill-creator skill says >300 lines — two thresholds, both official-ish; use the stricter 100 — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); local skill-creator SKILL.md line ~92 (`~/.claude/skills/synced/49334346-.../skill-creator/SKILL.md`)
- Patterns for splitting: (1) high-level guide pointing to FORMS.md/REFERENCE.md; (2) domain-specific files (reference/finance.md...) so unrelated context is not loaded; (3) conditional details ("for tracked changes see REDLINING.md") — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Name files descriptively (`form_validation_rules.md`, not `doc2.md`); forward slashes only — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Anthropic engineering post: progressive disclosure is "the core design principle that makes Agent Skills flexible and scalable"; when SKILL.md gets unwieldy split it; for mutually exclusive contexts keep paths separate to reduce tokens — [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (fetched via summarizing tool; quotes are the tool's, not verified against raw HTML)
- Naming: gerund form recommended (`processing-pdfs`), noun phrases / action forms acceptable; avoid vague (`helper`, `utils`) and inconsistent patterns within a collection — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

### Inferences
- For the UX skill, SKILL.md should hold only: when it applies, the stage flow with exit criteria, decision rules, and "which reference to read when". Templates (persona, journey map, screen inventory, flow spec) and method details go to references/ files linked directly from SKILL.md (no chains). Each reference >100 lines gets a Contents list.
- Put the 5,000-token-after-compaction constraint to use: the stage order and gates must be in the first ~100 lines of SKILL.md.

### Gaps
- Official docs give no hard limit on number/size of reference files, only "focused" (spec). No official token cap on references.

## 2. Writing the description for triggering (and competing with frontend-design)

### Takeaway
The description is the sole trigger mechanism. Anthropic's own advice: say what + when, include natural user phrasings, be "a little pushy" because Claude undertriggers, use imperative "Use this skill when...", describe user intent not implementation. There is no official priority/ordering mechanism between two matching skills; being first is achieved by a sharper, intent-based description plus an explicit boundary, not by an ordering field.

### Cited Findings
- "Claude uses it to choose the right Skill from potentially 100+ available Skills"; avoid vague descriptions like "Helps with documents" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Principles: imperative phrasing ("Use this skill when..."), focus on user intent not implementation, "err on the side of being pushy" listing contexts even when the user does not name the domain, keep concise (few sentences to a short paragraph) — [agentskills.io, Optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)
- skill-creator: description is "the primary triggering mechanism"; "All 'when to use' info goes here, not in the body"; "Claude has a tendency to 'undertrigger' skills ... make the skill descriptions a little bit 'pushy'", example: "Make sure to use this skill whenever the user mentions dashboards, data visualization... even if they don't explicitly ask for a 'dashboard.'" — local `~/.claude/skills/synced/49334346-.../skill-creator/SKILL.md` lines 62-69; same text in [anthropics/skills skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator)
- Agents consult skills mainly for tasks beyond what they can do alone; one-step trivial requests may not trigger even with a perfect match. So trigger tests must use substantive, multi-step prompts — [agentskills.io](https://agentskills.io/skill-creation/optimizing-descriptions); skill-creator "How skill triggering works" (local file line ~396)
- To tune: should-not-trigger queries should be near-misses (shared keywords, different need), not obviously unrelated ones; refine against train queries only; avoid pasting keywords from failed queries (overfitting); "add specificity about what the skill does *not* do, or clarify the boundary between this skill and adjacent capabilities" — [agentskills.io](https://agentskills.io/skill-creation/optimizing-descriptions)
- Claude Code troubleshooting for non-triggering: check the description has keywords users naturally say; `/skill-name` to invoke directly; "too often": make description more specific or `disable-model-invocation: true` — [Claude Code docs](https://code.claude.com/docs/en/skills)
- Claude Code lets you measure triggering for plugin skills with `claude plugin eval` and a `tool_used: Skill` grader — [Claude Code docs](https://code.claude.com/docs/en/skills) (the agent guide `claude plugin eval` exists per the agent-types list; not read in depth). A generic shell approach: run `claude -p "<query>" --output-format json` and check for a `tool_use` named `Skill` with `.input.skill == <name>`, 3 runs per query, pass threshold 0.5 — [agentskills.io](https://agentskills.io/skill-creation/optimizing-descriptions)
- The competing skill: `frontend-design` (claude-plugins-official) has description "Guidance for distinctive, intentional visual design when building new UI or reshaping an existing one. Helps with aesthetic direction, typography, and making choices that don't read as templated defaults." — local `/Users/Gary/.claude/plugins/marketplaces/claude-plugins-official/plugins/frontend-design/skills/frontend-design/SKILL.md` lines 1-5. It matches "build new UI"; it does not mention requirements, flows, IA or screens-as-structure. Plugin skills are namespaced and both load, so no name collision/override — [Claude Code docs, priority table](https://code.claude.com/docs/en/skills)
- Name-collision rules (enterprise > personal > project; skill beats `.claude/commands`) do not decide which of two differently-named skills fires — [Claude Code docs](https://code.claude.com/docs/en/skills). I found no official statement of how Claude ranks two matching descriptions.
- Community (not official, single-author tests): plain instruction to use skills ~50% activation; a forced "evaluate then activate" UserPromptSubmit-style hook ~84% on four SvelteKit skills — [scottspence.com](https://scottspence.com/posts/how-to-make-claude-code-skills-activate-reliably) (as reported in search snippet; page not fetched). Treat as anecdote.
- Anthropic: rules that must hold every time belong in a hook, not skill text — [Claude Code docs, "Claude stops following a skill"](https://code.claude.com/docs/en/skills)

### Inferences
- To fire before frontend-design: (a) put the upstream phrasings in the description ("I want to build an app", "what screens", "design the UX", "user flow", "information architecture", "app idea") plus Japanese equivalents (house style, see section 5); (b) describe user intent: deciding who the users are, what they do, which screens and flows exist, before any visual or code work; (c) add an explicit boundary sentence: "Use before any UI implementation or visual-design skill (e.g. frontend-design); not for styling, typography, or writing components." The boundary also reduces the opposite error (firing on pure visual-polish requests); (d) keep the key use case in the first ~300 chars because of the 1,536-char listing cap; (e) optionally use `when_to_use` for the extra phrase list.
- Because frontend-design triggers on "building new UI", the most reliable way to guarantee ordering is not description alone: add one line to the skill (and maybe to the repository CLAUDE.md or a hook) stating "if frontend-design/another UI skill is loaded and no UX design exists yet, stop and run this skill first". Hook-based enforcement is the only mechanism Anthropic documents for "must always happen" (claim above). This is a design choice for the parent agent; I did not test it.
- Do not set `disable-model-invocation: true` (z-prototype and z-teach do, locally) because that removes the description from context and the skill could never auto-fire.

### Gaps
- No official source on how ties between overlapping skill descriptions are resolved. Only empirical testing (see section 4) can show whether the new skill fires first.
- Did not read the claude.ai/Anthropic "Prompting best practices" or `claude plugin eval` docs in full.

## 3. Content design: concision, degrees of freedom, workflows, templates, feedback loops

### Takeaway
Write only what Claude lacks; match specificity to fragility (design reasoning = high freedom; output templates = medium; none need low freedom); use a checklist workflow with gates; give templates with stated strictness; explain why instead of shouting MUST.

### Cited Findings
- "Concise is key": context window is a public good; "Default assumption: Claude is already very smart. Only add context Claude doesn't already have"; challenge each paragraph for its token cost — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Degrees of freedom: high freedom (text instructions) when multiple approaches are valid and context decides; medium (templates/pseudocode) when a preferred pattern exists; low (exact scripts) when fragile. Analogy: narrow bridge vs open field — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Workflows: break complex work into sequential steps; for complex ones give a copyable checklist ("- [ ] Step 1 ...") so steps are not skipped; large workflows can be pushed to separate files — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Feedback loops: "run validator, fix errors, repeat", and the validator can be a reference document (e.g. STYLE_GUIDE.md checklist) rather than a script; "only proceed when all requirements are met" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Template pattern: say how strict it is. "ALWAYS use this exact template" for strict formats vs "sensible default ... use your best judgment" for flexible — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Examples pattern: input/output pairs convey style and detail level better than description — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Conditional workflow: decision points ("Creating new content? -> X; editing? -> Y") — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Avoid time-sensitive information (use an "old patterns" section); use one term consistently; do not offer too many options: give a default plus one escape hatch — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Writing style (skill-creator): imperative form; "explain to the model why things are important in lieu of heavy-handed musty MUSTs"; ALWAYS/NEVER in caps is "a yellow flag"; generalize rather than overfit to the test examples; keep the prompt lean (read transcripts, remove parts that cause wasted work); bundle a script when every test run writes the same helper — local skill-creator SKILL.md lines 137-139 and 296-306; [agentskills.io evaluating skills](https://agentskills.io/skill-creation/evaluating-skills) says the same ("Reasoning-based instructions work better than rigid directives")
- Anthropic's checklist before sharing: description specific with key terms and what+when; body <500 lines; details in separate files; no time-sensitive info; consistent terminology; concrete examples; references one level deep; workflows with clear steps; at least three evaluations; tested with Haiku, Sonnet and Opus — [best practices checklist](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

### Inferences
- UX design is mostly high-freedom (judgment: what are the users' jobs, which screens) with a few strict gates: (1) do not write UI/code until the stage outputs exist; (2) ask the user rather than invent unknown product facts. Use a numbered stage checklist in SKILL.md with an explicit exit criterion per stage and a "do not proceed if" rule; use a medium-freedom template per artifact (state "default, adapt as needed") in references/.
- Decision criteria in SKILL.md should be short rules each with a reason clause (matches the local "Text for agents" rule, section 5).
- Avoid offering five UX methods; name one default method per stage and put alternatives in references/ with a "use when" line.

### Gaps
- No official guidance specific to design/non-code skills beyond the generic "Skills without code" workflow example.

## 4. Evaluation and testing (the with/without comparison on 3 test cases)

### Takeaway
Anthropic's procedure: build evaluations first, 2-3 realistic prompts, run each with the skill and a baseline (no skill for a new skill) in clean-context subagents launched in the same turn, add assertions after seeing first outputs, grade with evidence, aggregate pass rate/time/tokens, review by a human, iterate; then optimize the description with ~20 trigger queries.

### Cited Findings
- Evaluation-driven development: identify gaps by running Claude without the skill, create three evaluations, establish baseline, write minimal instructions, iterate; "Create evaluations BEFORE writing extensive documentation"; Anthropic notes there is no built-in runner — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Test with all models you will use (Haiku: enough guidance? Sonnet: clear? Opus: avoids over-explaining?) — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude A / Claude B method: author with one instance, test on a fresh instance with real tasks, observe navigation (unexpected read order, missed references, ignored files), return observations to A — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Test case = prompt + expected_output (+ files). Start with 2-3 cases; vary phrasing/detail/formality; include an edge case; use realistic context. Stored in `evals/evals.json` (`skill_name`, `evals[]` with `id`, `prompt`, `expected_output`, `files`, later `assertions`) — [agentskills.io evaluating skills](https://agentskills.io/skill-creation/evaluating-skills); local skill-creator SKILL.md lines 141-160
- skill-creator exact run workflow (local `~/.claude/skills/synced/49334346-.../skill-creator/SKILL.md`, lines 163-250):
  1. Workspace `<skill-name>-workspace/` sibling to the skill dir; `iteration-N/` then one directory per test, named descriptively (`eval-<name>/`).
  2. Step 1: "spawn two subagents in the same turn" per test case, with-skill and baseline, so they finish together. With-skill prompt: `Execute this task: - Skill path: ... - Task: <prompt> - Input files: ... - Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/ - Outputs to save: ...`. Baseline for a new skill: same prompt, no skill path, `without_skill/outputs/`; for an improved skill: snapshot the old one (`cp -r <skill-path> <workspace>/skill-snapshot/`) and save to `old_skill/outputs/`. Write `eval_metadata.json` per test (`eval_id`, `eval_name`, `prompt`, `assertions`).
  3. Step 2: while runs proceed, draft objectively checkable assertions; explain them to the user; update `eval_metadata.json` and `evals.json`.
  4. Step 3: when each subagent finishes, save `total_tokens` and `duration_ms` immediately to `timing.json` (task notification is the only place they appear).
  5. Step 4: grade each run (grader subagent reading `agents/grader.md`, or inline) into `grading.json` with expectation fields exactly `text`, `passed`, `evidence` (viewer depends on them); use scripts for programmatic checks; aggregate with `python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>` (benchmark.json/benchmark.md with pass_rate, time, tokens, mean +/- stddev, delta; with_skill listed before baseline); do an analyst pass (`agents/analyzer.md`: non-discriminating assertions, flaky/high-variance evals, time/token trade-offs); launch viewer `eval-viewer/generate_review.py <workspace>/iteration-N --skill-name "..." --benchmark .../benchmark.json` (`--previous-workspace` for iteration 2+, `--static <path>` for headless, which downloads `feedback.json`).
  5. Step 5/Improve: read feedback; generalize, keep lean, explain why; rerun into `iteration-<N+1>/` including baselines; stop when the user is happy, feedback is empty, or progress stalls.
  6. Optional blind comparison via `agents/comparator.md` + `agents/analyzer.md`.
  7. In claude.ai (no subagents): run test cases yourself sequentially and skip quantitative benchmarking (local file lines 420-428).
- Assertion guidance: objective, specific; not "output is good"; not brittle exact phrases; style/visual quality goes to human review rather than assertions; require concrete evidence for a PASS; drop assertions that pass in both configs (non-discriminating); investigate assertions that fail in both — [agentskills.io evaluating skills](https://agentskills.io/skill-creation/evaluating-skills)
- Clean context per run is required so the agent follows only SKILL.md; each run's subagent isolation gives this — [agentskills.io](https://agentskills.io/skill-creation/evaluating-skills)
- Description optimization: ~20 queries, 8-10 should-trigger / 8-10 should-not (near-misses), realistic detail (file paths, backstory, typos); run each 3 times, trigger rate threshold 0.5; split 60% train / 40% validation, choose best iteration by validation pass rate, up to ~5 iterations — [agentskills.io](https://agentskills.io/skill-creation/optimizing-descriptions); skill-creator `scripts/run_loop` section (local file lines 333-402)
- Local skill-creator support files exist: `agents/` (grader, analyzer, comparator), `eval-viewer/`, `references/` (schemas.md), `scripts/` — `ls` of `~/.claude/skills/synced/49334346-a1e7-483b-9fec-48aed39b78ea_66fcd506-3620-4c1d-99a8-994b7d3fab77/skill-creator`

### Inferences
- For the stated 3-case comparison: workspace under /Users/gary/tmp/ux-design-skill/ (not inside the repo), baseline = no skill (new skill), three prompts that differ in specificity (e.g. a vague "I want to build an app for X"; a prompt that already names screens/UI; a mid-way case where frontend-design could be loaded). - Triggering evaluation is separate from output evaluation: do both. The 3 output cases are not enough to validate triggering (need the ~20-query set, or at least ~6-10 queries x 3 runs).
