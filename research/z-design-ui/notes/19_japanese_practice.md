# 日本の実務者の UI デザイン知(日本語 UI 中心)

調査日: 2026-10-26。範囲は GoodLinks 保存分 13 件と、日本語圏のデザインシステム・組版資料・実務者の記事。デジタル庁 DADS の数値は 07・11 で読了済みなので、ここでは再掲せず差分だけ書く。「読了」は本文を取得して読んだもの。【弱】は一次情報に届かない、または個人の意見。【推論】は私の推測。

## 結論

1. 日本の実務者の UI 知は、組版(約物・和欧間・字間)、文言(用字用語・操作語・エラー文)、入力(全角半角・住所・氏名)の 3 領域に集中している。色・余白・階層は欧米の知と同じ原則で、日本固有の数値はほぼ出てこない。
2. 組版の細部は、手で調整せず CSS と文言ルールに任せる流れにある。`text-autospace`、`text-spacing-trim`、`word-break: auto-phrase` がそれにあたる。ただし対応ブラウザが揃っておらず、実装前に必ず確認が要る。
3. 日本語 UI の文言は、SmartHR の「操作を表す用語」表が最も具体的で、1 語 1 意味に固定する方針がはっきりしている(例: 取り消し/キャンセル/中断を操作の進行状況で使い分ける)。
4. 余白は「大きさでグループを表す」記号として扱う。ktcryomm は 4/8/20pt、原は「数値の中央ではなく重心」と述べる。どちらも数値の根拠ではなく運用の型である。
5. 日本語の本文を太く見せる UD 書体の選択、游ゴシックの weight 差、Noto Sans JP の下寄り(Windows)は、日本語特有の落とし穴で、フォント指定と上下パディングの両方に効く。

## 原則カタログ

書式は 原則 / なぜ / 具体例・数値 / 例外 / 出典 の順。

### A. 余白・配置・重心

**A1 余白の大きさでグループを表す。** なぜ: 余白は「何もない領域」ではなく、要素の所属と重要度を示す記号だから。具体例: タイトルとコンテンツの間 8pt、セクション境界 20pt、コンテンツ同士 4pt に固定すると、見た目だけで関係が読める。同じ間隔は同等の重要度を示す。実装では VStack/HStack の spacing に意味を持たせる。例外: 記載なし。出典: ktcryomm https://speakerdeck.com/ktcryomm/naaxiong-di-yu-bai-noyi-wei-wokao-etekara-uishi-zhuang-sitekure (読了)

**A2 数値の中央ではなく視覚の中央に置く。** なぜ: 上方距離過大の錯視で、上下の数値上の中央に置くと下にずれて見える。左右も、文字を詰めたブロックは写真より重く見え、重心が外へ寄る。具体例: スライドでは Ameba の 20 周年サイトで上 317px・下 295px の差を調整前後で示し、193px / 193px でも左が重く見える例を出す。ライブ取得の数値で、画像は未確認【弱】。例外: 機械的に揃えるべきグリッドや表。出典: 原 https://speakerdeck.com/yuichi_hara7/mei-siiuiwozuo-rutameni-dezainagayi-shi-siteiru-tiyotutositakao-efang (読了。引用された Goodpatch と traP の錯視記事は未取得)

**A3 近接を守る。** なぜ: 関係のない要素が近いと所属が曖昧になり、利用者ごとに解釈が割れる。具体例: 社員紹介で役職名と名前が上下の写真の中間にあると、どの写真のものか分からない。同じ人の要素は近づけ、別の人との間を大きく離す。出典: qiita 9re-pe https://qiita.com/9re-pe/items/0296f8a8c11490efda21 (読了)

**A4 項目名・必須マーク・入力欄は一本の線に揃える。** なぜ: 揃っていないと見た目が散らかり、カーソルの開始位置も毎回ずれる。具体例: 左揃えにし、入力欄の右端もできる限り揃える。中央揃えは上級者向け。出典: 同上

**A5 余白は 8px の倍数、微調整は 4px の倍数。** なぜ: 一貫した規則を持つため。具体例: SmartHR の余白トークンは 0/4/8/12/16/20/24/32/40/48/64px(基準 16px)。旧セマンティック名(XXS=8px など)は非推奨になった。例外: 記載なし。出典: SmartHR https://smarthr.design/products/design-tokens/spacing/ (読了、理由の記載なし)。elevenlines (読了、一部推定)

**A6 図形を足さず、文字を小さくして余白を作る。** なぜ: 図形が増えると余白が消え、文字が読みにくくなる。具体例: 優先度が低い文字を小さくする、不要な図形を削除する、詰め込まずページを分ける。出典: desaken https://desaken.com/archives/8511 (読了、資料用。UI への転用は【推論】)

### B. 階層・ラベル・情報量

**B1 ラベルは最後の手段。** なぜ: すべてにラベルを付けると全データが等しく重く見え、階層が作れない。形式で自明なもの(メール、電話、価格)は不要。具体例: 「在庫 : 12」ではなく「残り在庫12個」、「ベッドルーム : 3」ではなく「3ベッドルーム」。ラベルを残すなら小さく、薄く、細くする(3 つを併用してもよい)。例外: 仕様表など、利用者がラベルを探す画面では、ラベルを濃く値を少し薄くする。出典: photoshopvip https://photoshopvip.net/160498 (読了、Refactoring UI の抄訳)

**B2 情報量は「誰が何のために使うか」で削る。** なぜ: 削る基準がデザイナーの都合だと、必要な情報まで消えて自己満足になる。具体例: 物件一覧は優先度の低い情報を詳細へ移し、自明な項目名を削り、設備の有無はアイコンにする。ただしアイコンの意味が初見で伝わるかを確かめる。サイズ表記が S/M/L と合わず失敗した例もある。出典: qiita 9re-pe (読了)

**B3 複雑な機能は削らず、制御された見た目で信頼を作る。** なぜ: B2B SaaS では複雑さが仕事そのもので、削ると機能が壊れる。整った UI は「複雑さを制御できている」証拠になり、信頼に変わる。具体例: 飛行機のコックピットの比喩。Stripe の品質基準は Powerful / Well-crafted / Beautiful / Pride の 4 つ。メール文面と UI の見直しで CV が 20% 向上したという話は一次情報未確認【弱】。出典: note inofthefor https://note.com/inofthefor/n/nb22fca5ac47d (読了)

**B4 「綺麗」「使いやすい」「美しい」を分けて評価する。** なぜ: 綺麗は規則から外れていない状態で画面 1 枚で判定できる。使いやすさは利用者・状況・目的が定義されて初めて測れる(ISO 9241-11)。美しさは主観で規則に書き切れない。見た目が良いと操作しやすいと感じる錯覚(美的ユーザビリティ効果、黒須・鹿志村 1995)が欠陥を隠す。具体例: 規約どおりでも入力手順が不自然なフォームがある。逆に、無骨でも熟練者がショートカットで一瞬で終える管理画面は使いやすい。画面に写らない設計(遷移元、権限による出し分け、エラー時、完了通知)が成否を分ける。出典: note kgsi https://note.com/kgsi/n/nd739362cbbae (読了)

**B5 チェックボックスとラジオボタンは慣習どおりに使う。** なぜ: 利用者は過去の経験から操作を予測する(メンタルモデル)。「最も当てはまるもの 1 つ」にチェックボックスを使うと複数選べると誤解される。具体例: 単一選択はラジオ。文化で異なる場合もある。出典: qiita 9re-pe (読了)。ソシオメディア HIG https://www.sociomedia.co.jp/category/shig (読了、24 項目)

**B6 迷う判断にはデフォルト値を置く。** なぜ: 重要度の低い判断でも、選択肢の違いが名前から分からないと利用者は進めなくなる。具体例: 多くの人が選ぶ値を推奨値として先に選んでおく。HIG の「プリコンピュテーション」「タスクコヒーレンス」(最後に行った操作を覚える)と同じ向き。出典: qiita 9re-pe、HIG

**B7 失敗を先に想定する。** なぜ: 送信後にパスワード条件を指摘され、入力が消える体験は離脱を招く。具体例: 条件と入力例を事前に示す。エラー文は「何をしたか・何が問題か・どう直すか」を、能動態の簡単な言葉で例を添えて書く。プロトタイプで失敗を事前に集める。出典: qiita 9re-pe、SmartHR https://smarthr.design/products/contents/error-messages/overview/ (読了。構成は事象・原因・対処。全部載せられない場合の優先順位は「原因・対処・事象」)

**B8 待ち時間は進捗を見せる。** 具体例: 進捗バーと終了予測、待ち中に Tips、バックグラウンド処理にして他の操作を許す。SmartHR は依頼した処理を「{処理名}を受け付けました」と書き、「予約しました」を使わない。出典: qiita 9re-pe、SmartHR 操作語

**B9 画面は名詞(オブジェクト)から決める(OOUI)。** なぜ: 動詞から入るタスク指向だと機能の羅列になり、操作体系にまとまりがない。名詞(オブジェクト)から入り、コレクションビューから詳細ビューへ遷移させる。具体例: ビューは「ソリューションビュー(一覧)」と「シングルビュー(詳細)」。プロセスは 要求分析 → モデル抽出 → ビュー定義 → ビジュアル定義。UI は「状態を適切に抽象化して表示し、内部処理を抽象化して操作を提供する」境界。出典: elevenlines https://speakerdeck.com/elevenlines/uidezainjiang-xi-hui (保存本文は文字化け。ライブ取得で再構成、一部推定)。HIG #23・#24

### C. 色・コントラスト

**C1 色だけで区別しない。** なぜ: 日本人の男性は約 20 人に 1 人、女性は約 500 人に 1 人が色覚の多様性を持つ(LINEヤフー)。P 型・D 型は赤と緑、青と紫、深緑と茶が見分けにくい。具体例: 暖色と寒色を組み合わせ、明度差を付け、文字やマークを併用する(「使用中」「あき」)。東京都ほか自治体が配色ガイドラインを公開し、東京大学・塗料工業会・DIC・CUDO は 2009 年に推奨配色 20 色のセットを作った。出典: LINEヤフー https://www.lycorp.co.jp/ja/story/20231115/accessibility.html (読了、数値基準なし)。検索結果(自治体 PDF)は本文未読【弱】

**C2 コントラスト比の適合基準。** 具体例: 24px(18pt)以上は 3:1、19px(14pt)以上の太字は 3:1、それ以外は 4.5:1(WCAG 1.4.3)。テキスト間隔を利用者が変えても壊れないこと(行間 1.5em 以上、段落後 2em 以上、字間 0.12em 以上)。200% ズームと 400% リフロー(横書き 320px 幅)も確認する。これは推奨値ではなく検証条件。出典: freee https://a11y-guidelines.freee.co.jp/categories/text.html (読了)

**C3 色の面積効果に注意する。** なぜ: 同じ色でも面積が大きいほど、明るい色はより明るく、暗い色はより暗く見える。具体例: #237B31 と #298737 のような近い緑は、並べて選ぶ。出典: 原 (読了)

**C4 キャンセルをグレーにするなら濃いグレー。** なぜ: 薄いグレーは disabled に見える。破壊的操作は赤(iOS HIG)。ユーザーは文を読まずボタンを押すことがあるので、重要なボタンは他と明らかに違う色にする。出典: classmethod https://dev.classmethod.jp/articles/designer_button_cancell_meeting/ (読了)

**C5 色数を絞る。色は意味のある色にする。** 具体例: 白文字と黒文字を混ぜてメリハリを付け、濃色の長方形を敷くと白文字が使いやすい。純色(#000 など)は避ける(elevenlines)。出典: desaken、elevenlines

### D. ボタン・ダイアログ・フォーム

**D1 ボタンには動詞を使う。「はい」「いいえ」を避ける。** なぜ: 押すと何が起きるかを瞬時に示すため。ユーザーは説明文を読まずボタンだけ見ることがある。具体例: 「削除」「キャンセル」(kintone の確認ダイアログの例)。「キャンセル」はキャンセル以外の意味で使わない。出典: classmethod (読了)、cybozu.dev kintone 【弱】(検索結果のみ)

**D2 確認ダイアログの選択肢は 2 つ以下。** なぜ: ダイアログは選ぶまで他の操作を止める。具体例: 3 つ以上ならアクションシートにし、破壊的操作を指から最も遠い上に、キャンセルを下に置く。キャンセル後に戻る画面(元か最初か)を設計し、保存後は完了を伝える。出典: classmethod (読了)

**D3 操作語は 1 語 1 意味に固定する(SmartHR の表)。** 具体例: 取り消し(実行済み)/キャンセル(未実行)/中断(実行中)、追加(新規作成)、複製(別データ作成。「コピー」は貼り付けを伴う場合のみ)、解除(元の状態に戻す)、差し戻し(承認者が修正を求める)、書き出す(「エクスポート」は他ソフトの UI 表記を指す場合のみ)、再読み込み(「更新」は保存に使うので避ける)、移動(「遷移」は使わない)、ボタンは「押す」(クリック/タップとは書かない)、リンクは「開く」、スイッチは「有効にする/無効にする」。ボタンラベルは動詞の終止形。「使用」を基本とし、役立つニュアンスを出すときだけ「利用」。例外: 公文書や他ソフトの UI 表記をそのまま引く場合。出典: https://smarthr.design/products/contents/idiomatic-usage/action/ (読了)

**D4 日本語の曖昧さはルールで埋める。** なぜ: 日本語は一人称や同音異義語で表記がぶれやすく、ぶれるとユーザーが言葉の読解に注意を使う。SmartHR の基準は 一貫性・統一感・検索性・標準化・効率化(『日本語スタイルガイド 第3版』準拠)。出典: https://smarthr.design/products/contents/ (読了)

**D5 郵便番号・電話番号は 1 欄にまとめ、type は text/tel + inputmode。** なぜ: `type="number"` は先頭 0 が消える、ハイフンを入れられない、postal-code の自動補完が効かない。分割欄はコピー&ペーストを妨げる。具体例: `<input type="text" autocomplete="postal-code" inputmode="numeric">`、電話は `type="tel" autocomplete="tel"`。ハイフンの有無は両方許し、サーバー側で正規化する。出典: yumemi https://zenn.dev/yumemi_inc/articles/c1c83cb4cdcaa8 (読了)、ICS MEDIA https://ics.media/entry/11221/ (読了)

**D6 日付は 1 欄+プレースホルダー。生年月日に type="date" は慎重に。** なぜ: 年月日を分けると入力の手間が増える。`type="date"` の年選択 UI はブラウザごとに統一されておらず、遠い日付(生年月日)で体験が悪化することがある。出典: yumemi (読了、2024/10/2 追記)

**D7 氏名は姓と名に分け、ふりがなも同じ単位で分ける。** 具体例: `family-name` / `given-name`。住所の autocomplete は Chrome と Safari で補完範囲が異なる(address-level2 は Chrome が補完しない、address-line1 は Chrome が建物名まで補完)ので、意図を持って設計する。出典: ICS MEDIA、yumemi。**資料間の矛盾**: yumemi は「ふりがな欄に `autocomplete="name"` を付けず、`off` か省略」、ICS MEDIA(2026-05 時点)は「通常の氏名欄と同じ値を指定する。`off` は多くのブラウザが無視する。Chrome はラベルのかな/カナで判定する」。どちらも一次検証は未実施。実装前に実機で確かめる【弱】

**D8 全角/半角・スペースの違いでエラーにしない。** なぜ: 全角と半角の区別がつかない利用者がいて、変換はサーバー側で簡単にできる。具体例: 住所の数字は両方受け付ける、かな/カナの混在はサーバーで変換、半角/全角スペースの差は許容する。出典: ICS MEDIA (読了)

**D9 氏名の異体字(髙・﨑など)は入力方針を早く決める。** 具体例: Shift-JIS 環境では文字化けするため「高」に置換する運用がある。IVS(字形選択子)と IPAmj 明朝(約 6 万字)で個別字形を扱う道もあるが、入力手段が追いついていない。出典: 検索結果のみ(zenn panda728 ほか)【弱】。【推論】戸籍上の字形を保存する必要があるか、事前に業務側と合意する。

**D10 「必須」表示は 07 の規則を参照。** 日本語の必須/任意は「※必須」(DADS)。ここでは追加の一次情報を取得できていない。

### E. 資料デザインから転用できるもの【推論】

**E1 1 ページ 1 メッセージ。** 出典: desaken (読了)
**E2 見出しは装飾せず「大きく太く」。** 背景図形を足すときは細い線のほうが邪魔にならない。出典: desaken
**E3 左揃えを基本にする。** 文章が少しでも長ければ、文頭が揃って読みやすい。中央揃えは短文のみ。出典: desaken、qiita
**E4 特殊書体(明朝・ポップ体)は理由がなければ使わない。** 個性の少ないゴシック体で足りる。出典: desaken。UI では SOMPO が逆に「Noto Sans JP が唯一の正解ではない」と述べるので、ここは目的次第。

### F. 評価の観点

**F1 UI の評価基準に Nielsen の 10 ヒューリスティクスと HIG 24 項目を使う。** HIG は、シンプルに、簡単に、メンタルモデル、シグニファイア、マッピング、一貫性、ユーザーの主導権、直接操作、モードレス、視覚ゲシュタルト、ユーザーの言葉、記憶に頼らない、コンストレイント、プリコンピュテーション、エラー回避、フィッツ、ヒック、複雑性保存、タスクコヒーレンス、メジャーなタスク優先、パースエージョン、ショートカット、オブジェクトベース、ビューはオブジェクトを表象する、の 24 項目。出典: ソシオメディア (読了)

**F2 ENVY DESIGN UI PATTERNS は型の目録。** 37 パーツ・282 型・2442 案。型は見た目の好みではなく、何を伝え、どう動いてほしいかで選ぶ。例: 料金表 23 型(3 プラン比較型、機能比較表型、下限価格型)、フォーム 10 型(1 ページ完結型、ステップ分割型、条件分岐型)、入力欄 9 型(郵便番号から住所型、氏名とフリガナ型)。ベータ版で 2026-12-01 に正式公開予定。各型の判断基準(向く/向かない/よくある失敗)は各ページにあるが未取得。出典: https://envydesign.jp/patterns/ (読了、目録のみ)

## 日本語 UI 特有の規則

### 1. 書体・フォント指定

- **Noto Sans JP は唯一の正解ではない。** 2014 年に Adobe と Google が公開(源ノ角ゴシック)。SIL OFL、10 ウェイト、2021 年に可変フォント化。一方、スマホなど小さい文字では UD 書体のほうが読みやすい場面がある。UD 書体の特徴は、シンプルな骨格、似た字の区別、大きい濁点・半濁点、広いアキ。評価軸は視認性・可読性・判読性。出典: SOMPO https://note.com/sompo_sprint/n/n1b4878cc1479 (読了)
- **UI 向けに挙がった書体:** BIZ UDゴシック/明朝(Google Fonts)、LINE Seed JP、IBM Plex Sans JP、M+、みんなの文字(2022 年から有料。NPO・医療・教育は審査で無料)。システムフォントを指定する考えも認められている(利用者が慣れた書体を尊重)。Web フォントは TypeSquare(月 1000PV まで 1 ドメイン 1 書体無料)、FONTPLUS、Adobe Fonts など。同記事は 2023 年時点の情報で、現在の条件は未確認【弱】
- **明朝体は UI に向きにくい。** 横線が細く、小さいサイズや暗い背景で判別しにくい。UD 明朝は線の細りが解消されている場合がある。
- **SmartHR はあえて書体を指定しない。** OS の設定に委ね、さまざまな言語で正しく表示させる。出典: https://smarthr.design/products/design-tokens/typography/ (読了)。Web フォントは LP やキャンペーン、OS 標準は業務アプリ・日常 UI という使い分けもある(classmethod whatsui5 【弱】、数値なし)。
- **`system-ui` は日本語環境では避ける案。** Windows で游ゴシック UI が使われるため。font-family は `"Local Noto Sans JP", "Noto Sans JP", sans-serif`。出典: tak-dcxi gist https://gist.github.com/tak-dcxi/0f8b924d6dd81aaeb58dc2e287f2ab3a (読了、個人のメモ【弱】)
- **游ゴシックは OS で既定ウェイトが違う。** Windows は Regular、Mac は Medium で、Windows では細く読みにくい。名前も Mac は `YuGothic`、Windows は `Yu Gothic`。出典: 検索結果の要約(フォーラム、CSS Nite)【弱】。メイリオは日本語部分が等幅設計で palt が効かない(ICS MEDIA、読了だが旧記事【弱】)。
- **Noto Sans JP は Windows で視覚的に下寄りになる。** Android の Noto Sans より下に出る原因はハーフレディングの差。Chrome 128 以降と Edge で Noto が既定になりつつあり、アイコンと並べると上下のずれが目立つ。対策は `text-box: trim-both ex alphabetic`(Chrome 133 以降、Safari 18.2 以降)か Meiryo の明示指定。出典: zenn 15 https://zenn.dev/15/articles/d6516675dac2dc (読了)。ICS MEDIA https://ics.media/entry/250319/ は日本語フォントで `cap alphabetic` を使うと削りすぎに見えることがあり、画像との上辺揃えには `trim-both text` が合う場合が多いと書く。矛盾というより、揃える相手で値が変わる。【推論】ボタンは「`text-box` で削る → 上下に同量の padding を足す → 目視」の順で作る。
- **強調は太字、斜体は使わない。** 日本語には斜体がない。`em:lang(ja)` を `bolder` にする運用(tak-dcxi)。ウェイトは本文 400・見出し 700 が多く、日本語は画数が多く同じウェイトでも欧文より太く見えるという指摘がある。小さいサイズでは太字が潰れやすい。出典は一般ブログの寄せ集め【弱】。

### 2. 字間・行間・行長

- **行間は DADS で 170% など(07・11 参照)。** 日本の別実装も同じ範囲にある。SmartHR は段落 1.5、見出し 1.25、ラベル 1。tak-dcxi は段落 1.7〜2、見出し 1.25〜1.5(英文は 1.5〜1.8 / 1.2〜1.4)で、`line-height: 1` を Stylelint で禁止し、`text-box-trim` で代替する。elevenlines は約 1.2 倍が目安で、1.2 以下は読みにくい、1.5 でゆったり、2 で本文中心。出典: 各リンク(読了)。JLReq は印刷が対象で画面の文字サイズは範囲外(11 参照)。
- **日本語の本文はベタ組みが原則。** 字間は原則ゼロ(JLReq)。tak-dcxi は `font-kerning` を日本語で `none`、見出しとキャプションで `normal`、`palt` は見出しのみ。本文の `palt` は影響が大きいので、まず見出しから(ICS MEDIA)。ただし `kern` と `palt` の併用や Firefox の `kern` 無効など、ブラウザ差の議論が続いている(W3C i18n、gist のコメント欄)。出典: https://ics.media/entry/14087/ (読了)
- **字間を足す場合の根拠は弱い。** DADS が小さい字に 2% を足す理由は 11 で未記載とされており、本ノートでも新しい根拠は得られなかった。【弱】
- **行長は文字サイズの整数倍に揃える(JLReq)。** 見出しの高さは「字枠×行数 + 行間×(行数−1)」で計算できる。行長の上限は 11 参照(横組み 40 字)。「35〜45 字」を挙げるブログがあるが出典不明【弱】。ケースによっては「カラム幅は 60ch を超えない」という個人メモもある【弱】。
- **折り返しは文節で。** `word-break: auto-phrase`(Chrome 119 以降、日本語のみ、BudouX の機械学習)。見出しとキャプションに使い、本文まで文節改行すると段落内に不自然な空きが出る(tak-dcxi)。誤判定は `<wbr>` で直し、分離したくない箇所は `&zwj;`。`line-break: strict` で禁則を厳格にする。出典: Chrome https://developer.chrome.com/blog/css-i18n-features?hl=ja (読了)
- **中央揃えは `text-wrap: balance` とセット。** `text-align: justify` は英語混在で崩れるため原則禁止。日本語の `text-wrap: pretty` は Safari に balance のように動くバグがあり、日本語には指定しない(tak-dcxi、バグの現状は未確認【弱】)。

### 3. 約物・和欧混植

- **和欧間は原則として四分アキ**(JLReq)。フォントによっては少し詰めたほうがよい。CSS では `text-autospace: normal` が自動で入れる(Chrome 139 以降、Safari 18.4 以降。MDN は Baseline 2025 の newly available。アキは全角の 1/8 とする資料があるが MDN には記載がなく【弱】)。`pre`、`time`、`input`、`textarea`、`[contenteditable]` は `no-autospace` に戻す運用。
- **コンテンツ側では和欧間に半角スペースを入れない。** SmartHR は「PDFファイルをアップロード」「2020年の年末調整」と詰める。自動アキ(CSS)と手入力のスペースは役割が別で、書き手は詰めて書き、見た目のアキは CSS に任せる。【推論】
- **連続する約物は詰める。** 開き括弧の連続(「（)、閉じ括弧の連続(。」)、終わり→始め(」「)は、後ろの文字の前を二分詰める(JLReq)。`text-spacing-trim: normal`(初期値)がこれを自動で行い、`trim-start` は行頭の開き括弧も半角にする(見出しの先頭を揃える。Chrome 123 以降)。フォントに `halt` か `chws` がないと無効。`space-first` は段落冒頭だけ全角のまま。MDN は実験的機能で Baseline ではない。出典: MDN https://developer.mozilla.org/en-US/docs/Web/CSS/text-spacing-trim (読了)
- **行頭に置けない文字・行末に置けない文字。** 行頭禁則: 句読点、閉じ括弧、中点、ハイフン類、繰返し記号、長音記号、小書き仮名。行末禁則: 開き括弧。分割禁止: 2 倍ダーシ、2 倍三点リーダー、連続する欧文。ぶら下げ組は行末の句読点を行外に出す任意機能(CSS では `hanging-punctuation: last allow-end`、Safari のみ)。出典: JLReq https://w3c.github.io/jlreq/docs/line-composition/ (読了)
- **記号の使い分け(SmartHR)。** 句点は見出しで省略、箇条書きは単語なら省略・文なら付ける。順序に意味があれば「、」、入れ替え可能なら「・」。感嘆符・疑問符は単独なら全角、「!?」「!!」は半角、後ろに文が続くときは全角スペースを入れる。三点リーダーは Web では 1 つに統一(紙は 2 つ組)。括弧: 丸括弧=補足、鉤括弧「」=画面上のメッセージ・入力値・強調、角括弧［］=設定項目名・タブ名・ボタン名、隅付き括弧【】=ユーザーが命名したオブジェクト名、波括弧{}=変数、バッククォート=コードや URL。『』と“”は使わない。例示は「例：」を使い、「（例）」にしない。出典: https://smarthr.design/products/contents/idiomatic-usage/symbol/ (読了)
- **半角にするもの:** ¥、%、3 桁区切りのカンマ、階層の区切り(/、>)。数字は半角。ファイルサイズは「5GB」(スペースなし、英字 2 文字)。出典: SmartHR 数字 https://smarthr.design/products/contents/idiomatic-usage/count/ (読了)

### 4. 数字・日付・数え方

- **人は「名」、件数は「件」。** 「37名の従業員情報」「22件のアカウント」。SmartHR は従業員の氏名と写真を登録しているため「名」が合うとする。自社製品の判断で、他社へそのまま適用できるとは限らない。
- **日付は UI で「2025/01/01」、期間は「〜」。** 時刻は hh:mm:ss。システム処理用は 2 桁そろえ(YYYY/MM/DD)。ヘルプなど文章では「2025年1月1日」「15時35分」も可。
- **表の数字は右揃え。** 桁を縦に比べやすい(SmartHR 表)。数字を目立たせる箇所は `font-variant-numeric: tabular-nums`(tak-dcxi)。日本語フォント自体が tnum を持つかは 07 でも未確認のまま。
- **丸数字は原則使わない。** 環境依存文字。使う場合は Unicode の ①〜⑳(U+2460〜2473)。「か所」「か月」に統一(箇所・個所は使わない)。

### 5. 文言(ライティング)

- **「することができる」を避ける。** 「◯◯できます」。「削除を行う」ではなく「削除する」。
- **敬語を使いすぎない。** 「確認してください」。「ご確認いただけますようお願いいたします」「させていただきました」は避ける。「ご参考ください」は誤り。
- **格助詞を省略しない。** 「項目名を変更します」(「項目名変更します」は不可)。
- **漢字とひらがな。** 表外読み(想い、旧い)は使わない。読みやすい漢字はひらがなに。ただしひらがなにしすぎると、どの漢字か判断する手間が増える。カタカナ語は漢字語への言い換えを先に検討する(意味の振れ幅が大きく、利用者が都合よく解釈するため)。同じことを複数の表現で書かない。社内用語を使わない。出典: https://smarthr.design/products/contents/writing-style/ (読了)
- **漢字:ひらがなの比率。** 7:3 を目安とする一般向け記事はあるが、UI 文言の根拠ではない【弱】。
- **文化に合わせた声を 1 つに決める。** 口調がボタンと FAQ でばらけると体験が一貫しない。急かす言葉と怖がらせる言葉を避け、専門用語には読みを添える。例: 御神籤（おみくじ）。出典: scrapbox ichizen https://scrapbox.io/ichizen/%E6%97%A5%E6%9C%AC%E6%96%87%E5%8C%96%E3%82%92%E4%BC%9D%E3%81%88%E3%82%8BUI%E3%81%A8%E6%96%87%E7%AB%A0 (読了、個人のメモ【弱】)
- **○×△。** 日本では ○ が肯定・決定、△ が部分的、× が否定という体系が説明なしで通じ、一覧表の比較(ENVY の「○×比較型」)に使われる。海外では ○ が「オフ」を意味する場合があり、PlayStation の決定ボタンも日本と欧米で逆になる例がある。海外展開では記号を文字ラベルに置き換える。出典: Wikipedia ほか検索結果【弱】

### 6. 密度

- **日本のサイトが高密度になる理由は、実証研究が見つからない。** 「余白を無駄と感じる」「情報が多いと安心する」は筆者の仮説。Yahoo! の日本版と米国版の比較のような事例はあるが、利用者調査ではない。【弱】 07 の「密度は文脈で決める」(業務画面 Dense、読み物 Standard)に従い、文化を理由に密度を上げない。
- **多言語対応で日本語は短くなりやすい。** 英語原文の最大 2 倍の長さを想定する経験則があるが(出典は一般ブログ【弱】)、日本語は固定幅のボタンを逆に余らせる。可変幅を前提にする。

## 資料間の矛盾と注意

- ふりがなの `autocomplete`(D7)。yumemi と ICS MEDIA で逆。
- text-box の値(`cap alphabetic` / `ex alphabetic` / `text`)。ICS MEDIA と zenn 15 で違うが、揃える相手が違う。
- 07 の「ラベル 14px」と SmartHR の「ラベル M=16px、S は例外」は水準が違う。業務画面(DADS Dense)は 14px 可、SmartHR は 16px 基準。判断軸は密度。
