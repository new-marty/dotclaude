PR 本文はレビュワーと、数年後に履歴を検索する開発者のための文書。diff とコミットが正確に持っている情報（ファイル名・件数・設定キー）を本文で繰り返してもノイズにしかならない。読む人が本文から得たいのは「これで自分の世界がどう変わるか」だけ。この前提をすべての判断基準にする。

## 手順

1. base ブランチを決める。決め打ちせず `gh pr list --state merged --limit 5 --json baseRefName` で直近のマージ先を確認し、それに合わせる。判断できなければユーザーに確認する。指示があればそれに従う。
2. 情報を集める: `git log origin/<base>..HEAD` でコミット群を読み、必要なら `git diff origin/<base>...HEAD --stat` で全体像を掴む。ブランチ名・コミットから関連 Issue を特定する。
3. PR テンプレートを読む(`.github/pull_request_template.md` または `.github/PULL_REQUEST_TEMPLATE/` 配下。なければ見出しなしの散文で書く)。`gh pr create --body` はテンプレートを自動適用しないので、この構成を自分で埋める。SDD・チェックリストの欄は実際にやったことだけに正直にチェックを入れる。タスクが完了した Issue には `Closes #xxxx` を入れ、クローズの意図を明示する。
4. タイトルと本文を下書きし、base とあわせてユーザーに提示して承認を得る。承認前に `gh pr create` を実行しない。
5. 承認後に `gh pr create --base <base>` で作成し（指示があれば `--draft`）、URL を返す。

## タイトル

- 1 行だけで変更内容が完結すること。履歴を流し読みする人はタイトルしか読まない。
- 「Fix bug」「対応」「Phase 1」のような、文脈がないと意味を成さないタイトルにしない。

## 本文の書き方

- 書き出しは日常の言い方 1 文で目的を宣言する。大上段に構えない。「デグレを止める最後の砦が人間のレビューしかなかった」ではなく「CI のチェックがゆるかったので厳しくした」が伝わる。
- what より why を書く。コードと diff は what を語るが、なぜこの変更が要るのか・なぜこのやり方を選んだのかは本文にしか書けない。
- ファイルパス・lint ルール名・件数・設定キーは本文に書かない。詳細が必要なら「詳細はコミットを参照」の一文で足りる。例外として、ツール名や機能名（knip、StrictMode 等）は読者が学ぶべき内容なので書いてよい。
- 変更内容の欄は、変更ファイルの列挙ではなく読者への影響（何ができるようになる・できなくなる・何に気をつけるか）で書く。全件列挙は安全装置ではなく思考停止のサイン。
- 動作確認の欄は、レビュワーがそのまま手を動かせる手順を書く。UI 変更なら Before / After のスクリーンショット欄を残す。
- 変更ファイルが多いときは「どこから読み始めるべきか」を一言添える。diff はアルファベット順に並ぶだけなので、読み順の設計は書き手の仕事。
- 表やボールド装飾を使わない。見出し・箇条書き・本文だけで構成する。

## 文章の書き方

本文の言語はリポジトリに揃える。既存の PR やコミットが英語なら英語、日本語なら日本語で書く。日本語で相談していることは、本文を日本語にする理由にならない。判断がつかなければユーザーに訊く。

以下の規則は言語に依らない。例は日本語のものを挙げている。

AI の文章は「全部を均等に・安全に・対称に」書くから読みにくい。読者が既に知っていることを省き、重要度で文の長さと順序を決める。

- 平易な言葉で書く。PM 隠語（パイロット、エピック等）や、他言語からの直訳（プロダクションコード → 実装コード、本番環境が自然）を使わない。
- 評価語で水増ししない。「大幅に高速化」ではなく「3.2s → 0.4s」。数値や固有名詞に置き換えられない文は削除候補。
- 前置き（「以下 3 つの観点から説明します」）と締めの要約を書かない。1 文目から本題に入る。
- 箇条書きにするのは並列な事実だけ。因果や判断は「だから」「しかし」でつないだ散文で書く。
- 文長を揺らす。大事な点は短文で切り、補足は長めの文にまとめる。「〜です。〜です。」の単調な連続を避ける。
- 長い複文は切る。括弧の挿入は 1 文に 1 つまで。

## 例

書き直し前（実装の言葉。diff の繰り返しでしかない）:

> - `eslint-plugin-boundaries` の `no-unknown-files` を有効化し、違反 42 ファイルを修正
> - `knip.json` の `ignoreDependencies` に 3 件追加

書き直し後（読者への影響の言葉）:

> - FSD のレイヤーに属さない場所にファイルを置くと CI が落ちるようになります。新しいファイルは所属レイヤーの中に置いてください
> - knip の誤検知を整理したので、今後出る未使用依存の警告はすべて本物です

## 提出前チェック

- 本文にファイルパス・件数・設定キーが残っていないか
- レビュワーが動作確認欄だけ見て手を動かせるか
- このチームの新人が読んで一発で分かるか
