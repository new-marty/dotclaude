# 良い UI とは何か、UI を作る人は何を考えるか(UI スキルのための調査)

UX の設計を終えた後に見た目と実装を担う UI スキルを作る前提で、良い UI の条件と、UI デザイナー・UI エンジニアが考えるべきことを調べた。あわせて、Marty が GoodLinks に保存した UI 関連のリンク 178 件から好みの傾向を読んだ。画面・フロー・状態の決め方は [z-design-ux](../../skills/z-design-ux/SKILL.md) の範囲なので、ここでは扱わない。詳細と出典は `notes/` の5本にあり、本文の各節の末尾にどのノートかを書く。

## 結論

良い UI は二層に分けて考えると扱える。下の層は「床」で、コントラスト 4.5:1、操作領域 24px 以上、キーボード操作、状態の網羅、動きを減らす設定への対応など、測って合否を決められる。上の層は「判断」で、誰がどの頻度で使うかという文脈と、先に決めた参照から導く。こぎそ氏の整理では、規則に沿って破綻がない「綺麗」は必要条件にすぎず、「使いやすい」は利用者と状況を決めて初めて測れる。

AI に UI を作らせると平均に収束する。既存のスキルは避けるべき見た目を名指しで禁じてきたが、禁止リストへの対処として配った処方がそのまま次の「AI っぽさ」になった(Anthropic の公式スキル自身が、いまの生成物はクリーム地にセリフ体とテラコッタ色に寄ると書いている)。したがって UI スキルに固定すべきなのは手順で、見た目の答えは書かない。文脈と参照を決める、目盛り(トークン)を先に決める、作る、床を機械で検査する、スクリーンショットを別の目で批評する、の順を飛ばさせない。z-design-ux と同じく「工程は固定し、答えは実行時に調べて決める」設計になる。

Marty の好みは保存物から5つ読み取れた。細部の作法を数値で守ること、説明文やラベルを足さずに減らすこと、動きは装飾でなく機能として使うこと、日本語の文字組を整えること、最後の判断は人が持つこと。どれも上の手順と矛盾せず、むしろ床と批評の基準として書き込める。

## Marty の保存物に表れた好み

保存は 2026年3月に別アプリから一括で取り込んだ 124 件と、その後に手で保存した 54 件に分かれる。手での保存は 10 月に 37 件と急増し、直近3か月の保存の4割は「AI に良い UI を作らせる」ためのスキルや論考だった。スターは1件、ハイライトは0件なので、好みは保存した対象の内容から読むしかない。強く表れた傾向は次のとおり(根拠の一覧は [01_goodlinks_taste.md](notes/01_goodlinks_taste.md))。

| 傾向 | 根拠になった保存物の例 |
|---|---|
| 細部の作法を、近似でなく正確な値で守る | jakub.kr「Details That Make Interfaces Feel Better」(同心円の角丸、`tabular-nums`、`text-wrap: balance`)、better-ui、lintapple |
| 説明文やラベルを減らし、操作と構造で伝える | stop-describing-ui、「ラベルは最後の手段」、Fluid Functionalism(アイコンだけに畳むサイドバーを作らない) |
| 動きは情報であり、イージングを選んで使う | emilkowalski/skills、transitions.dev、モーション・イージング辞典、kumagi「動きの引き出し」 |
| 余白はグルーピングという意味を持つ | 「余白の意味を考えてから UI 実装してくれ」「美しいUIを作るために」 |
| 日本語の文字組を整える | 池田泰延氏の「日本語を美しく表示するためのCSS」(`palt`、`word-break: auto-phrase`、`text-autospace`)、「とりあえず Noto Sans JP、考え直してみませんか」 |
| 綺麗と良いを分け、判断は人が持つ | こぎそ氏の note とスライド、マネーフォワードのデザインハーネス(複数案を別モデルに反論させ、人が決める)、カナリーの NestUI |
| AI っぽい UI を嫌い、検査と禁止則で抑える | impeccable、emilkowalski/skills(「エージェントは趣味が良くない」) |

保存物の技術は shadcn/ui、Tailwind、React/Next.js、Motion が中心で、プリミティブには Radix と Base UI が挙がる。一方で、特定の見た目の流派(グラスモーフィズム、ネオブルータリズムなど)を追う保存はなく、ギャラリーは多いが色調も分野も揃っていない。動きについては、バウンスを禁じる impeccable と、バウンスを辞典として並べる資料が混在しており、どちらを好むかはこのデータでは決められない。

## 良い UI の条件

古典の原則は言い方が違うだけで、同じ核に収まる。Nielsen の10ヒューリスティクスはシステムの状態を見せることと、本質でない情報を除くことを挙げ、Rams の10か条は「できるだけ少ないデザイン」と細部まで徹底することを挙げる。Apple の現行の HIG(Liquid Glass 以降)も、最重要のコンテンツを前に出し、色を控えめに使い、標準の配置に従うよう求める。

職人の側の書き手は、これを検査できる形に落としている。Refactoring UI は強調したいものを強めるより周りを弱めること、間隔と文字の大きさを有限の目盛りから選ぶことを説く。Rauno Freiberg と Emil Kowalski は動きを使用頻度と目的で決め、何度も使う操作やキーボード操作には動きを付けない。Linear は情報密度の高い製品で、要素を削るのではなく視覚的な重みを不均等に配って密度を扱う。

論争になっている点は、どれも文脈で答えが変わる。見た目が美しいと使いやすく感じられる効果(Kurosu と Kashimura、1995年)は追試で支持された研究もあるが、2019年の研究では SUS(標準的な使いやすさ質問票)の評価に美しさの影響は見られなかった。だから見た目の印象を使いやすさの根拠にはしない。表現を強める流れにも限界がある。Google は Material 3 Expressive の調査で、慣れた型を崩すと使いやすさが下がった例を自ら報告し、NN/g は iOS 26 の Liquid Glass について、動きと透過が操作を見えにくくしたと評価した。感動を生む表現は低頻度で戻せる場面に限って効き、一貫性の代わりにはならない。

熟練のデザイナーが画面を批評するとき、見る順はおおむね決まっている。主要な操作はどれか、目が最初にどこへ行くか、目を細めても主従とまとまりが残るか(スクイントテスト)、競合する要素を弱められるか、の順で、観察と推測を分けて伝える。ただし、公開された標準の採点表は見つからなかった。詳細は [02_what_is_good_ui.md](notes/02_what_is_good_ui.md)。

## デザイナーとエンジニアが考えること

見た目を作る側の仕事は、先に目盛りを決めることから始まる。間隔は 4px か 8px の刻み、色は OKLCH で定義した shadcn/ui 流の「背景と文字」の組、角丸は入れ子で外側が内側と余白の和になる、影は数段に限る。いずれも先に有限の値を決めて、以降はそこからしか選ばない。日本語は欧文の既定値をそのまま使えない。本文は行間 1.7〜2 で字詰めをせず、見出しにだけ `palt` と `word-break: auto-phrase` を使い、`font-family` は `system-ui` を避けて `sans-serif` で終える。動きは既定で付けず、付けるなら 300ms 未満の ease-out にして、`prefers-reduced-motion` を必ず見る。数値と出典の一覧は [03_visual_fundamentals.md](notes/03_visual_fundamentals.md) にある。

作る側の仕事は、ネイティブの HTML を壊さないこと、状態を全部作ること、測れる基準を守ることの三つに集約される。`div` をボタン代わりにしない、`outline: 0` でフォーカスを消さない、貼り付けを塞がない、`transition: all` を書かない、といった禁止は Vercel の Web Interface Guidelines にまとまっている。待ち時間は1秒未満なら何も出さず、2〜10秒はスケルトンかスピナー、10秒を超えたら進捗を出す。日本語のフォームでは全角と半角の両方を受け付けてサーバー側で揃え、電話番号と郵便番号を欄で分けない。表示速度の指標は INP 200ms 以下、CLS 0.1 以下、LCP 2.5秒以下が目安になる。

自動の検査で拾える範囲には限りがある。axe のようなツールが見つけるのはアクセシビリティの問題の約57%で(Deque の 2021年の数字)、キーボードでの操作順、読み上げ、文言の適切さは人が確かめるしかない。部品は Radix や React Aria、shadcn/ui のような既存のプリミティブを使い、操作の作り込みを再発明しない。チェックリストは [04_ui_engineering.md](notes/04_ui_engineering.md) にある。

## AI が作る UI の失敗と、既存スキルの対策

AI っぽさの典型は実務者の間でほぼ共有されている。紫や藍のグラデーション、どこでも Inter、同じアイコンのカードが3枚並ぶ構成、絵文字のアイコン、中央揃えのヒーローと見出し上の小さな大文字ラベル、そして最近の波としてクリーム地にセリフ体とテラコッタ色。ただし、出現頻度を測った一次の研究は見つからなかった。

公開されている UI スキル16件を読むと、対策は四つに集約される。題材から方向を導いて既定値の外に出る、既定値を名指しで禁じる、測れるものを検出器にする、スクリーンショットを見て直す。このうち名指しの禁止は即効性があるが、次の既定値を生む。最も進んだ検証は二段構えで、決定的な検出器と、コードも意図も渡さずスクリーンショットだけを見る別の批評者を組み合わせる(juliobsz の jury、impeccable の critique)。検出器の作者自身が、検査を通ることは品質の証明にならないと明記している。

個人やプロジェクトの好みを書く場所は、Google が仕様と lint を公開した DESIGN.md(色・文字・角丸・間隔の値と、その理由の散文)に寄りつつある。仕様はまだ alpha で、こぎそ氏が指摘するとおり Markdown には拘束力がない。守らせるのは型、lint、テストの役目になる。比較表とライセンスは [05_ai_ui_skills.md](notes/05_ai_ui_skills.md) にある。ライセンスはほとんどが MIT か Apache-2.0 だが、transitions.dev は再配布を禁じる独自ライセンスなので、発想の参照にとどめる。

## UI スキルの設計に持ち込むこと

調査から導いた設計の骨格を次に示す。どれも推論で、Marty との相談で変わりうる。

1. z-design-ux の引き渡し(画面、状態、利用場面)を入力にし、UI の段で新しい質問をなるべく増やさない。
2. 作る前に、製品の性格(業務の道具か、説得するページか、読み物か)と参照を決める。業務の道具では既知のパターンを正当とし、宣伝ページの「凡庸さを避ける」発想を持ち込まない。
3. 目盛り(トークン)を DESIGN.md か CSS 変数で先に書き出し、実装はそこからだけ値を選ぶ。既存のプロジェクトにトークンがあればそれを読む。
4. 床の検査をスクリプトで行う。コントラスト、操作領域、フォーカス、320px 幅、ダークモード、長い文字列や空の状態での崩れを見る。
5. 見た目の批評は、スクリーンショットだけを渡した別のエージェントに任せる。
6. 最後に「自動で確かめた」「人が確かめた」「確かめていない」を分けて報告する。

Marty の好みは、スキル本体から切り離して好みの文書に置くのが筋がよい。本体には誰にでも通る手順と床を書き、好み(細部の正確な値、説明文を削る、動きの採否、日本語の文字組の既定値)は差し替えられる層に置く。こうすれば好みが変わっても本体を書き換えずに済み、案件ごとの DESIGN.md が好みより優先される関係も明確になる。

決めてもらいたい点は三つある。好みの文書を dotclaude に置くか案件ごとに置くか、対象を Web(React/shadcn)に絞るか iOS などのネイティブも含めるか、動きについてバウンスやオーバーシュートを許すか。

## 調べきれなかったこと

- マネーフォワードのデザインハーネスの記事本体は取得を拒まれ、紹介文だけを根拠にした。
- Apple HIG の現行の原則ページ、Material 3 の動きの数値、Refactoring UI の本文、Norman や Fitts の原典は二次資料でしか確認していない。
- Emil Kowalski の動きの数値(300ms、押下時の 0.97 倍)は個人のブログが出典なので、既定値ではなく初期値として扱う。
- 日本語の UI に特有の AI っぽさや対策を扱った資料は見つからなかった。
