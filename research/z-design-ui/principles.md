# UI デザイン原則集(統合版)

UI を設計する agent が「この判断の理由は何か」を調べるための原則集である。研究ノート 15〜20(共有動画・YouTube 実務者・文章の正典・日本の実務・リデザイン事例)の原則を 1 項目 1 回に統合し、確定済みのノート 03・07・09・10・11(WCAG、NN/g の実測、デザインシステムの規定値)で実務者の数字を訂正・限定した。確度は 4 段: **実証あり**(規格・実験・計測に遡れる)/ **多数一致**(独立した 2 つ以上の実務者やデザインシステムが一致。実験はない)/ **一人の意見**(一人または一社の主張)/ **要確認**(字幕の聞き違い、二次要約、出典間の食い違い、ブラウザ対応の未確認を含む)。

読み方: 出典の括弧内の数字はノートの番号(例: Mizko(17))。該当のない欄は省く。値の単位は断りがなければ px。出典が割れる項目は「割れ」「既定」「選んだ理由」を書いた。末尾に既定値の早見表がある。調査者の推論(ノート内の【推論】)は確度を「要確認」とした。

## 1. 階層と強調

#### 1.1 強調は「目立たせる」より「周りを弱める」で作る
- なぜ: 注意は要素の性質でなく隣との差で決まる。全部を強くすると何も目立たない。既定を静かにして、差のあるものだけ強めるほうが少ない手数で済む。
- 値: 強調の手段は大きさ・太さ・色(+位置・背景)。重ねがけせず 1〜2 本に絞る。NN/g は対比の種類を 3 種までとする(11)。6 個のチップが全部青いと差がない。既定を灰色にし、選択だけ色づける(Kole K09)。
- 使わない場面: ページタイトルだけは全部強くしてよい(Kennedy)。
- 出典: Refactoring UI(18,20)、Kennedy(18)、Kole(16)、Showalter(16)、NN/g(11)
- 確度: 多数一致

#### 1.2 見せたい順に、大きさ・太さ・コントラストで差を付ける
- なぜ: 利用者が最初に見る場所を設計者が決める。差がないと脳が全部を同じ重さで処理して疲れる。
- 値: 見出し → 本文 → 補助の順に下げる。見出し 24 → 54px、medium → semibold の例(Showalter)。見出し:本文が 96:48 のように倍々(Flux)。NN/g は大きさの階層を小・中・大の 3 段まで、最大の要素は 2 つまでとする(10,11。経験則)。
- 使わない場面: 最小の要素でも余白とコントラストで焦点になりうる(ニューヨーカー誌の表紙の黒い球。Flux)。
- 出典: Kole K01・K02(16)、Showalter J1(16)、Waterworth(15)、Malewicz(17)、Flux(17)、NN/g(10,11)
- 確度: 多数一致

#### 1.3 先に「この画面のひとつの仕事」を 1 文で書き、要素を 3 層に分ける
- なぜ: 位置を決めながら層を決めると主役がぶれる。内容の優先順位を先に並べれば、配置の理由を「課題・頻度」で言える。
- 値: 第 1 層は 1 つ(最大スケール・最高コントラスト)、第 2 層は見出しや補助操作、第 3 層は弱めて見せる。2 文要る画面は分けるか、副次を第 2・第 3 層へ落とす。「機能から始める」例: 飛行機検索なら日付 2・出発/到着・検索ボタン(Refactoring UI)。
- 使わない場面: 監視や探索のように 1 画面に複数の仕事が並ぶことが設計の目的の画面(ダッシュボードは 8.9 を参照)。
- 出典: Priority guide(10)、NN/g(10)、Kole K02・Rachel How(15,16)、Refactoring UI(18)
- 確度: 多数一致

#### 1.4 重要度は操作の頻度で見積もる(ただし近似)
- なぜ: 最頻の操作を最重要とみなすと、弱める・隠す・消す対象が決まる。
- 値: Anki で 95/100 が「答えを見る」だった例で、UI 要素が 10 → 5 に(Kennedy の自作事例)。頻度と重要度は別軸(週 1 回でも契約は重要)。Top Tasks は利用者に重要度を投票させる(10)。
- 使わない場面: 危険な操作は頻度が低くても別扱い(目立たせず離す。9.13)。
- 出典: Kennedy K4(18)、McGovern(10)
- 確度: 一人の意見(Kennedy 自身が出発点でありユーザーテストが要ると断る)

#### 1.5 スクイントテスト(目を細める・ぼかす)で、最初に見えるものが最重要か確かめる
- なぜ: 細部に囚われず階層の崩れを見つけられる。例: 一番目立つのが夏時間の黄色い箱で、都市名と現地時刻より強かった(Learn UI)。灰色の主ボタン、目立つ「ヘルプ」リンクも同じ。
- 値: 5〜10px のぼかしで意図した階層が残り、20px で意図しない焦点が出た例(Spotify。NN/g)。対照実験はなく、注釈つきの例示にとどまる。
- 出典: Kennedy(18,20)、NN/g(10,11)
- 確度: 多数一致

#### 1.6 文字色は主・副・第三の 3 段に固定する
- なぜ: 太さや大きさを増やさずに階層が作れる。副次情報を薄くして主を目立たせる。
- 値: 主 = 濃、副 = 中灰、第三 = 薄灰。同じ 15px の文字で 2 行目だけ不透明度 55%(Kole K03)。薄くする下限は 4.5:1(6.8)。透明度で作った灰は背景次第で見え方が変わるので、固定パレットから選ぶ(Transistor 事例。20)。
- 出典: Refactoring UI(18)、Dannaway(18)、Kole K03(16)、Schoger(20)
- 確度: 多数一致

#### 1.7 主ボタンは 1 画面 1 つ。副・第三で段を付ける
- なぜ: 同じ重みのボタンが複数あると「どっちを押す?」で止まる。
- 値: 主 = 高コントラストの塗り+太字、副 = 枠線かやや弱い面、第三 = テキストリンク。例: ログインが主、登録は小さな文字リンク(Showalter J2)。
- 使わない場面: 最重要の操作がない画面は副・第三だけでよい。
- 出典: Dannaway(18)、Refactoring UI(18)、Kennedy K4(18)、Schoger(20)、Showalter J2(16)、Waterworth(15)
- 確度: 多数一致

#### 1.8 意味色より階層を先にする(危険 = 赤でも主操作でなければ目立たせない)
- なぜ: 成功は緑、危険は赤と色を分けると、画面の主従が壊れる。主操作でない破壊的操作が赤く目立つと誤操作を誘う。
- 値: 主操作 1 つに強い色、副は白か枠線、第三はテキストリンク(Schoger の SNS 再設計)。切断ボタンを副次・第三の見た目にし、タイトルから離して右端へ(Transistor)。
- 使わない場面: 確認モーダルの内側では、破壊的操作そのものが主役なので赤でよい(Refactoring UI。9.13)。
- 出典: Schoger(20)、Transistor 事例(20)、OJS 事例(20)
- 確度: 多数一致

#### 1.9 道具の枠(上部バー・ロゴ・サイドバー・挨拶)を静かにし、中身を主役にする
- なぜ: 利用者が使うのは中身。最初に目に入るのが枠の色や大きなバーなら、強調の場所を間違えている。
- 値: ダッシュボードのロゴの箱と挨拶、ログアウト欄を小さくする(Showalter J2)。青いサイドバーが一覧表より目立つ → 彩度を下げる(Spike.sh)。クレジットカード画像のような「見た目だけの大きな要素」は外して口座情報にする(Malewicz #6)。
- 使わない場面: 道具でなく LP や公式サイトはブランドを前に出してよい(J2)。
- 出典: Showalter J2(16)、Spike.sh(20)、Malewicz(17)
- 確度: 多数一致

#### 1.10 ラベルは最後の手段にする(自明なら削り、残すなら小さく薄く)
- なぜ: 「ラベル: 値」は全データを同じ強さにして階層が作れない。形式で意味が分かるデータ(メール・電話・価格)は値だけで足りる。
- 値: 「在庫: 12」→「残り在庫 12 個」、「ベッドルーム: 3」→「3 ベッドルーム」。残すなら小さく・薄く・細く(併用可)。値が埋もれるなら値を大きく、ラベルを小さく・薄く(Schoger)。
- 使わない場面: 仕様表のように利用者がラベルを探す画面は、ラベルを濃く値を少し薄くする。入力欄とチャートの軸はラベル必須。スクリーンリーダー向けのラベルは視覚的に隠して残す【推論】。
- 割れ: NN/g と Bokardo は「ラベルは常に勝つ」(アイコンに常設ラベル。11.4)。既定: 操作(ボタン・ナビ)はラベルを残し、繰り返し現れる補助情報とデータ項目から削る。理由: 対立は対象の違いで解ける(03)。
- 出典: Refactoring UI(18,19,20)、photoshopvip(19)、NN/g(03)
- 確度: 多数一致(操作系ラベルの扱いは割れ)

#### 1.11 表示する内容を先に決める。一覧は判断に要る情報だけ、詳細は詳細で
- なぜ: 内容が先で見た目は後。削る基準が「デザイナーの都合」だと必要な情報まで消えて自己満足になる。基準は「誰が何のために使うか」。
- 値: 宿の一覧は場所・評価・価格だけ(Kole K02)。物件一覧は優先度の低い情報を詳細へ移し、自明な項目名を削り、設備の有無はアイコンにする(9re-pe。19)。ただしアイコンが初見で伝わるか確かめる(S/M/L と合わず失敗した例)。
- 出典: Kole K02(15,16)、9re-pe(19)、NN/g 複雑アプリ(07)
- 確度: 多数一致

#### 1.12 複雑な機能は削らず、段階的開示で制御する
- なぜ: B2B では複雑さが仕事そのもので、削ると機能が壊れる。整った UI は「複雑さを制御できている」証拠になり信頼に変わる(コックピットの比喩)。
- 値: NN/g は「機能を減らさず散らかりを減らす」。詳細は段階的に開く。メール文面と UI の見直しで CV が 20% 上がったという話は一次未確認。
- 出典: inofthefor(19)、NN/g 複雑アプリ(07)
- 確度: 一人の意見

#### 1.13 低頻度の操作ほど表示を弱める(明示度の幅)
- なぜ: 常時表示は画面を重くする。操作の重さに応じて、常時ボタン → ラベルなしアイコン → hover で出る → ポップオーバーの順に明示度を下げる。
- 値: 追加は全員が使うので見える場所(半透明 50% でも)。削除はまれなので hover 時のみ+tooltip(Kole K04、Learn UI)。共有はポップオーバーにして中の最重要は検索欄。
- 使わない場面: 主要操作は隠さない。隠すなら「探し始めた瞬間に出る」。タッチには hover がない(9.18)。
- 出典: Kole K04(16)、Learn UI 事例(20)
- 確度: 多数一致

#### 1.14 状況(初回・再訪・常連)で画面の主役を入れ替える
- なぜ: 初回向けの案内を毎回見せると、常連には無駄な面積になる。
- 値: Uber Eats は初回がカテゴリ検索、再訪が「再注文」、常連が「いつものメニューと代替案」(Mizko #3)。
- 使わない場面: 利用データがない新規サービスは初回向けを優先する。
- 出典: Mizko(17)
- 確度: 一人の意見

## 2. 余白とまとまり

#### 2.1 近いものは関係があるように見える。間隔は関係の強さに比例させる
- なぜ: 近接は関係の最強の手がかり(ゲシュタルト)。余白は区切りでなくグルーピングの記号。関係のないものが近いと所属が曖昧になる(社員紹介で役職名が 2 枚の写真の中間にある例。9re-pe)。
- 値: グループ内 < グループ間。LP の文字ブロックで見出しと小見出し 8、アイブロウ 12、ボタン 32(Kole K03)。タイトルとコンテンツ 8pt、セクション境界 20pt、コンテンツ同士 4pt(ktcryomm)。DADS の例は 8 / 24 / 64(1× / 3× / 8×)。キャプションは画像に近づけ、本文と離す。
- 使わない場面: ブロック間を広げるのは「別の機能」と見せたいとき。原則の破りでなく、別の層の話(Mizko #2)。
- 出典: Kole(16)、Showalter(16)、Waterworth(15)、Mizko(17)、DADS(07,11)、NN/g(07)、ktcryomm(19)
- 確度: 実証あり(ゲシュタルトは知覚心理学の古典。03 の法則表で「強い」)。具体値は多数一致

#### 2.2 入れ子では、外側の余白 ≥ 内側の間隔にする
- なぜ: コンテナの端より内側の要素同士が近いほうが、グルーピングが保たれる。
- 値: 外枠 16 に対し内側 8 や 4(Mizko)。サイドバーは外側 20、ブロック間 40、ブロック内 12、タイトル周り 8 と深いほど小さく。カード内 12 か 16、カード間・外側 24 か 32(Malewicz #5)。カード外側 20・内側 16(同 #11)。
- 使わない場面: 一次資料(規格・DS)でこの不等式を明文化したものは見つからなかった(11)。DADS の近接規則からの導出。
- 出典: Mizko(17)、Malewicz(17)、Hobday #19(18)、DADS(11)
- 確度: 多数一致(実務者間のみ)

#### 2.3 余白は「多めに始めて削る」。詰めすぎは初心者の印
- なぜ: 既定の HTML は詰まっている。後から足す発想では足りない。余白がないと組が見えず、要素が競う。
- 値: メニュー項目は文字高の約 2 倍(12px 文字+上下 12px)、見出しと下線の隙間約 15px、リスト間約 25px(Kennedy の音楽プレイヤー事例)。モバイルは思うより余白が要る(Kole K05)。
- 使わない場面: 高密度の業務画面(2.12)。機能を削ってまで余白を取る再設計は教材であって本番の手本ではない(Kennedy 自身の注)。
- 出典: Kennedy(18,20)、Refactoring UI(18)、Waterworth(15)、Kole K05(16)
- 確度: 多数一致

#### 2.4 余白は少数の値だけを使う(8 の倍数、微調整に 4)
- なぜ: 値が少ないと整って見え、実装者も迷わない。不揃いな余白は「何が悪いか分からないが雑」に見える。
- 値: DADS は基準 8px・3〜5 段(例 8 / 24 / 64)。Carbon は 2・4・8 の倍数(2 / 4 / 8 / 12 / 16 / 24 / 32 / 40 / 48 / 64 / 80 / 96 / 160)。SmartHR は 0 / 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64。Material は 8dp、アイコンと文字は 4dp。
- 割れ: Mizko は 4 の倍数なら何でも(理由は「いつでも半分に割れるから」で、見栄えではない)。Malewicz・Flux は 8pt を基本に最小 4・8。既定: 8 の倍数を基本、微調整に 4。理由: 主要な DS(DADS・Carbon・SmartHR・Material)が 8 基準で、Mizko の 4 の倍数とも矛盾しない。
- 使わない場面: アイコン周りの意図的な微調整、タブバーの 10px 文字など(Malewicz)。
- 出典: DADS・Carbon・SmartHR(11,19)、Material(03)、Mizko・Malewicz・Flux(17)、Kole K01(16)
- 確度: 多数一致。なぜ 8 か(画面密度で割り切れる)は通説で、DADS・Carbon・SmartHR は理由を書いていない(要確認)

#### 2.5 区切りは余白 → 薄い線 → 背景 → 枠・帯の順に強い手段へ。必要になるまで強い手段を使わない
- なぜ: 「念のため」の枠は散らかりを生む。明確な境界は近接に勝つ強い手がかりなので、使うのは必要なときだけ。
- 値: DADS の区切り線はリストで余白 8px 以上、セクションで 16px 以上。「区切り線がなければ伝わらない構成は避ける」。枠を足す前の問い: 理解に必要か / 余白で足りないか / 枠なしで利用者が困ったか(NN/g)。区切りの 3 択は余白・線・色(Kole K15)。
- 使わない場面: 異種の要素を 1 つにまとめる、クロームとコンテンツを分ける(ヘッダ・サイドバー・ドロワー)ときは背景か枠が適する。
- 出典: NN/g 共通領域(07)、DADS(07)、Refactoring UI(07)、Kole K15(16)
- 確度: 多数一致。余白と線の読み取り速度を比べた実験は見つからなかった

#### 2.6 カードを入れ子にしない。外側の枠は 1 つ
- なぜ: 枠の上の枠、角丸の重なりは構造を増やさない。1 行の線でカードをなくし、列の端がカードの辺の働きをする。
- 出典: Kole K09・K15(16)
- 確度: 一人の意見

#### 2.7 フォームは「グループ間 > グループ内」で束ね、ラベルは自分の入力に寄せる
- なぜ: 15 項目を 4〜6 項目の 3 グループに分けると「3 つの短いフォーム」のように感じられる(Walgreens の例。測定値ではない)。ラベルが上の入力と下の入力のどちらのものか分かるようにする。
- 値: グループ内 8〜16・グループ間 24〜32【推論】。入力高 40px のとき、ラベルとの間隔を入力高の約半分(資料の記載は 24px。数値の整合は要確認)(Resolute 事例)。
- 出典: NN/g フォーム(07)、DADS(07)、Resolute 事例(20)
- 確度: 多数一致

#### 2.8 余白で優先順位を示し、罫線やアイコンを減らす
- なぜ: 余白が関係を示せるなら、飾りの線は要らない。重要なものにより多くの余白を与えて目立たせる。
- 値: Flux の修正例は飾りの罫線をすべて外し、12 カラムと 8px 倍数の余白に置き換えた。
- 出典: Flux(17)、NN/g(10)
- 確度: 多数一致

#### 2.9 余白が多い = 高級だが、空ければ高級になるわけではない
- なぜ: 空間は富の記号で、商品を少数に絞り間を空けると高級に見え、詰めると安売りに見える。使い方を誤ると「高級」でなく「空っぽ」になる。
- 使わない場面: 商品が多い小売りや、情報量が命の画面。
- 出典: Flux #17(17)
- 確度: 一人の意見

#### 2.10 間隔は高コントラストの縁から縁で測る
- なぜ: 目は文字や図形の輪郭で縁を捉える。行ボックスの余白は見えない。Figma のボックス端基準は見かけとずれる。
- 値: テキストの上下はグリフ(x 高・cap 高)基準で合わせる【推論】。日本語は 5.9。
- 出典: Hobday #14(18)
- 確度: 一人の意見

#### 2.11 数値の中央でなく視覚の中央に置く
- なぜ: 上方距離過大の錯視で、数値上の上下中央に置くと下にずれて見える。左右も、文字を詰めたブロックは写真より重く見え、重心が外へ寄る。
- 値: Ameba 20 周年サイトで上 317px・下 295px の差を調整した例(ライブ取得の数値。画像は未確認)。
- 使わない場面: 機械的に揃えるべきグリッドや表。
- 出典: 原(19)
- 確度: 要確認

#### 2.12 密度は文脈で選び、余白でなく行高と部品の高さで切り替える
- なぜ: 業務の毎日使う画面と、読ませる画面で最適が違う。余白を詰めると近接の手がかりが壊れる。
- 値: DADS の Dense は 14 / 16 / 17px・行高 120% または 130%・字間 0、Standard は 16px・170%。Carbon の表の行高は 24 / 32 / 40 / 48 / 64(64 は 1 セルに 2 行入るときだけ)。Material は密度 1 段で部品の高さ 4dp 減、パディングは変えない。密度の切替は表の外に置き、選択を保存する(Pencil & Paper【弱】)。
- 使わない場面: 「日本のサイトは情報が多いと安心する」を理由に密度を上げない。これは筆者の仮説で、実証研究は見つからなかった(19)。
- 出典: DADS・Carbon(07)、Material(11)、Pencil & Paper(07)
- 確度: 多数一致

#### 2.13 不揃いな幅の要素は最大幅にそろえる
- なぜ: 間隔が同じでも幅が違うと不揃いに見える。
- 出典: Raptis(18)
- 確度: 要確認(図解のみで根拠の説明がない)

## 3. 揃えとグリッド

#### 3.1 すべての要素を何か別の要素と揃える。揃えの種類は最小に
- なぜ: 揃えは関係の証。揃っていないものは属していないように見える。見えない軸ができると、斜めに置いても秩序が残る。
- 値: 小さな UI(チャット欄・かんばんカード・サイドバー)は、各要素が 2 本以上の辺に触れる(Kole K09、意訳)。左・右・中央を混ぜない。
- 使わない場面: 全部を幅いっぱいに広げても読みやすくはならない。量が多いなら日付などで組にする(K09)。
- 出典: Hobday #8(18)、Dannaway #8(18)、Showalter J1(16)、Kole K09(16)
- 確度: 多数一致

#### 3.2 左揃えを基本にする。中央揃えは 3 行未満の短文だけ
- なぜ: 左揃えは文頭が揃って読みやすい。中央揃えは行頭が揃わない。
- 値: 中央は 3 行未満(Kennedy K100 #22)。Refactoring UI は 2〜3 行を超えたら左。日本語の中央揃えは `text-wrap: balance` と組み合わせる(5.3)。
- 出典: Kennedy(18)、Refactoring UI(18)、Dannaway #15(18)、desaken(19)
- 確度: 多数一致

#### 3.3 数値は右揃え、文字は左。見出しは列の内容に揃える
- なぜ: 桁の比較は一の位から始まるので、右端と小数点位置がそろうと大小が見える。中央揃えは行端が揃わず、区切り線が要る。
- 値: `tabular-nums`+右揃え+小数桁を列内で統一。単位は列に 1 回(Ström)。郵便番号・日付・電話のような識別子は左でもよい。
- 出典: Ström(10)、SmartHR(19)、Refactoring UI(18)、Pencil & Paper(07)、MDN(07)、Kole K04(16)
- 確度: 多数一致(tabular の読みやすさを測った実験は見つからなかった)

#### 3.4 項目名・必須マーク・入力欄を一本の線に揃える
- なぜ: 揃っていないと散らかり、カーソルの開始位置も毎回ずれる。
- 値: 左揃え。入力欄の右端もできる限り揃える。中央揃えは上級者向け(9re-pe)。Web フォームの主ボタンは入力欄の左端に揃えるという主張もある(Silver。8.16)。
- 出典: 9re-pe(19)、Silver(10)
- 確度: 一人の意見

#### 3.5 アイコンや記号は本文の外へぶら下げ、本文を字下げして走査線を作る
- なぜ: 左揃え文章の右側は行末が揃わない。アイコン・箇条書き記号は文字より軽いので、本文の左端の外に出す。
- 値: アイコンの右にテキストを揃える(アイコンは円に入れて大きく見せる)。結果として上の罫線や各カードの区切りが不要になり、余白を増やしたのに縦の高さは減った(SneakedIn 事例)。
- 出典: Kennedy KA・K100 #10(18)、Schoger(20)、Transistor 事例(20)
- 確度: 多数一致

#### 3.6 重い側が「主」か「枠」かを説明できるようにする(視覚的な重み)
- なぜ: バランスは等しく配分されるが対称とは限らない。大きなテキストの塊が反対側の小さな要素の群れと釣り合う。重い側が主役なのか枠なのかを言えない配置は、置き直す。
- 値: 重いものを先頭・外縁に、軽いものを後ろに(Hobday #12)。ただし根拠は美的判断で、バランスを実験した資料は見つからなかった。
- 出典: NN/g(10)、Hobday(18)
- 確度: 要確認

#### 3.7 列グリッドは、横に並べる部品が多い画面で使う。整列の軸は全画面で決める
- なぜ: 揃えること自体は両陣営で一致する。列数の事前決定は画面の種類で効き方が違う。
- 割れ: Hobday は 12 列(1・2・3・4 に割れる)。Kennedy は初心者に不要とする(320px で 12 列だと 1 列約 26px でタップ下限を割る。内容に幅を決めさせ、左 16・中央・右 16 のガイド 3 本で足りる)。Kole は 12 列や 8px 間隔に全部合わせなくてよい(LP は列に乗らない配置も多く、ギャラリー・ブログ・繰り返しの一覧ではタブレット 8 列・モバイル 4 列の目安が役立つ)。既定: 軸(左端・右端・中央)は必ず決め、列数はカード・ダッシュボードのような横分割の多い画面だけで決める。理由: 両者が共通して「揃える」を求め、モバイル幅では 12 列が成立しないため。
- 出典: Hobday #13(18)、Kennedy KD・K100(18)、Kole K01・K05(16)
- 確度: 一人の意見どうしの対立(整列そのものは多数一致)

#### 3.8 ブレークポイントごとに列数・マージン・ガターを決め直す
- なぜ: 画面幅で並びが変わるので、列と余白も幅ごとに設計し直す。
- 値: Mizko が Dribbble を実測した例: 最小 320、約 630 で 2 列、約 960 で 3 列。モバイルは 4 列・マージン 16・ガター 8、630 は 4 列・マージン 16・ガター 32、768 超は 12 列・マージン 24・ガター 32、広い画面はマージン 80・ガター 40。値は 4 の倍数で目で合わせたもので、厳密な規則はないと本人が言う。
- 出典: Mizko #4(17)
- 確度: 要確認(自動字幕。前半のみ読了)

#### 3.9 固定幅の領域は列グリッドの外に置く。グリッドを崩すときは理由を書く
- なぜ: 幅が変わると中身の折り返しが変わる。
- 値: Material の list-detail はリストが固定幅、詳細が可変。幅が狭い画面では副次内容をボトムシートやサイドシートへ。崩してよい条件: (a)固定幅の領域、(b)主役を強調するために意図して外す、(c)アイコンなどの視覚補正。理由が書けない崩しは戻す【推論】。
- 出典: Material(10)、Refactoring UI(18。本文は未取得)
- 確度: 要確認

#### 3.10 コンテンツの最大幅を決める(全幅にしない)
- なぜ: 入力欄や行が長すぎると、読み幅と期待が狂う。
- 値: フォームの中央部を最大 960px にし、ラベルを左 1/3・入力を右 2/3 の 2 カラムにしてラベル側に説明を置く(Resolute)。共有テンプレートの幅 1127px → 960〜1024px(Transistor)。サイドバーは固定幅(Refactoring UI)。
- 出典: Resolute・Transistor 事例(20)、Refactoring UI(18)
- 確度: 一人の意見(Schoger の事例。効果の数値はない)

## 4. 文字(サイズ・太さ・行間・字間)

#### 4.1 書体は 1 つ(サンセリフ)。2 つ目は理由があるときだけ
- なぜ: 見た目は書体より階層と余白で決まる。種類が多いと脳の処理が重くなり、初心者はペアリングで失敗する。
- 値: 4 書体 → 1 書体(Waterworth)。Malewicz は Level 1 が書体 7 つ、Level 4 以上が 1 つ。
- 割れ: Dannaway は 1、Hobday は最大 2、Kennedy は役割に応じて足す。Linear は見出しだけ Inter Display。既定: 1。個性や雰囲気が目的のときだけ 2(高級感のためにヴィラ予約で別書体を選んだ例。Rachel How)。
- 出典: Kole K01(16)、Waterworth(15,16)、Malewicz(17)、Hobday・Dannaway・Kennedy(18)
- 確度: 多数一致

#### 4.2 2 書体にするなら、本文書体を可読性で先に決め、足りない性格だけを 2 つ目で補う
- なぜ: 見た目の性格から書体を選ぶと、本文の可読性が後回しになる。
- 値: ブランドの形容詞を 2〜3 個 → 本文書体を可読性で決める(x 高が高く字間が広い)→ 足りない性格を 2 つ目で補う(セリフ × サンセリフが基本)→ 役割ごとの使い方(太さ・大小文字・斜体・色)を書く(Kennedy KF)。書体を替えたらサイズと太さも調整し直す(WP Pusher: Raleway → Gotham)。
- 出典: Kennedy KF(18)、Schoger(20)
- 確度: 一人の意見

#### 4.3 1 画面で見える文字サイズは 3〜4 種に絞る。ただしスケール表は持ってよい
- なぜ: 同時に見える階層の数で決まる【推論】。種類が多いと階層の差が読めない。
- 値: Malewicz は最小 12、次に 14 か 16、20、最大 24(LP は各値に +4〜8、タブバーの 10px のみ例外)。Kole は LP が 6 段まで、ダッシュボードは 24px を超える文字を普通使わない。NN/g の web 目安は本文 14〜16、小見出し 18〜22、見出し最大 32(経験則)。
- 割れ: Mizko はラベル 10 / 12 / 14 / 16、段落 12 / 14 / 16 / 18、見出し 18 / 20 / 24 / 28 / 32 / 36 〜 52 の表を持ち、2px 刻みで基準 16。実案件は 16 を基準に ±2〜4 で足りるとも言う。既定: 画面で同時に出すのは 3〜4 種。表を持つこと自体は構わない。
- 出典: Malewicz(17)、Mizko(17)、Kole K01・K15(16)、NN/g(11)
- 確度: 多数一致

#### 4.4 型スケールは「比で候補を出し、画面で丸める」
- なぜ: 比は示唆で、数学は経験ある目の代わりにならない(Tim Brown 本人)。実際の製品の表は一定比でなく、本文付近は 1〜2px 刻み、見出し側は大きく跳ぶ。
- 値: 比は 1.125〜1.333(Utopia は 320px で 1.2、1500px で 1.333 を決めて補間)。例: Tailwind 12 / 14 / 16 / 18 / 20 / 24 / 30 / 36 / 48 / 60 / 72 / 96 / 128。Refactoring UI 12 / 14 / 16 / 18 / 20 / 24 / 30 / 36 / 48 / 60 / 72。Carbon は 12 起点で増分が 2 → 4 → 6… と増える式。Apple は 11 / 12 / 13 / 15 / 16 / 17 / 20 / 22 / 28 / 34pt。数列外の値は計算メモをコメントに残す。
- 割れ: Raptis は ×1.25 を例示(40 → 32px)。Kennedy は「比を当てても悪いデザインは悪い」として段の区別だけ守る。本文付近の比の幅は Apple 1.06〜1.18、見出しは 1.27〜1.33(計算。11)。
- 出典: Brown・Utopia・Carbon・Tailwind・Apple(11)、Raptis・Kennedy(18)
- 確度: 多数一致

#### 4.5 本文の基準サイズを 1 つ決める。日本語は 16px、業務の密な画面は 14px まで
- なぜ: すべての段の起点になる。下限は公的な規定と画面の密度で決まる。
- 値: DADS は本文・UI の基準を 16 CSS px 以上とし、14px 未満は原則許容しない(14px は付随情報や領域制約のみ)。Dense は 14 / 16 / 17px。SmartHR は基準 16(XS 12 / S 13.71 / M 16 / L 19.2)で、段落では S・XS を積極的に使わない。欧文は Carbon productive が本文 14/20 とラベル 12/16、Fluent が 14/20、M3 が body-large 16/24、GOV.UK が 19/25 と 16/20(14px 以下を廃止)、Apple が iOS 17pt・最小 11pt。補足・脚注は日本語 14px、欧文 12px が下限。
- 割れ: ラベルは DADS Dense なら 14px、SmartHR なら 16px。判断軸は密度(19)。
- 使わない場面: 日本語の読み物は 16〜18px・行高 1.7〜1.75(07)。LP は expressive で本文 16 以上。
- 出典: DADS・SmartHR・Carbon・Fluent・M3・Apple・GOV.UK(07,19)
- 確度: 多数一致(公的 DS の規定。14px 以下を避ける根拠は GOV.UK の利用者の声とディスレクシア協会の指針)

#### 4.6 行間は欧文本文 1.5、日本語本文 1.7。大きい文字ほど詰める
- なぜ: 大きい文字は同じ比率でも空きが多く見える。行長が長いほど行間を広げる。
- 値: 欧文本文 16px/1.5(1.5〜2。Hobday・Schoger・Dannaway・Kennedy)、見出し 1〜1.25(Kole は 110〜120%)。Tailwind は 16px で 1.5、24px で 1.33、36px で 1.11、48px 以上で 1。日本語は DADS が 16px/170%、18px/160%、20〜32px/150%、36〜45px/140%。SmartHR は段落 1.5・見出し 1.25・ラベル 1。tak-dcxi は日本語本文 1.7〜2、見出し 1.25〜1.5。JLReq の行間は 0.5〜1 字で、行送りにすると 1.5〜2.0 倍【推論】(DADS の 170% は行間 0.7 字)。
- 使わない場面: `line-height: 1` は折り返しで崩れるので、1 行のボタン・ラベル(DADS Oneline 100%、SmartHR ラベル 1)だけ。DADS の Dense(120〜130%)と見出し 140% は JLReq の下限 0.5 字を下回る。JLReq は印刷の本文が対象で画面の文字サイズは範囲外。
- 出典: DADS・SmartHR(07,11)、tak-dcxi・JLReq(11,19)、Kole K01(16)、Tailwind(11)
- 確度: 多数一致

#### 4.7 大きい文字は字間と行間を詰め、小さい文字は開く
- なぜ: 大きいほど字間が広く見え、小さいほど空きが足りなくなる光学補正。単位は em で持つ。
- 値: Kole は見出しの字間 -2〜-3%。Flux は見出し -3、カラム見出し -2(単位は字幕上不明で要確認)。Inter の式 tracking = -0.0223 + 0.185·e^(-0.1745·px) em(16px で -0.011em、32px で -0.022em、11px で +0.005em)。Apple SF は 17pt で最も詰め(-26/1000em)、12pt で 0、6pt で +41。M3 は body-large +0.5px、display-large -0.25px。大文字の短いラベルには字間を足す(Hobday #6)。
- 使わない場面: 日本語本文は 5.1。
- 出典: Kole K01(16)、Flux #18(17)、Inter・Apple・M3・Carbon・DADS(11)、Hobday(18)
- 確度: 多数一致(Apple・Inter は設計値)

#### 4.8 小さい文字は重く、大きい文字は軽く見せる(見かけの太さをそろえる)
- なぜ: 大きい文字は同じウェイトでも太く見える。小さいサイズで細いウェイトは読めない。
- 値: Carbon の大見出し(54px)は Light 300、heading-03〜05 は Regular 400。Apple は Ultralight / Thin / Light を小さい字で避ける。ダークでは小さい文字ほど不利なので、細い字を避ける(6.16)。
- 使わない場面: ブランド表現の見出し。
- 出典: Hobday #6(18)、Schoger #8(18)、Carbon・Apple(07,11)
- 確度: 多数一致

#### 4.9 太さは 2〜3 水準(Regular と Bold、必要なら Semibold)に絞る
- なぜ: 水準が多いと階層の差が読めない。細い・極太は大見出しだけに向く。
- 値: DADS は N(400)と B(700)の 2 水準だけ。Apple の強調の既定は Semibold。Butterick は太字とイタリックを併用せず、semibold は bold より読みやすいが対比は弱い。
- 割れ: Refactoring UI は 5 つ以上のウェイトを持つ書体を選べと言う。既定: 書体は幅広いものを選び、使うのは 2〜3 種。
- 出典: Dannaway(18)、Kennedy K2(18)、DADS・Apple・Butterick(11)
- 確度: 多数一致

#### 4.10 強調の道具は 1〜2 本。同階層は太さ、階層をまたぐ比較は大きさ、状態は色
- なぜ: 1 要素に 3 つ重ねると、何が強調か分からない。
- 値: 太字は軽い・標準の文章に対して目立つ。二次情報は小さくするより色を薄くするほうが読みやすさを損なわない(Refactoring UI の二次要約)。
- 出典: NN/g・Butterick(11)
- 確度: 要確認(使い分けは調査者の推論)

#### 4.11 大文字は長文で避け、短いラベルだけ字間を広げて使う
- なぜ: 大文字は語の形が長方形になり読みにくい。字形の差が少ないので、字間で補う。
- 値: 投票数のラベルを大文字+字間(Bad About)。ナビの区分見出しはリンクより小さく薄く、大文字+字間(Schoger)。
- 割れ: Dannaway は避ける、Hobday・Schoger は字間つきで使う。既定: 長文は避け、短いラベルだけ字間つき。日本語に大小の区別はない。
- 出典: Dannaway #12(18)、Hobday #6(18)、Schoger(20)
- 確度: 多数一致

#### 4.12 数字は用途で選ぶ: 比べる・更新される数字は tabular、文中はプロポーショナル、コードと ID は等幅
- なぜ: tabular は桁幅がそろい縦に比べやすい。更新される数字は桁が揺れてレイアウトが動く。プロポーショナルは文中の間隔が均等に見える。
- 値: `font-variant-numeric: tabular-nums`(フォントが tnum を持つときだけ有効。Inter・IBM Plex・SF は対応、Noto Sans JP は未確認)。コード・ID・ハッシュは等幅+`slashed-zero`。通貨の小数桁は 0 か 2 に統一(Vercel)。日本語 UI の数字には、tnum を持つ欧文フォントを先に指定する(`"Inter", "Noto Sans JP", sans-serif` の順)【推論】。
- 使わない場面: 大きな装飾数字(時計など)はプロポーショナルでもよいが、更新で揺れるなら tabular。
- 出典: MDN・Butterick・Apple・Vercel(07)
- 確度: 多数一致(tabular が読み取りを速める実験は見つからなかった)

#### 4.13 ヒーロー数字は型スケールの最上段近くから選び、倍率を根拠にしない
- なぜ: 別系統で決めると階層が壊れる。比は結果として書く。
- 値: 値を大きく、通貨と期間は小さく(WP Pusher)。大きい数字は Light・字間を詰める(Carbon fluid-display、60・92px で -0.64px)。「36〜72pt、主数字はラベルの 2〜3 倍」という KPI 記事の経験則は弱い。最大の要素は 2 つまで。
- 出典: Carbon・NN/g(11)、WP Pusher(20)
- 確度: 要確認

#### 4.14 本文の行長は欧文で約 40〜80 字、日本語は 40 字前後
- なぜ: 行が長いと次の行頭を探しにくい。日本語は欧文の約半分の字数が目安。
- 値: Hobday 約 70(60〜80)、Practical UI 40〜80、Kennedy 50〜75、Refactoring UI 45〜75、Raptis 500〜700px か `ch` で上限。WCAG 1.4.8(AAA)は 80 字、CJK は 40 字。JLReq は横組み最大 40 字。「35〜45 字」を挙げるブログは出典不明。日本語 UI の本文は `max-width: 40em` 前後【推論】。
- 出典: Hobday・Practical UI・Kennedy・Raptis(18)、WCAG・JLReq(03,11)
- 確度: 実証あり(日本語 40 字は規格・組版仕様)、欧文の幅は多数一致

#### 4.15 `text-align: justify` を使わない。片側揃えにする
- なぜ: 川(rivers)と不均一な語間を生む。日本語でも英語混在で崩れる。
- 出典: WCAG 理解文書(03)、tak-dcxi(19)
- 確度: 実証あり

#### 4.16 リンクは文字の見た目で区別する。青リンクだらけにしない
- なぜ: プレースホルダーや見出しと同じ見た目だとリンクと気づけない。色だけに頼らない(6.9)。
- 値: 大文字・不透明度・下線で扱いを分ける(Showalter J2)。青リンクだらけなら濃い太字(YouTube・Medium・Airbnb 式。Schoger)。リンクが多い UI では太さ・色・ホバー下線で控えめに(Refactoring UI)。DADS はリンクの青と紫が色覚で見分けにくいとして、紫に赤みを足し明度差をつけた。
- 出典: Showalter J2(16)、Schoger(20)、Refactoring UI(18)、DADS(09)
- 確度: 多数一致

#### 4.17 ユーザーが文字間隔を変えても壊れない作りにする
- なぜ: 低視力の利用者がスタイルを上書きする。固定高さは崩れる。
- 値: WCAG 1.4.12 は行間 1.5 倍、段落後 2 倍、字間 0.12em、語間 0.16em に上書きしても壊れないこと。1.4.4 の 200% 拡大、1.4.10 の 320 CSS px 幅リフロー(2 次元スクロールなし)。文字サイズを vw だけで決めるとズームで大きくならない(rem と併用。Roselli)。
- 出典: WCAG(03,19)、Smashing 経由 Roselli(11【弱】)
- 確度: 実証あり(規格)

#### 4.18 混在サイズの文字はベースラインで揃える
- なぜ: 中央揃えだとサイズ違いの文字の底がずれる。
- 出典: Refactoring UI(18。二次要約)
- 確度: 要確認

## 5. 日本語の文字組と文言

ブラウザ対応の版数は、ノート 19 が報告値を転記したもので Can I Use で未確認。実装前に必ず確かめる。ボタンや操作語の文言は 13 章にある。

#### 5.1 日本語の本文はベタ組み。本文に字間・`palt`・`font-kerning` を入れない
- なぜ: 日本語は印刷でも字間ゼロのベタ組みが基本で、アキ組み・詰め組みは見出しとキャプション用(JLReq)。本文の `palt` は影響が大きい。
- 値: tak-dcxi は `font-kerning` を本文で `none`、見出しとキャプションで `normal`、`palt` は見出しのみ。
- 割れ: DADS は 26px 以下の字間を 2%、28〜36px を 1%、45px を 0 とし、2% を足す理由を書いていない(JLReq のベタ組みとずれる)。既定: 本文 0。DADS 準拠(公共系)の案件は DADS の値に従う。理由: ベタ組みは組版仕様に根拠があり、2% には説明がない。画面は印刷より粗いからという説明はどこにもない【推論】。`kern` と `palt` の併用や Firefox の `kern` 無効など、ブラウザ差の議論が続いている。
- 出典: JLReq(11,19)、tak-dcxi(19)、ICS MEDIA(19)、DADS(11)
- 確度: 一人の意見(組版仕様は実証に近いが画面は範囲外)。DADS の 2% は要確認

#### 5.2 見出しだけ `palt` を使う
- なぜ: 見出しの文字間を締めて視覚のまとまりを作る。本文では詰めすぎる。
- 値: `font-feature-settings: "palt"`。フォントが対応している必要がある(ヒラギノ角ゴ・游ゴシック・Noto Sans CJK JP は対応、メイリオは非対応)。約物が詰まりすぎるなら `pwid` / `pkna`、詰めすぎは `letter-spacing` で微調整。
- 使わない場面: 本文、メイリオ。ICS MEDIA の `palt` 記事は旧く、メイリオ前提の記述がある【弱】。
- 出典: ICS MEDIA(03,19)、tak-dcxi(19)
- 確度: 要確認

#### 5.3 見出しの折り返しは文節で。中央揃えは `text-wrap: balance` とセット
- なぜ: 短い見出しの途中で切れると読みにくい。本文まで文節改行すると段落内に不自然な空きが出る。
- 値: `word-break: auto-phrase`(Chrome 119 以降、日本語のみ、BudouX による機械学習。`lang="ja"` が必要。Firefox・Safari の現況は未確認)。誤判定は `<wbr>`、分離したくない箇所は `&zwj;`。`:root` に `line-break: strict` と `overflow-wrap: anywhere`。`@supports` で囲む。左揃えの見出しは `text-wrap: pretty` だが、Safari は日本語で `balance` のように動くバグがあるとされ、日本語には指定しない(現状は未確認)。
- 使わない場面: 本文の折り返し、`text-align: justify`(英語混在で崩れる。4.15)。
- 出典: Chrome i18n ブログ(03,19)、tak-dcxi(19)
- 確度: 要確認

#### 5.4 和欧間は CSS の自動アキに任せ、コンテンツ側に半角スペースを入れない
- なぜ: 自動アキと手入力のスペースは役割が別。書き手は詰めて書き、見た目のアキは CSS に任せる【推論】。
- 値: 和欧間は四分アキ(JLReq)。`text-autospace: normal`(Chrome 139 以降、Safari 18.4 以降。MDN は Baseline 2025 の newly available)。アキを全角の 1/8 とする資料はあるが MDN に記載がなく仕様で未確認【弱】。`pre`・`time`・`input`・`textarea`・`[contenteditable]` は `no-autospace`。SmartHR は「PDFファイルをアップロード」「2020年の年末調整」と詰めて書く。
- 出典: JLReq・MDN(19)、SmartHR(19)
- 確度: 要確認

#### 5.5 連続する約物は詰める(`text-spacing-trim`)
- なぜ: 開き括弧の連続や、閉じ括弧と開き括弧の隣接は、全角のままだと空きすぎる。
- 値: 開き括弧の連続、閉じ括弧の連続、「」「のような終わり→始めは、後ろの文字の前を二分詰める(JLReq)。`text-spacing-trim: normal`(初期値)が自動で行う。`trim-start` は行頭の開き括弧も半角にする(Chrome 123 以降)。フォントに `halt` か `chws` がないと無効。MDN は実験的機能で Baseline ではない。
- 出典: JLReq・MDN(19)
- 確度: 要確認

#### 5.6 禁則を守る。行頭に置けない文字・行末に置けない文字を決める
- なぜ: 行頭の句読点や閉じ括弧、行末の開き括弧は組版上の誤りになる。
- 値: 行頭禁則は句読点・閉じ括弧・中点・ハイフン類・繰返し記号・長音記号・小書き仮名。行末禁則は開き括弧。分割禁止は 2 倍ダーシ、2 倍三点リーダー、連続する欧文。ぶら下げ組(行末の句読点を行外へ)は任意で、`hanging-punctuation: last allow-end` は Safari のみ。`line-break: strict` で禁則を厳格にする。
- 出典: JLReq(19)
- 確度: 実証あり(W3C の組版要件)

#### 5.7 `font-family` に `system-ui` を使わず、`sans-serif` で終える
- なぜ: Windows で `system-ui` が游ゴシック UI になり、意図した字形にならない。
- 値: `"Local Noto Sans JP", "Noto Sans JP", sans-serif`(tak-dcxi)。明朝は Android に無いので Noto Serif JP を読み込む。ウェイトを絞り、サブセット化・`display=swap`・フォールバックを整える。日本語フォントは 1 ウェイト数百 KB〜1MB になりうる【弱】。
- 割れ: SmartHR はあえて書体を指定せず OS に委ねる(さまざまな言語で正しく表示するため)。業務アプリ・社内ツールは OS 標準で速さを優先、LP・キャンペーンは Web フォント(Resolute、classmethod【弱】)。既定: Web アプリの本文は上の指定、社内ツールで速さを優先するなら OS 標準。
- 出典: tak-dcxi(03,19)、SmartHR(19)、Resolute(20)
- 確度: 一人の意見(個人 gist)

#### 5.8 Noto Sans JP が唯一の正解ではない。小さい文字では UD 書体、明朝は UI に向きにくい
- なぜ: UD 書体は骨格が単純で、似た字の区別、大きい濁点・半濁点、広いアキがあり、スマホの小さい文字で読みやすい場面がある。明朝は横線が細く、小さいサイズや暗い背景で判別しにくい。
- 値: UI 向けの候補は BIZ UDゴシック / 明朝(Google Fonts)、LINE Seed JP、IBM Plex Sans JP、M+、みんなの文字(2022 年から有料)。Noto Sans JP は 100〜900 の可変フォント。BIZ UDPゴシックは視認性が高いが詰まって見えるので行間を広めに【弱】。Web フォントのサービスの無料条件は 2023 年の情報で、現在は未確認。
- 使わない場面: 資料デザインの「特殊書体を避ける」(desaken)は UI では SOMPO と逆。目的次第。
- 出典: SOMPO Digital Lab(19)、desaken(19)
- 確度: 一人の意見

#### 5.9 游ゴシックと Noto Sans JP の OS 差を前提にし、ボタンの上下を `text-box` で整える
- なぜ: 游ゴシックは Windows が Regular、Mac が Medium で、Windows では細く読みにくい。Noto Sans JP は Windows で視覚的に下寄りになる(ハーフレディングの差)。Chrome 128 以降と Edge で Noto が既定になりつつあり、アイコンと並べると上下のずれが目立つ。
- 値: `text-box: trim-both ex alphabetic`(Chrome 133 以降、Safari 18.2 以降)か Meiryo の明示。ICS MEDIA は `cap alphabetic` が削りすぎに見えることがあり、画像との上辺揃えには `trim-both text` が合う場合が多いと言う。揃える相手で値が変わる。作り方: `text-box` で削る → 上下に同量の padding → 目視【推論】。名前は Mac が `YuGothic`、Windows が `Yu Gothic`。
- 出典: zenn 15(19)、ICS MEDIA(19)
- 確度: 要確認

#### 5.10 日本語に斜体はない。強調は太字にする
- なぜ: 斜体は日本語の字形にない。日本語は画数が多く、同じウェイトでも欧文より太く見え、小さいサイズでは太字が潰れやすいという指摘がある。
- 値: `em:lang(ja)` を `bolder` に(tak-dcxi)。ウェイトは本文 400・見出し 700 が多い。
- 出典: tak-dcxi(19)、一般ブログ(19【弱】)
- 確度: 要確認

#### 5.11 用字用語を決めて統一する
- なぜ: 日本語は一人称や同音異義語で表記がぶれやすく、ぶれると利用者が言葉の読解に注意を使う。基準は一貫性・統一感・検索性・標準化・効率化(『日本語スタイルガイド 第3版』準拠)。
- 値: 表外読み(想い、旧い)は使わない。読みやすい漢字はひらがなに。ただしひらがなにしすぎると、どの漢字か判断する手間が増える。カタカナ語は漢字語への言い換えを先に検討(意味の振れ幅が大きく、利用者が都合よく解釈する)。「か所」「か月」に統一(箇所・個所は使わない)。丸数字は環境依存なので原則使わない。同じことを複数の表現で書かない。社内用語を使わない。漢字:ひらがな 7:3 は一般向けの記事の目安で、UI 文言の根拠ではない。
- 出典: SmartHR(19)
- 確度: 一人の意見(一社。用字用語の詳細ページは 404)

#### 5.12 敬語を使いすぎず、「することができる」を避け、格助詞を省略しない
- なぜ: 冗長さが読解の負荷になる。声が揺れると体験が一貫しない。
- 値: 「◯◯できます」「削除する」(「削除を行う」でない)、「確認してください」(「ご確認いただけますようお願いいたします」「させていただきました」は避ける。「ご参考ください」は誤り)、「項目名を変更します」(「項目名変更します」は不可)。口調はボタンと FAQ でばらけさせず 1 つに決める。急かす言葉と怖がらせる言葉を避け、専門用語には読みを添える(御神籤(おみくじ))。
- 出典: SmartHR(19)、scrapbox ichizen(19【弱】)
- 確度: 一人の意見

#### 5.13 約物と括弧を使い分ける
- なぜ: 括弧の種類に意味を持たせれば、読み手が要素の種別を見分けられる。
- 値: 句点は見出しで省略、箇条書きは単語なら省略・文なら付ける。順序に意味があれば「、」、入れ替え可能なら「・」。感嘆符・疑問符は単独なら全角、「!?」「!!」は半角、後ろに文が続くときは全角スペース。三点リーダーは Web で 1 つに統一。丸括弧 = 補足、「」= 画面上のメッセージ・入力値・強調、［］= 設定項目名・タブ名・ボタン名、【】= ユーザーが命名したオブジェクト名、{} = 変数、バッククォート = コードや URL。『』と“”は使わない。例示は「例：」で、「(例)」にしない。
- 出典: SmartHR(19)
- 確度: 一人の意見(一社)

#### 5.14 数字・日付・数え方を決める
- なぜ: 表記が揃うと比較と検索ができる。
- 値: 数字は半角。¥・%・3 桁区切りのカンマ・階層の区切り(/、>)も半角。ファイルサイズは「5GB」(スペースなし)。人は「名」、件数は「件」(SmartHR は氏名と写真を登録する製品のため「名」。他社へそのまま適用できるとは限らない)。UI の日付は「2025/01/01」、期間は「〜」、時刻は hh:mm:ss。システム処理用は 2 桁そろえ。ヘルプなどの文章では「2025年1月1日」「15時35分」も可。
- 出典: SmartHR(19)
- 確度: 一人の意見(一社)

#### 5.15 郵便番号・電話番号は 1 欄にまとめ、`type="number"` を使わない
- なぜ: `type="number"` は先頭の 0 が消え、ハイフンを入れられず、`postal-code` の自動補完が効かない。分割欄はコピー&ペーストを妨げる。
- 値: `<input type="text" autocomplete="postal-code" inputmode="numeric">`、電話は `type="tel" autocomplete="tel"`。ハイフンの有無は両方許し、サーバー側で正規化する。
- 出典: yumemi(19)、ICS MEDIA(19)
- 確度: 多数一致

#### 5.16 氏名は姓と名に分け、ふりがなも同じ単位で分ける
- なぜ: 日本語はふりがな欄が要り、`family-name` / `given-name` で自動入力と対応させる。住所の autocomplete は Chrome と Safari で補完範囲が異なる(`address-level2` は Chrome が補完せず、`address-line1` は Chrome が建物名まで補完)ので意図して設計する。
- 割れ: ふりがな欄の `autocomplete` は、yumemi が「`name` を付けず `off` か省略」、ICS MEDIA(2026-05 時点)が「通常の氏名欄と同じ値。`off` は多くのブラウザが無視する。Chrome はラベルのかな / カナで判定する」と逆。どちらも一次検証は未実施。実機で確かめる。
- 使わない場面: 英語圏の EC 調査(Baymard)は氏名を 1 欄にまとめるよう勧める(9.6)。これはふりがなの要件がない前提の結果。
- 出典: ICS MEDIA(19)、yumemi(19)
- 確度: 要確認

#### 5.17 全角/半角・スペース・かな/カナの違いでエラーにしない
- なぜ: 全角と半角の区別がつかない利用者がいて、変換はサーバー側で簡単にできる。
- 値: 住所の数字は両方受け付ける。かな / カナの混在はサーバーで変換。半角 / 全角スペースの差は許容する。
- 出典: ICS MEDIA(19)
- 確度: 一人の意見

#### 5.18 日付は 1 欄+プレースホルダー。生年月日に `type="date"` は慎重に
- なぜ: 年月日を分けると入力の手間が増える。`type="date"` の年選択 UI はブラウザごとに統一されておらず、遠い日付(生年月日)で体験が悪化することがある。
- 出典: yumemi(19)
- 確度: 一人の意見

#### 5.19 氏名の異体字(髙・﨑など)は入力方針を早く決める
- なぜ: Shift-JIS 環境で文字化けするため「高」に置換する運用がある。IVS(字形選択子)と IPAmj 明朝(約 6 万字)で個別の字形を扱う道もあるが、入力手段が追いついていない。
- 値: 戸籍上の字形を保存する必要があるか、事前に業務側と合意する【推論】。
- 出典: 検索結果のみ(zenn panda728 ほか。19)
- 確度: 要確認

#### 5.20 ○×△は日本で通じるが、海外では逆に読まれうる
- なぜ: 日本では ○ が肯定、△ が部分的、× が否定という体系が説明なしで通じ、比較表に使われる。海外では ○ が「オフ」を意味する場合があり、PlayStation の決定ボタンも日本と欧米で逆になる例がある。
- 値: 海外展開では記号を文字ラベルに置き換える。
- 出典: Wikipedia ほか検索結果(19【弱】)
- 確度: 要確認

#### 5.21 日本語は英語より短くなりやすい。固定幅のボタンを前提にしない
- なぜ: 英語原文の最大 2 倍の長さを想定する経験則があるが、日本語は固定幅のボタンを逆に余らせる。
- 値: 可変幅を前提にする。
- 出典: 一般ブログ(19【弱】)
- 確度: 要確認

## 6. 色

#### 6.1 色を減らす。色は意味を運ぶ道具で、装飾ではない
- なぜ: 色は注意の通貨。全部に使うとどれも目立たない。伝達の目的があるときだけ、意味の違いに対応するときだけ別の色を使う(Few)。判定法: 別の色に入れ替えても体験が変わらないなら装飾(Atlassian)。
- 値: 悪い黄色の背景を白に(Waterworth)。カードの 5 色のアクセントを 1 色に、アイコンは基本無色で色は現在地・状態に残す(Kole K06)。ピンクをアイコン・文字・入力欄の枠・リンクに使い回すと全部が叫ぶ(Showalter J2)。
- 使わない場面: スタイルを立てた画面は濃い影や色を意図して使ってよい。ただし注意すべき場所(操作できる所、大きなグラフ)だけ(J2)。
- 出典: Waterworth(15)、Kole K06・Showalter J2(16)、Few・Atlassian(09)
- 確度: 多数一致

#### 6.2 まずグレースケールで階層・間隔・配置を決め、色は最後に足す
- なぜ: 色で目立たせると階層の欠陥が隠れる。色なしで成立していれば、色は意味の補強になる。
- 値: 色を全部外して文字のスタイルを言葉で書き出し、不自然な点に注をつける(Learn UI のログイン画面)。要素は 1 つずつ足し、毎回よい状態を保つ。
- 割れ: Kennedy は白黒から作る、Schoger は先に灰を決めてブランド色を一点に入れる。どちらも「色は最後か、少なく」。
- 出典: Kennedy(18,20)、Refactoring UI(18)、Dannaway #6(18)
- 確度: 多数一致

#### 6.3 アクセント(主操作の色)は 1 色に固定し、操作できる所にだけ使う
- なぜ: 「この色が出た所は押せる」と学習させるため。アクセントの最適な数を示した実証研究はない。1 色は慣習で、研究の結論ではない(09)。
- 値: Carbon は青が主操作色。Primer は links・selected・active・focus にアクセントを割り当てる。色相の決め順【推論】: ①既存のロゴ・ブランドの資産 ②競合・隣接サービスと同じ色相でないか ③白 / 暗い面に対して 4.5:1 以上の段が作れるか ④状態色(赤・緑・黄)と混同しない(赤系・緑系のアクセントは避ける)。2 つ目のアクセントは、1 つ目と別の意味を持つ操作クラスがあるときだけ。
- 割れ: Raptis は最重要要素のみ、Dannaway はリンクとボタンなど操作可能な要素すべて(クリックできないものには使わない)。既定: Dannaway の規約(色 = 操作できる)に従い、画面の主役の強い色は 1 つに保つ。理由: 学習できる規則として明快で、両者とも「乱用しない」で一致する。通知の丸にブランドの緑を使ったら背景に埋もれた例(Showalter J2)。
- 出典: Carbon・Primer・Atlassian(09)、Raptis・Dannaway(18)、Showalter J2(16)
- 確度: 多数一致(数の最適値は実証なし)

#### 6.4 中立色が画面の大半。階段(段階)を用途で割り当てて作る
- なぜ: 中立色は意味を持たないので、意味のある色が目立つ土台になる。階層は面のわずかな明度差で作る。
- 値: パレットは灰 8〜10 段、主色 1〜2 色×5〜10 段、アクセント(状態・カテゴリ用)数色×5〜10 段(Refactoring UI)。作り方: 500(ボタン背景として使える色)→ 900 と 100(アラートで試す)→ 700 と 300 → 残り。`lighten()` で場当たりに作らない。Radix の 12 段は 1-2 背景、3-5 部品の背景(通常 / hover / 押下)、6-8 境界(8 はフォーカスリング)、9-10 ソリッド、11 低コントラスト文字、12 高コントラスト文字。Kole は製品に背景 4 層、線 1〜2 本、文字 3 種。Linear はテーマ入力を 98 変数から基調色・アクセント・コントラストの 3 つに減らした。
- 出典: Refactoring UI(18,20)、Radix・Atlassian・Carbon(03,09)、Kole K07(16)、Linear(20)
- 確度: 多数一致

#### 6.5 60-30-10 は目安にすぎない。製品 UI では中立色の層が主役
- なぜ: 60-30-10 の根拠となる実証は見つからなかった(03,09)。製品 UI は LP より色が少ない。
- 値: Malewicz は背景 60%(白)・第 2 色 30%(濃灰)・アクセント 10%(ボタンなど)。Kole K07 は Vercel が黒 90%・白 8%・赤 2%、背景は 98〜100% の白(Linear 99%、Notion 100%、Vercel 98%)、サイドバーは主面より約 2% 暗く(Mercury は青を 2% 足す)、カードの縁は約 85% の白、文字は最も濃い見出しで約 11% 白・本文 15〜20% 白・補足 30〜40% 白、ボタンは重要なほど暗く多目的は 90〜95% 白と述べる。
- 使わない場面: LP は 3〜5 色の中立色で足りる(K07)。比率を入れ替えると認知的に重いがブランドによっては合う(Malewicz)。
- 出典: Malewicz #7(17)、Kole K07(16)
- 確度: 要確認(実証なし。数値は自動字幕で「% 白」の意味が曖昧)

#### 6.6 純黒・純白を避け、灰に色相を足す(温冷を混ぜない)
- なぜ: 現実の影や暗部は無彩色でなく、無彩色の灰はフラットに見える。
- 値: 灰の彩度は HSB で約 5% 未満(Hobday #1-2)。ブランドの色相を少し混ぜる(HSL で彩度 22% ほど、明度は同じ。Schoger)。青系ブランドには青、赤・黄・橙には黄褐色。アクセントの色相に最も近い低彩度の灰を選ぶ(Radix: mauve / slate / sage / olive / sand)。Tailwind v4 の 500 段は slate 色相 257・彩度 0.046、gray 264・0.027、zinc 286・0.016、neutral は彩度 0、stone 58・0.013。色相は全段で一定に保ち、暗部の彩度をわずかに上げる(OneSignal【弱】)。
- 使わない場面: ダークでカラフルな部品が多いなら、彩度のある灰はぶつかるので無彩色寄りにする(Radix)。
- 注意(色の理由の書き方): 「温かい / 冷たい印象」は理由にしない。暖色 = 親しみ、寒色 = 冷静を実証した研究は見つからなかった。理由は「アクセントとのまとまり」(Radix)と書く。
- 出典: Hobday・Kennedy・Refactoring UI(18)、Schoger(20)、Radix・Tailwind・OneSignal(09)
- 確度: 多数一致(印象の効果は実証なし)

#### 6.7 背景は中立にする。鮮やかな背景を避け、色はにじませる程度に
- なぜ: 背景は背景であるべきで、後で主操作に使う色が使えなくなる。
- 値: 灰にほんの少し紫を足す(Kole K06)。薄い淡色の背景は目に優しくコントラストも出る(Rachel How)。中間色を背景に多用せず、非常に薄いか非常に濃い地にするとコントラストが取りやすい(Flux #14)。ヘッダ全面にブランド色を塗ると強すぎる(Schoger)。
- 出典: Kole K06(16)、Rachel How(15,16)、Flux(17)、Schoger(20)
- 確度: 多数一致

#### 6.8 コントラストは本文 4.5:1、大きい文字と UI 部品・状態の識別は 3:1(WCAG 2.2 AA)を合格線にする
- なぜ: 読めないのは機能の欠落。比は WCAG 2 の式で測る。OKLCH の L は目安にすぎない。
- 値: 大きい文字は 24px(18pt)以上、または太字 19px(14pt)以上(freee・WCAG 1.4.3)。UI 部品と意味のある図形は 3:1(1.4.11)。薄い灰の塗りのボタンは無効に見える。Apple は独自色の小さい字で 7:1 を目指す。APCA は WCAG 3 のドラフトから外れ、2026-04 の草案でもアルゴリズム未定。使うなら WCAG 2 を満たしたうえで「薄すぎ」の検知に足すか、満たさない色の理由を記録する(Roselli)。
- 訂正: Dannaway の「18px 超の太字 / 24px 超の通常」は WCAG の大きい文字の定義と一致しない。
- 出典: WCAG 2.2・Roselli(03,09)、freee(19)、Dannaway(18)、Apple HIG(07)
- 確度: 実証あり(規格)

#### 6.9 色だけで意味を運ばない(WCAG 1.4.1、Level A)
- なぜ: 色覚が多様。男性の約 1/12(NEI)、日本人男性は約 20 人に 1 人・女性は約 500 人に 1 人(LINEヤフー)が色覚の多様性を持つ。最多は赤と緑の区別が難しい型。Few は「男性約 10%、女性 1%」と書くが 2008 年の数値で古い。
- 値: 選択タブに下線、選択のナビはアイコンの塗り替え、増減に +/-、グラフは同色相の濃淡。状態色はアイコン・文言・形とセット(SmartHR・Atlassian)。暖色と寒色の組み合わせ、明度差、文字・マークの併用。Okabe-Ito の指針: 暖色と寒色を交互に、同系の 2 色は明度か彩度に差、凡例でなく直接ラベル、赤文字は暗背景を避ける。色覚シミュレーションは近似。
- 出典: WCAG・NEI・Okabe-Ito(09)、LINEヤフー(19)、Dannaway・Raptis(18)
- 確度: 実証あり

#### 6.10 状態色(成功・警告・危険・情報)は広く共有された連想に従う
- なぜ: 利用者は赤を危険、緑を成功と学習している。読む前に状態が伝わる(DADS: メンタルモデルに影響する視覚的な共通言語)。
- 値: 赤 = 危険・緊急、黄 = 警告、緑 = 成功(Kole K01)。ブランドが紫でも破壊的操作は赤(K06,K07)。ログアウトを赤にしない(システム色の誤用。J2)。警告の黄の面は暗い文字とセット(SmartHR)。
- 使わない場面: 文化で逆転する。中国・日本・韓国の株価チャートでは赤が上昇(日本は媒体で不統一。2005 年の調査と 2024 の記事のみ)。日本向けの上昇 / 下落は既存の慣習と逆にしない、または色に頼らず矢印と符号を足す【推論】。
- 出典: Kole(16)、DADS・SmartHR・Radix・欧州データポータル(09)、Showalter J2(16)
- 確度: 多数一致

#### 6.11 色の「心理効果」(信頼の青、温かみ)を設計の理由にしない
- なぜ: 赤が成績を下げるという研究は追試で失敗が続き、Gnambs(2020)のメタ分析(22 論文・38 サンプル・67 効果量)は、推論課題の小さな負の効果(d = -0.34、初報の半分未満)を認めつつ、出版バイアス補正後は「証拠価値なし」とした。Elliot 本人も 2015 年に「決定的な主張は時期尚早」と述べた。
- 値: 存在が確かなのは「色と感情の連想」(Jonauskaite 2020: 30 か国 4,598 人、共通パターン r = .88)。これは「色を見せると行動が変わる」根拠ではない。使える理由の型は ①利用者がすでに持つ連想(赤 = 危険、青リンク)②機能(コントラスト・区別)③ブランドの既存資産・競合との区別。
- 訂正: Kole K01 の「青 = 信頼」は慣習の説明として読み、効果の根拠としては使わない。
- 出典: Gnambs・Elliot・Jonauskaite(09)、Kole K01(16)
- 確度: 実証あり(効果の否定)

#### 6.12 ブランド色が WCAG を満たさなければ調整してよい
- なぜ: ブランドの色が基準を満たさないことがある。暗くするだけだと「暗く濁る」。
- 値: 色相環で少し回す(類似色)か補色を使う。オレンジの地に白文字が落ちるなら、暗くするか補色の青に(Kole K06)。または明るい橙(黄寄り)に濃い文字(暗くすると茶色。Bad About)。DADS はリンクの青と紫の明度差を、紫に赤みを足して作った。Stripe は CIELAB で再構築し、5 段以上離れた 2 色は小さい文字で必ず十分なコントラスト(アイコン・大きい文字は 4 段)という規則にした。
- 出典: Kole K06(16)、Bad About(20)、DADS・Stripe(09)
- 確度: 多数一致

#### 6.13 明暗を変えるときは、明度だけでなく彩度と色相も動かす
- なぜ: 黒を足して暗くすると彩度が増えず、濁る。
- 値: 暗くする = 明度↓・彩度↑・色相を最寄りの R / G / B 側へ。明るくする = 明度↑・彩度↓・色相を最寄りの Y / C / M 側へ(Kennedy)。例: コーラル 21° → 0° に寄せた影。グラデーションの色相ずらしは 10〜20°(Schoger)。
- 使わない場面: 配分(彩度・明度をどれだけ動かすか)は Kennedy も有料コース扱いで未提示。OKLCH を使えば知覚的に近い操作が可能【推論】。
- 出典: Kennedy KC(18)、Schoger(18)
- 確度: 一人の意見(観察ベース)

#### 6.14 トークンの色は OKLCH で定義し、最終判定は WCAG 2 の比で行う
- なぜ: HSL は同じ L でも色相で明るさが違う(黄は青より明るく見える)。OKLCH は L が色相をまたいで知覚的に揃うので、段階の調整が予測しやすい。ただしアクセシビリティの保証にはならない。
- 値: Tailwind v4 は既定パレットを oklch に変更。Linear は HSL から LCH へ。グラフの多色は OKLCH で明度・彩度を固定して色相を 25〜30 度ずつ回す(Kole K07)。P3 では範囲外が丸められ、Chrome / Safari はクリップして色相がずれうる(`color-gamut: p3` で明示)。色トークンは `x` と `x-foreground` のペア(shadcn)。
- 出典: Evil Martians・Tailwind・Linear・shadcn(03,09)、Kole K07(16)
- 確度: 多数一致

#### 6.15 色付き背景の上では灰色の文字を避け、背景の色相に寄せた色にする
- なぜ: 色付きの背景に灰を載せると濁る。
- 値: 背景の色相を混ぜた淡い色、または白の不透明度 20〜30%(Schoger)。暗い背景に白より、明るい背景に濃い文字のほうがアクセシブル(Refactoring UI)。アラートは暗い背景+白文字をやめて、淡い背景+濃い文字(Transistor)。
- 出典: Schoger(18,20)、Refactoring UI(18)、Transistor 事例(20)
- 確度: 多数一致

#### 6.16 ダークモードは反転でなく別に設計し、面の明度差で高さを表す
- なぜ: 暗い色同士は似て見えるので差を大きく取る。ダークは影が効かないので、面を明るくして高さを表す。
- 値: 面の差はライトの 2 倍(2% → 4〜6%。Kole K07)。縁は明るく、文字は目の疲れのため白でなく明るい灰、主色は 300〜400、白は最重要のみ。ブランドのロゴは彩度を少し落とし、チップは彩度と明るさを下げる。Hobday のコンテナ間の明度差はダーク 12% 以内・ライト 7% 以内(約 100 サイトの調査と記載、方法は非公開【弱】)。純黒を避ける: Material 2 の面は #121212 級で白本文との比 15.8:1。純黒の地の白文字は乱視でにじむ(halation)とされるが機序は一次未確認。白背景の画像は少し暗くする(Apple)。Carbon はライトが白とグレー 10 を交互、ダークは 1 段ずつ明るくして階層を作る。
- 使わない場面: Material 2 の白オーバーレイ(0〜16%)は M3 で surface container に置換された。
- 出典: Kole K01・K06・K07(16)、Hobday(18)、Juxtopposed #20(17)、Material・Apple・Carbon・Radix(03,07,09)
- 確度: 多数一致(個別の値は要確認)

#### 6.17 ライト / ダークの既定は OS に従う。信号がなければライト
- なぜ: 実験が一貫して、ポジ極性(暗い字・明るい背景)が成績で勝ち、小さい字ほど差が開く。本人は差に気づかない。
- 値: Piepenbrock 2014(Human Factors): 8〜14pt でポジ極性の優位が文字が小さいほど大きい。Dobres 2016(Ergonomics): 暗い部屋(約 23 lux)でポジ極性の読み取り閾値が 38.6% 低い(結論は暗い実験室の条件に限る)。NN/g は一般向けの既定をダークにしないよう勧め、切替の提供を強く勧める。Apple は OS 設定を尊重し、アプリ独自の外観設定は避ける。web は OS の信号に従い手動切替を併設してよい【推論】。ダークで小さい字を扱うなら本文を 1 段上げる(14 → 15〜16px)【推論】。
- 使わない場面: 動画・写真・没入メディア・夜間の開発は、ダーク既定でもよい(ただし OS 設定を優先)。白内障など水晶体が濁る人は暗いモードで成績が上がることがある(Legge 1985、7 人)。暗い環境(50 lux)ではダークの快適さの評価が高い(二次記事のみ【弱】)。
- 出典: NN/g・Piepenbrock・Dobres・Apple HIG(07)
- 確度: 実証あり

#### 6.18 データの色は変数の種類で選び、色を使わずに済むなら使わない
- なぜ: 色は最も希少な強調。位置やラベルで区別できるなら色は要らない。
- 値: カテゴリ(順序なし)は Okabe-Ito か Carbon の固定順 14 色。連続(低 → 高)は単色の明度(ライトは濃い = 大きい値)。発散は中心を淡色に、両端を別の色相に。赤と緑の組は避ける(Few。正負は青 - 赤)。強調は注目 1〜2 系列だけ濃く、残りは灰(Datawrapper)。凡例でなく直接ラベル。カテゴリが 7〜8 を超えたら、色を足さずグルーピング・強調・小さい複数の図に切り替える【推論】。Okabe-Ito の 8 色: #000000、#E69F00、#56B4E9、#009E73、#F0E442、#0072B2、#D55E00、#CC79A7(コード値は検索のみ。黄は白背景で薄い)。
- 出典: Few・Datawrapper・Carbon・Okabe-Ito(09)
- 確度: 多数一致

#### 6.19 アクセントの彩度・明度の目安は一人の好みと割り切る
- なぜ: 100% の彩度と明度は強すぎる。
- 値: Malewicz は HSB で彩度・明度を約 90(90 超は強すぎ)、色相 40〜120 を避ける、HSB の枠の中央あたりを選び、他の色は色相スライダーだけで作る、パステルや超高彩度と最初の赤は避ける。AI の色については、Kole が「明るい色を選びがちで組合せが悪い」、Malewicz が「地味になりがち」と逆のことを言うので、どちらも印象にとどまる。
- 使わない場面: 色相 40〜120 の回避は Malewicz の好みで、他の動画に裏付けがない【推論】。
- 出典: Malewicz #5・#7(17)、Kole K08(16)
- 確度: 一人の意見

## 7. 面・線・影・角丸

#### 7.1 光は上から。影は少し下にずらす
- なぜ: 現実の光は上から来る。全周に同じ広がりの影は光源がない。
- 値: 上端を明るく下端を暗く。凹(入力欄・押下ボタン・スライダの溝)と凸(通常ボタン・カード・ポップアップ)を区別する(Kennedy)。光源は全ページで 1 つ(縦:横 = 2:1。Comeau)。
- 使わない場面: 完全フラットは「押せるか」を分かりにくくする。手がかりは控えめに(Kennedy)。
- 出典: Kennedy R1(18,20)、Refactoring UI(18)、Schoger(20)、Comeau(18)
- 確度: 多数一致

#### 7.2 影は弱く、ぼかしを大きくする。強い影は「覚えたての装飾」
- なぜ: 影が最初に目に入るなら使い方が悪い。
- 値: 不透明度を下げ、ぼかしを上げる。強すぎる影は不透明度 8% へ(Schoger)。カードは弱く、ポップオーバーは強く(Kole K01)。Figma の既定は強すぎるので、影の色を薄い灰にしてぼかしを大きくするか消す(K05)。1 層で作るなら、ぼかしは縦オフセットの約 2 倍(4px → 8px。Hobday #16)。影を弱めると押せる範囲が分からなくなるので、薄い線を足す(Waterworth)。
- 使わない場面: 意図したスタイル(ネオブルータリズム)では太い影を、操作できる所と大きなグラフにだけ使う(Showalter J2)。
- 出典: Schoger(20)、Kole K01・K05(16)、Waterworth(15)、Hobday(18)
- 確度: 多数一致

#### 7.3 品質を上げるなら影を多層にし、色を背景に合わせる
- なぜ: 黒の半透明は灰色の曇りになる。多層にすると自然な柔らかさになる。
- 値: Comeau の 3 段例は 小 `0.5px 1px 1px` / 不透明度 0.7、中 `3px 6px 6px` / 0.33、大 `16px 32px 32px` / 0.2。3〜5 層で 1 / 2 / 4 / 8 / 16px の倍々、各 0.075。色は背景と同じ色相で彩度・明度を落とした色。浮くほどオフセット↑・ぼかし↑・不透明度↓。標高は低・中・高の 3 段に絞りトークン化。Refactoring UI は「大きく柔らかい影 + 小さく濃い影」の 2 段。浮いたカードの影はそのオブジェクトの色に合わせる(青いカードに青い影。Rachel How)。
- 割れ: Hobday の 1 層式と Comeau の多層。併用可。既定: 1 層ならぼかし = オフセット × 2、品質を上げるなら多層+色合わせ。
- 使わない場面: 重ねた影をアニメーションさせない(描画コスト)。
- 出典: Comeau(03,18)、Refactoring UI(18)、Rachel How(15)
- 確度: 一人の意見(実装記事。03 は【弱】)

#### 7.4 深度の手法を 1 種類に統一する。ダークでは影でなく面の明度差で表す
- なぜ: 柔らかい影・硬い影・影なしを混ぜると、奥行きの規則が読めない。暗い地では影が効かない。
- 値: 近い面ほど明るい(ライト・ダークとも。Hobday #15)。ダークは影を使わず(#26)、縁の反射(明るい上端)で浮きを作る(Schoger【弱】)。
- 出典: Hobday #15・#26・#27(18)、Schoger(18)、Kole K07(16)、Juxtopposed(17)
- 確度: 多数一致

#### 7.5 境界は 1 本にする。隣り合う硬い境界を 2 つ置かない
- なぜ: 二重の境界は交点が見えて雑になる。
- 値: コンテナの縁は内外の両方と対比させる(Hobday #7)。重なる半透明の枠線は交点が見えるので、枠は 1 回だけ描く(Geist)。
- 出典: Hobday #7・#25(18)、Geist(09)
- 確度: 一人の意見

#### 7.6 枠線の代わりに、背景色の差・薄い塗り・余白で分ける
- なぜ: 枠が増えると雑然とする。強い手段は必要になるまで使わない(2.5)。
- 値: 隣り合う面を少しだけ違う背景色にして区切る(Transistor)。入力欄は白地に灰の塗りにして枠をなくす(WP Pusher)。パネルの見出しは線でなく背景差で分ける(Schoger #15)。ナビは背景を約 2% 暗い off-white にしてパネルを浮かせる(Schoger)。カードは線か背景色で分け、暗いテーマは線、明るいテーマは背景色が好み(Kole K15)。
- 使わない場面: 影を弱めた結果、押せる範囲が分からなければ薄い線を足す(Waterworth)。
- 出典: Transistor・WP Pusher・SneakedIn 事例(20)、Kole K15(16)、Refactoring UI(18)
- 確度: 多数一致

#### 7.7 角丸は部品間でそろえる。角が鋭ければ少し丸める
- なぜ: 同種の面で半径が違うと崩れて見える。小さい角丸は中立、大きい角丸は遊び心(Refactoring UI)。
- 値: 入力と部品は通常 4〜6px(Schoger)。Kole は小さい部品すべて 10px。Malewicz は同種のカードを 24px にそろえ、重要度の低いほうのボタンは黒の輪郭線にする。2 つの検索欄、戻るとスキップのボタンは同じ大きさ・角丸・スタイル。
- 出典: Kole K05(16)、Waterworth(15)、Malewicz(17)、Schoger(20)、Dannaway #12(18)
- 確度: 多数一致

#### 7.8 入れ子の角丸は、内径 = 外径 - 隙間
- なぜ: 同心の曲線になり、角の余白が均一に見える。
- 値: 外 24・余白 8・内 16。0 や完全な丸のときは不要。境界線がある場合は枠の太さも距離に含める流儀もある。
- 割れ: Raptis は「外径 = 内径 × 2」を簡易式とする(隙間があれば正確でないと自認)。既定: Hobday の式。理由: 同心にするなら幾何学的にこちらが正しい【推論】。
- 出典: Hobday #24(18)、Raptis #8(18)、ブログ群(03)
- 確度: 要確認(幾何学の導出で、実験ではない)

#### 7.9 グラデーションは同系色の濃淡か、使わない
- なぜ: 青と緑のようなグラデーションは破綻する。
- 値: 同じ色の濃淡。色相をずらすなら 10〜20°(Schoger #16)。
- 出典: Kole K05(16)、Schoger(18)
- 確度: 一人の意見

#### 7.10 全幅の色帯は「偽の床」になる。続きがあると分かる余白と見出しを残す
- なぜ: 下に続きがないように見える空白や色帯は、スクロールを止める。
- 値: 閲覧時間の約 57% がフォールドの上(2018)。2 画面目までで約 74%(8.2)。見出し帯(色付きの帯に見出し)の使い分けは一次資料が見つからなかった。使うならクロームとコンテンツを分ける用途(表のヘッダ行・カードの頭)に限る【推論】。
- 出典: NN/g(07,10)
- 確度: 実証あり(観察。帯の使い分けは要確認)

#### 7.11 質感(影・グラデ)を足すなら主ボタン 1 つだけ
- なぜ: 平らな要素ばかりだと全部同じに見え、手がかりが減る。ただし全面に質感を付けると控えめの原則に反する。
- 値: Shopify の質感のある主ボタン、Airbnb のダイヤルのようなアニメ(Malewicz)。
- 割れ: Malewicz は「フラットは終わり」、Waterworth・Kole は控えめに。既定: 控えめ。主ボタン 1 つだけ質感を足してよい。
- 出典: Malewicz #10(17)、Waterworth(15)
- 確度: 一人の意見

## 8. 配置(画面の型ごと)

#### 8.1 慣習の配置に従う。外すなら 1 点に絞り、理由を書く
- なぜ: 30 年分の慣習で利用者が期待を持つ。慣習は自己強化する(人は見たことのある場所を見て、企業はそこに置く。NN/g)。従えば新しい区画を足しやすく、レスポンシブにもしやすい。
- 値: 上から下、左から右。ナビは上か左。行動を促すボタンは目立たせる。外すのは小さな動きや独自の機能など 1 点。「規則は事故でなく意図して破る」(Kole K02)。パターンを一度崩す驚きは、よく作られていれば効く(K10)。
- 出典: Kole K02・K10(15,16)、NN/g(10)、Hobday(18)
- 確度: 多数一致

#### 8.2 主役は左寄り・上寄りに置く(視線の実測)
- なぜ: 注視は左半分と画面の上に集中する。
- 値: 注視の 80% が左半分(2010 年は 69%)。検索結果は 94% が左。最左 0〜192px は 6%(左ナビは必要なときにだけ見られる)。ピークは左から約 600px。閲覧時間の約 57% がフォールドの上(2018)、2 画面目までで約 74%(2010 年は約 80%)、ページ上位 20% に 42% 超。120 人超・13 万注視・1920×1080(NN/g)。
- 使わない場面: 「右は見られない」ではない。重要なものを右に置くなら視覚的な強さを上げる。左ナビをやめる理由にならない。「全部を上に置け」でも「フォールドは存在しない」でもない。
- 出典: NN/g(10)
- 確度: 実証あり

#### 8.3 F / Z / グーテンベルクを配置の理由にしない
- なぜ: F は NN/g の 2006 年の調査から出た大まかな形で、実際は E 型・逆 L 型にも変わる。NN/g は F を「避けたい失敗型」と位置づけ、書式で和らげる(最初の 2 段落に要点、情報の多い語から始まる見出し、箇条書き)。意味のある小見出しがあるページでは、見出しだけを拾う「レイヤーケーキ」が最も効率的。Z は一次の実測が見つからず、グーテンベルクは均質な印刷物の話で UI に適用する前提が合わない。
- 値: 理由に使えるのは NN/g の左・上の実測(8.2)と、「意味のある小見出し・箇条書き・文頭に要点」。F / Z を使うなら「実測がないが慣習として左上から右下へ」と書く。データの出所: 03 は 232 人・数千ページ、10 は公開ヒートマップが 45 人強と 47 人の 2 例と記す。
- 出典: NN/g(03,10)、Kennedy・Raptis(18)
- 確度: 実証あり(否定的に)

#### 8.4 ヒーロー(LP)は「キッカー → 見出し → 説明 → 1〜2 ボタン」
- なぜ: ヒーローで 9 割を納得させ、残りは直下の「不安を消す節」(社会的証拠など)で補う。
- 値: キッカー(小さな実績文)で現実感、見出しで「何の問題を解くか」、説明で補足。ボタンは通常 1 つ。高価で導入が重いなら副ボタンに「事例」「デモ」。「今すぐ購入」を 2 つ目にしない(摩擦が大きい)。LP の骨組みは文字ブロック・ナビ・統計・画像の 4 領域(Kole K03)。力強い一文なら中央寄せ・大きな文字・広い余白。機能が多くあふれるならベントグリッド。
- 使わない場面: 「Welcome to」で始めない(13.3)。
- 出典: Malewicz #8(17)、Kole K03(16)、Flux(17)
- 確度: 多数一致

#### 8.5 先導線: 見出し → 説明 → ボタンの順に行を短くし、視線をボタンへ運ぶ
- なぜ: 行の右端が斜めの線を作り、視線がそれに沿う。説明文をボタンより長くすると視線が外へ逃げ、ボタンへ戻る時間がかかる。
- 値: 画像の暗い部分は無視され、明るい部分が次の視線の停留点になる。画像をぼかして何が残るかを見る。
- 使わない場面: 規則を破ると記憶には残るが、認知負荷を上げない範囲でのみ。
- 出典: Malewicz #8・#9(17)
- 確度: 一人の意見

#### 8.6 ヒーローにアプリ画面を大きく置かない
- なぜ: 初見の人はアプリの見た目に関心がなく、複雑な画像は視線の線が増えて認知負荷になる。
- 値: 人物と、アプリの 1 パネルだけを切り出して並べる。全体は下の節で見せる。
- 使わない場面: 対象が特定の技術者で、画面が価値の証明そのものなら成立する(Linear)。
- 出典: Malewicz #8・#9(17)
- 確度: 一人の意見

#### 8.7 焦点は顔・視線・コントラスト・余白・動きで作る
- なぜ: 人は顔と視線の先に引かれる。大きさだけが手段ではない。
- 値: 人物の視線を CTA の方へ向ける。服の 1 か所だけを CTA の色相に合わせる。写真は上端を切って視線を口元に落とす(歯科の例)。
- 使わない場面: 動画や動く要素は目を奪うので、焦点を競合させない。
- 出典: Malewicz #8(17)、Flux #13(17)
- 確度: 一人の意見

#### 8.8 ダッシュボードはデータに形を決めさせる
- なぜ: 表が合うデータと、そうでないデータがある。
- 値: 種類が決まっている(部署・雇用形態)はチップ。数字は桁をそろえて右揃え。長い文字は省略。無効の行は薄く。時間で並ぶデータは表より時系列。色はデータから(緊急は赤、誰がしたかはアバター)。部品はリスト・表、カード、入力、タブの 4 つ。表は検索・絞り込み・並べ替えを備える(Kole K15)。
- 出典: Kole K04・K15(16)
- 確度: 一人の意見

#### 8.9 監視用ダッシュボードは 1 画面に、常に重要なものを左上の固定位置に
- なぜ: 短期記憶の限界から、スクロールや画面切替を避ける。位置はデータを強調する最も効果的な手段の 1 つ。
- 値: 常に重要なデータは固定位置(特に左上)。今この瞬間だけ重要なものは動的な強調(中央のポップアップなど)。強調しすぎると何も目立たない。関連する項目を近くに置き、グループは最も目立たない手段で区切る(近接 → 囲み → 線の順に強い)。「異常件数を左上の大きな数値に」(10 の例)。
- 使わない場面: 探索・分析用の画面には当てはまらない【推論】。Few の「ナビは右下」は慣習と衝突するので無批判に採らない(書評者が異議)。Few の原典と 2007 年のホワイトペーパーは未入手で、書評経由。
- 出典: Few(10。書評経由)、NN/g(10)
- 確度: 一人の意見(左上は NN/g の実測が補う)

#### 8.10 ダッシュボードの骨組み: サイドバーは背骨、最重要は最上部、グラフは軸つき
- なぜ: 利用者に一番大事なものを最初に見せる。
- 値: サイドバーは上にプロフィール(画像と矢印でクリックできると示す)、リンクは「見慣れたアイコン + 短い題」で関連ごとに組、設定とヘルプは頻度が低いので下、現在地に印。上端はページの主要操作か簡単なナビ。グラフは折れ線 + 格子線 + 数値 + 要約 + 期間選択。軸と目盛りを入れる(Dribbble 風のグラフは縦軸がなく、丸い棒の先で値が読めず、棒が 16 本あるのに曜日は 7 つだった例)。数値には単位・期間・前年比・傾向(スパークライン)を添え、同じ KPI を 3 回出さない(Data School、Kole K08)。
- 出典: Kole K05・K08・K15(16)、Data School(20)
- 確度: 一人の意見

#### 8.11 画面は名詞(オブジェクト)から決め、一覧 → 詳細で見せる
- なぜ: 動詞から入るタスク指向だと機能の羅列になり、操作体系にまとまりがない。
- 値: ビューは一覧(ソリューションビュー)と詳細(シングルビュー)。手順は要求分析 → モデル抽出 → ビュー定義 → ビジュアル定義。Material の list-detail はリスト固定幅・詳細可変、狭い画面で副次内容をボトムシート / サイドシートへ。
- 出典: elevenlines(19。保存本文は文字化けでライブ取得から再構成、一部推定)、ソシオメディア HIG #23・#24(19)、Material(10)
- 確度: 一人の意見

#### 8.12 操作は効果が起きる場所の近くに置く(Locality の 3 法則)
- なぜ: 最小驚きの原則。
- 値: ①操作は変化が起きる対象の上に(Gmail の行 hover で削除・既読)。②領域全体に効く操作はその領域の上に(「すべて既読」は一覧の上。広い範囲ほど高い位置)。③効果が起きる場所から遠いほど目立たせる(モバイルの FAB。フォーム右上の保存は見落とすので、他の操作と同じ列に)。長いリストの「追加」は末尾に置き、画面下にスクロールが達したら固定する(固定できないなら先頭)。
- 使わない場面: Kennedy 自身が、新しい Gmail は厳密には守っていないと述べる。
- 出典: Kennedy KL・K4(18)
- 確度: 一人の意見

#### 8.13 モバイルは主要な内容と操作を画面中央に。親指ゾーンを根拠にしない
- なぜ: 「下 1/3 が親指ゾーン」は一次研究の結論ではない。Hoober 本人が 2013 年の列を廃止と明言し、2017 年に「中央が最も正確で、上下の端は間隔を大きく空ける」へ改めた。
- 値: 観察(2013、780 人): 片手 49%、持ち替え 36%、両手 15%。2017 年の確かな数: 親指 1 本で触る人 75%、ただし片手持ちは半数未満。主要な内容と主要操作は中の半分〜3 分の 2、副次の操作とタブは上下の端、第 3 層は隅のメニュー。約 95% のタップが当たるサイズは中央約 7mm・隅約 12mm。物理寸法で設計し約 20% の誤差を見込む。危険な操作と無関係な操作は離す。
- 使わない場面: 下端への配置は「親指だから」でなく OS の慣習(iOS のタブバーは下)で理由を書く。macOS はウィンドウの下端に重要操作を置かない(HIG)。長いフォームの主ボタンは最後の項目の近くか下(NN/g)。
- 出典: Hoober(10)、NN/g(10)、Apple HIG(10)
- 確度: 実証あり(観察とメタ研究。広まった図は撤回済み)

#### 8.14 ナビは項目数・切替の頻度・OS の慣習で決める
- なぜ: 隠すと使われない。NN/g の実験(179 人・6 サイト・各 2 課題)でナビの使用率はデスクトップが 隠す 27% / 見せる 48% / 併用 50%、スマホが 隠す 57% / 併用 86%。
- 値: デスクトップは隠さない。スマホは最上位が 4 つ以下なら見せ、5 つ以上なら一部を隠すのも妥当。タブバーは約 5 以下で頻度が高いとき、多数で閲覧中心ならハンバーガー(ラベル「Menu」+画面内の横断リンク)、1 セッション 1 枝ならハブ。Apple のタブバーは最上位の区分の移動用(操作はツールバー)、1 語ラベル+アイコン、iPadOS は 5 以下。ナビに「Home」を入れない(ロゴが兼ねる。Flux)。時間差は一部有意でなく、課題がナビ使用を指示していない限界がある。
- 使わない場面: ハンバーガーを一律に否定しない。悪いのは重要なナビを隠すときだけ(Hoober)。Luke W の「ハンバーガー → タブバーでエンゲージメントが増えた」は数値の裏づけがない【弱】。
- 出典: NN/g(10)、Apple HIG(10)、Flux #12(17)
- 確度: 実証あり(限界あり)

#### 8.15 チェックアウト・申込: 次にすることと戻り道、安心の一言を置く
- なぜ: 決済は速く直感的で、すぐ払って去れることが目標。
- 値: 見出しで次にすることを伝える。ステッパーは各段に副題、未到達の段は不透明度を下げ、現在の段を太字に。戻るボタン。「まだ課金されません」と小さく書く。購入前に見返せるサイドバー(プランの詳細・切替)、お客様の声(円形の顔写真は彩度を落とす)、遷移元サイトの文脈(ナビ)。価格は数字を大きく、通貨と期間は小さく。カードは実物の縦横比、追加はカルーセル末尾、カード番号の読み取りと CVV の説明、「カードを保存」「既定にする」。ゲスト購入が見つからないと 60% が重大な困難なので、ログイン / 新規 / ゲストの 3 つの見出し(ゲストが先頭)で折りたたむ(Baymard)。
- 出典: Rachel How R1(15,16)、WP Pusher 事例(20)、Baymard(20)
- 確度: 一人の意見(R1・Schoger)。ゲスト購入は実証あり(Baymard)

#### 8.16 ボタンの並びは OS の慣習に従う。破壊的操作を既定にしない
- なぜ: 実験の決着はない。NN/g は「一貫性を外れて迷う時間のほうが高くつく」とする。
- 値: Apple は行なら肯定が trailing(右)・取消が leading(左)、縦積みなら肯定が上。Windows は肯定が左端、安全な操作が右端。Material は横並びで確定が最後(右)、積むと確定が最初。NN/g はユーザーの多いプラットフォームに従い、不明なら OK を先に、最も選ばれるボタンを既定にする(危険な操作は既定にしない)。Cancel を既定にしない(Apple)。
- 割れ(Web フォーム): Silver は主ボタンを入力欄の左端に揃える(拡大表示で右のボタンを見失う)。Wroblewski は取消を主ボタンの右にリンク風に置く。Jarrett は取消をボタンの下に置いて見つけにくくする。NN/g は Reset / Clear を避け、取消は送信ボタンよりずっと目立たなくする。既定: 理由に「慣習」と書き、取消は主ボタンより弱くする。
- 出典: Apple・Microsoft・MDC・NN/g(10)、Silver(10【弱】)
- 確度: 多数一致(慣習。実験なし)

#### 8.17 サインイン・登録: 15 則
- なぜ: 失敗の離脱を減らす。コンバージョンの数値は示されない。
- 値: 最初の欄にオートフォーカス(スクリーンリーダーで確認)、`type=email` など専用キーボード、blur で検証、ラベルをクリック可能に、パスワード要件を入力中に表示、パスワード表示トグル、ボタン文言は利益を示す、SSO、マジックリンク(有効 30〜60 分。コードならフィッシング耐性)、利用規約は同意チェックより通知(EU 等は例外)、サインイン / サインアップの語を離す(Register)、切替リンクはテキストリンク、ログインはメール、失敗理由を具体的に、リセット画面でメールを引き継ぐ。
- 使わない場面: Raptis の「ソーシャルログインは上に置くと転換が上がる」は根拠が示されない。
- 出典: Kennedy KS(18)、Raptis(18)
- 確度: 一人の意見

#### 8.18 番号付きは「順序が必須の手順」だけ。任意順は番号なしで状態を示す
- なぜ: 番号は順序を約束する。任意順の作業に番号を付けると、後続を無視してよい錯覚が生じる(Eventbrite で Step 7 の後を重要でないと誤解し、Step 8 のプライバシー設定を飛ばした例)。
- 値: 順序が決まった申請・セットアップ・レシピは番号付きで、全手順と現在位置を出す。設定やリファレンスは番号なしの見出し+状態バッジ(未入力・完了)。GOV.UK のタスクリストは番号でなく「まだ始められません」で依存を示す。NN/g のウィザードは順序が決まった手順にのみ。
- 出典: GOV.UK・NN/g(07)
- 確度: 多数一致

## 9. 部品(ボタン・入力・表・カード・ナビ)

#### 9.1 タッチ領域は、見た目と別に当たり判定で満たす。最小と推奨を分けて書く
- なぜ: 太い指でも押せるように。値の根拠が物理量・OS・規格で別々なので、混ぜると訂正が効かない。
- 値: WCAG 2.5.8 AA は最小 24×24 CSS px(または 24px の円が他と重ならない間隔)。2.5.5 AAA は 44×44。Apple は 44×44pt(visionOS は 60pt)。Google は 48×48dp ≈ 9mm、ターゲット間 8dp 以上、見た目 24dp のアイコンに余白を足して 48dp に。Parhi ら(2006)の親指の実験は単発 9.2mm・連続 9.6mm 四方で足りる(被験者数と端末は未確認)。Microsoft は理想 9mm・最小 7mm(弱)。換算は 24px ≈ 6.4mm、44pt ≈ 6.9mm で、Parhi と Google の 9mm より小さい。
- 訂正: 実務者の「ボタンは高さ 44px 以上」(Rachel How)と Schoger の 40〜48px は矛盾しない。タッチ対象なら 44 以上にすれば両方を満たす【推論】。Dannaway の「WCAG の 44pt」は誤記の疑い(AA は 24、44 は AAA)。Dannaway の 48pt は Material 寄り。
- 出典: WCAG・Parhi・Google・Apple・Microsoft(03,11)、Rachel How・Kole(15,16)、Dannaway(18)
- 確度: 実証あり(最小は規格、推奨は測定値)

#### 9.2 ボタンの高さは「行高 + 上下パディング」で組み立て、段は 24 / 32 / 40 / 48
- なぜ: 数値をトークンの倍数に載せれば、値の理由が言える。
- 値: Carbon のボタンは 24 / 32 / 40 / 48 / 64 / 80。ラベルは 14px(expressive は 16)、アイコンは 16px(expressive は 20)。隣り合うサイズの混在は不可。例: 14px の行高 20 + 上下 10 = 40、+6 = 32。16px の行高 24 + 上下 12 = 48【推論】。水平パディングは垂直の 2 倍(Hobday #22)。密度モードは高さを 4px 刻みで増減しパディングは変えない(Material)か、行高を変える(DADS)。ゴーストボタンの幅の目安は高さの 2 倍(Kole K01)。
- 出典: Carbon(11)、Hobday(18)、Material(11)、Kole K01(16)
- 確度: 多数一致(Hobday の 2 倍と Kole の目安は一人の意見)

#### 9.3 リンクとボタンを見分けさせる。押せないものからボタン風を外す
- なぜ: 期待と実際を一致させる。見た目が同じものは同じように動く。
- 値: 単独のリンク(ヘッダ・フッタ・本文を除く)はボタンのほうが分かりやすい。細い輪郭線で囲むとボタンに見える。ボタンに見える「ラベル」は見出しにし、外部リンクのアイコンを付ける(Transistor)。クリックできるカードは行動ボタンを置く。
- 出典: Raptis(18)、Dannaway #3(18)、Malewicz #6(17)、Transistor 事例(20)
- 確度: 多数一致

#### 9.4 入力欄のラベルは常に見える位置(欄の上)に置き、placeholder を代わりにしない
- なぜ: placeholder は入力で消え、エラー時に確認するために消す羽目になる。値を入れると説明も消える。
- 値: GOV.UK はすべての入力に「たいてい見える」ラベルを上に。DADS はサポートテキストをラベルと欄の間に置き、placeholder を代用してはならない。SmartHR は placeholder を原則非推奨。Baymard はモバイルで欄の上(横向きを除く)。入力例は placeholder でなく欄の外に出し、ラベルの繰り返しにしない(Raptis #32)。NN/g は非常に長いデスクトップのフォームでは横。
- 実験: Penzo(2006)は、ラベル上置きの視線移動が約 50ms、左揃えが約 500ms、右揃えが約 170〜240ms(短い必須項目のみ。実ページに似せていない)。Napier 大の 11 人の研究は右揃えが最速で上揃えがほぼ同等と逆。Jarrett は単純なフォームで別の結果を指摘。「約 2 倍速い」とするブログは原典が確認できない。
- 出典: GOV.UK・DADS・SmartHR・NN/g(07)、Baymard(20)、Penzo・Napier(10)
- 確度: 実証あり(限定条件つき)

#### 9.5 ヒントは短く 1 文、多数の利用者に要るものだけ。必須情報は常設テキストに
- なぜ: スクリーンリーダーは操作のたびにヒント全体を読む。placeholder やツールチップに入れた必須情報は見落とされる。
- 値: GOV.UK のヒントは 1 つの短い文・句点なし・リンクなし。DADS は入力形式の条件や例を簡潔具体的に、必要十分を先に。SmartHR はヘルプと入力例を欄の上、操作に影響しない補足を下。Carbon の helper-text は 12/16 でフィールド名の下専用。「この段落を消すと誰が何に迷うか」を 1 行書く【推論】。
- 使わない場面: 初回やまれにしか使わない画面(申請・設定)は説明を増やしてよい。毎日使う業務画面は説明を 1 項目 1 文以下に。
- 出典: GOV.UK・DADS・SmartHR・Polaris・NN/g・Carbon(07)
- 確度: 多数一致(説明を減らすと完了率が上がる定量実験は見つからなかった)

#### 9.6 フォームの欄を減らす
- なぜ: 見えている欄数が多いと気後れする。複雑さは設計で直せる。
- 値(Baymard、英語圏のチェックアウト): 平均 11.3 欄(2019 年は 12.7)、8 欄で足りるサイトが大半、米国の平均は既定で 23.48 の入力要素(14.88 欄)で理想は約 12。20〜60% 削減できる。離脱は「長い・複雑」が 17%、平均離脱率 70.19%、単なる閲覧が 42%(設計では減らせない)。設計の改善で大規模サイトの転換率が約 35% 伸びる試算。手段: 任意欄はリンクの奥へ、不要な欄を削除、自動入力、多ければ折りたたむか複数ステップ。氏名・電話・郵便番号は 1 欄に(89% のサイトが氏名を複数欄にし、42% が姓の欄に氏名全部を入れた。住所 2 行目は 75% が既定表示で 30% が止まった)。
- 使わない場面: 日本語はふりがなの要件で姓・名を分ける(5.16)。数値は Baymard 記事の記載で、有料レポート本体は未読。31% と 32% の食い違いが記事内にある。
- 出典: Baymard(20)
- 確度: 実証あり(自社計測。英語圏)

#### 9.7 欄ごとの設計: 略語を避け、入力形式は制限せず、自動入力は編集可能に
- なぜ: 利用者は欄を文脈の外で読み、様々な形式で書く。
- 値(Baymard): セキュリティコードは「Security Code」と書き、カード上の位置をサムネイルかツールチップで示す(38% がここで止まった。CVV / CID は略語で分からない)。入力形式の例は 89% が無視するので、入力マスクで整形し制限は緩く。自動入力された値は静的な文字でなく編集できる欄で見せる(誤検出に気づけない)。「電話」でなく「請求先の電話」。
- 出典: Baymard(20)
- 確度: 実証あり

#### 9.8 検証は欄を離れたとき(blur)に。直したら即座にエラーを消す
- なぜ: 送信後にエラーを探すのは負担。早すぎる検証と消えないエラーは不信を生む。
- 値: 桁数が決まっている欄は桁数に達したときに検証。正しい欄には確認の印。31% のサイトにインライン検証がなく、53% がカード番号の Luhn 検証をしない(Baymard)。モバイルは `type` と `inputmode` を設定し、autocorrect / autocapitalize を無効に(上位 50 モバイルサイトの 60% が 5 つの最適化のうち 2 つを満たさない)。NN/g の指針に沿ったフォームは初回エラーなしで送信できた割合が 78%、違反は 42%(CHI 2014。個別の配置でなく一式の効果)。
- 出典: Baymard(20)、NN/g(10)、Kennedy KS(18)
- 確度: 実証あり

#### 9.9 ドロップダウンは最後の手段にする
- なぜ: 選択肢が隠れ、操作が増える。
- 値(Kennedy の ABD): 2 択は、既定の答えがなく同程度ならセグメント、既定オフ / 保存時反映ならチェックボックス、即時反映ならスイッチ。2〜5 択は縦のセグメント、補助要素があるならラジオ、カード。多数はタイプアヘッド。日付は近未来に偏る(予約・フライト)ならカレンダー、分散が大きい(誕生日)ならテキスト入力。個数は少ない値が多いならステッパー。
- 使わない場面: 既定がほぼ変わらない、選択肢が少ない、デスクトップ。
- 出典: Kennedy K4・K100(18)、Raptis #22(18)
- 確度: 一人の意見

#### 9.10 チェックボックスとラジオは慣習どおりに使う
- なぜ: 利用者は過去の経験から操作を予測する(メンタルモデル)。「最も当てはまるもの 1 つ」にチェックボックスを使うと複数選べると誤解される。
- 値: 単一選択はラジオ。ラジオは大きく、非選択も分かるように(Rachel How)。チェックボックスは未選択だと細い枠だけ、選択で塗りとチェック。
- 使わない場面: 文化で異なる場合もある。
- 出典: 9re-pe(19)、ソシオメディア HIG(19)、Kole K09(16)、Rachel How(15)
- 確度: 多数一致

#### 9.11 迷う判断には既定値を置く
- なぜ: 選択肢の違いが名前から分からないと利用者は進めなくなる。
- 値: 多くの人が選ぶ値を推奨値として先に選んでおく。最後に行った操作を覚える(HIG の「タスクコヒーレンス」)。
- 出典: 9re-pe(19)、ソシオメディア HIG(19)
- 確度: 一人の意見

#### 9.12 確認ダイアログの選択肢は 2 つ以下。3 つ以上はアクションシート
- なぜ: ダイアログは選ぶまで他の操作を止める。
- 値: 3 つ以上のときは、破壊的操作を指から最も遠い上に、キャンセルを下に置く。キャンセル後に戻る画面(元か最初か)を設計し、保存後は完了を伝える。
- 出典: classmethod(19)
- 確度: 一人の意見

#### 9.13 危険操作は目立たせず、既定を目立たせる。確認と取り消しを付ける
- なぜ: 破壊的操作が目立つと誤操作を誘う。理由は速度でなく事故の回避で書く【推論】。
- 値: 色・大きさ・種類・位置の複数の特徴で副に見せる。削除は確認(インライン / ポップアップ)と、可能なら取り消し。確認ボタンは「はい / いいえ」でなく文で書く。破壊的操作は確認モーダルの中以外では主にしない(Refactoring UI)。キャンセルをグレーにするなら濃いグレー(薄いと disabled に見える)。破壊的操作は赤(iOS HIG)。
- 出典: Raptis #23-25(18)、Refactoring UI(18)、classmethod(19)、Schoger(20)
- 確度: 多数一致

#### 9.14 表: 薄い罫線、数値は右、列見出しは列に合わせる
- なぜ: 表は比較して読む。罫線が強いと行が読みにくい。
- 値: 行に薄い下罫線(Carbon)。縦罫は付けないか 1px の極薄。ゼブラは hover・無効・選択の状態と背景が衝突するので、対話型の表では避け、非対話の閲覧用だけ(Pencil & Paper【弱】。Ström は避ける、NN/g は横の行を結ぶ)。中央揃えは使わない。背景色は合計などデータの種類が変わる所だけ。行の補助操作は hover 時のみ、最重要の表だけ別の強弱にする(Spike.sh)。比較表は行を揃え、ラベル列を 1 つにする(ラベルが全列で重複するのはよくある誤り。WSS)。行高は毎日使う業務で 32〜40、通常 48、2 行入るなら 64(Carbon)。識別する主役列を左端【推論】。
- 出典: Carbon・Pencil & Paper・NN/g(07)、Ström(10)、Spike.sh・WSS(20)
- 確度: 多数一致

#### 9.15 カードは内容の入れ物。向きと位置をそろえ、重ねない
- なぜ: 向きや位置がばらばらなカードは「ガレージセール」に見える。反復で利用者が画面を学ぶ。
- 値: カード外側 20・内側 16(Malewicz)。一覧のカードは説明文を省略して判断に要る情報だけ(1.11)。カードの余白は広く、線か背景色で分ける(Kole K15)。重ねない(2.6)。実物の比率があるもの(クレジットカード)は実寸の縦横比に。
- 出典: Showalter J1(16)、Kole K09・K15(16)、Malewicz(17)、Rachel How(15)
- 確度: 多数一致

#### 9.16 チップ・タグは「種類が決まったデータ」に。×を削除に見せない
- なぜ: ピル形+×のタグは、削除されるものと誤解される。ボタンとタグが見分けにくいと操作が読めない。
- 値: フラグのタグは行の表+チェックボックスで完了にし、重大度は赤い太字+赤い点(Resolute)。タグはステータスにだけ色を付け、操作ボタンと別の見た目に(Spike.sh)。既定は灰色で、差があるものだけ色づけ(1.1)。
- 出典: Kole K04(16)、Resolute・Spike.sh(20)
- 確度: 一人の意見

#### 9.17 ナビ項目は「アイコン + 短いラベル」で現在地を示し、親子で並べる
- なぜ: 現在地が分からないと迷う。太字にすると隣がずれる。
- 値: 各項目にアイコン、現在地を強調(Raptis #36)。現在地は薄い背景+橙の細線(Bad About)、太さは固定して色だけで示す(Transistor)。タブは選択中だけ色の線(WSS の虹色タブを直した)。使用頻度の高低を罫線で分け、文字を大きく(Resolute)。区分見出しはリンクより小さく薄く、大文字+字間(Schoger)。親子で並べ替え、重複リンクを消す(WSS)。
- 出典: Raptis(18)、Bad About・Transistor・Resolute・WSS(20)、Schoger(20)
- 確度: 多数一致

#### 9.18 ツールチップは補足専用。必須情報を入れず、タッチには「?」を置く
- なぜ: hover のみのラベルは操作コストが高く、タッチでは使えない。
- 値: 短く、キーボードでも出す。モバイルはタップできる「?」を横に置く(Raptis #34)。ショートカットはボタンの横に表示。遅延 tooltip は 1000ms 以上の hover で出す(アイコンが多くラベルの場所がないとき。Kole K13)。初心者のダッシュボードにほぼ必ず欠けているのは tooltip(Kole K04)。
- 出典: NN/g(07)、Raptis(18)、Kole(16)
- 確度: 多数一致

#### 9.19 ポップオーバー・モーダル・ページの使い分け
- なぜ: 文脈の複雑さと戻りやすさで決まる。
- 値: ポップオーバーは文脈が単純で、外をクリックしても害がない設定向け。モーダルは文脈が複雑でも同じページに留めたいとき(ブロックする)。確認の toast を足す。恒久的で大きいものは新しいページにして、戻るボタンかパンくずを必須にする(Kole K15)。右が空いたフライアウトはモーダルにする(K08)。下から出る = 一時的な操作、左から出る = 進行(K10)。
- 出典: Kole K08・K10・K15(16)
- 確度: 一人の意見

#### 9.20 グラフの種類はデータの形で選ぶ
- なぜ: 種類を誤ると誤読を生む。月次合計を折れ線にすると日次があるように見える。
- 値: 円は合計 100% のときだけ、棒は重なるカテゴリ、折れ線は時系列(Kennedy K100 #32、Raptis #37)。軸と目盛り、格子線、直接ラベル(8.10、6.18)。
- 出典: Kennedy(18)、Raptis(18)
- 確度: 一人の意見

#### 9.21 検索は最重要の機能なら目立たせ、閲覧が主なら小さくして押したら開く
- なぜ: 目的に応じて明示度を変える(1.13)。
- 値: 検索が最重要の社内ツールは、上部バーをブランド色にして白い入力欄にする(暗い背景の入力は彩度を落とす。Resolute)。閲覧が主になったら検索欄を小さくして押したら開く(Kole K02)。
- 出典: Resolute 事例(20)、Kole K02(16)
- 確度: 一人の意見

## 10. 状態と端の場合

#### 10.1 操作には必ず反応を返す。ボタンは最低 4 状態、入力は focus とエラー
- なぜ: 反応がないと壊れたと思われる。小さな瞬間が体験の良し悪しを分ける。
- 値: ボタンは既定・hover・押下・無効(必要なら読み込みのスピナー)。入力は focus、エラー(赤い枠+メッセージ)、任意の警告(Kole K01)。hover は少し明るく、押下は少し暗く、無効は彩度を落とす。モバイルは hover がないので押下時に少し暗い灰色にして「押し込む」感じを出す(K06)。画面遷移が遅いときは、押したボタンを灰色にして読み込みの輪を付ける(K05)。
- 出典: Kole K01・K05・K06(16)
- 確度: 多数一致

#### 10.2 hover・選択でサイズ・太さ・ケースを変えない
- なぜ: レイアウトがずれる。ナビの現在地を太字にすると隣がずれる。
- 値: 色・背景・影・下線・微小な動きで示す。hover の動きは 100〜250ms(Kennedy K100 #6)。押下で影を小さく / 消し、hover・ドラッグで影を増す(Refactoring UI)。
- 出典: Kennedy K2・K100(18)、Refactoring UI(18)、Transistor(20)
- 確度: 多数一致

#### 10.3 幸せな道だけでなく、空・読み込み・成功・エラーと「見えない部分」を設計する
- なぜ: 実アプリが扱うのはその全て。初心者の画面には状態がない(Kole K05 の兆候)。
- 値: 空状態は「アニメ + 文言 + 次の一手」(dub.co)。白紙でなくテンプレートを置く(Raptis #26)。サンプルデータで最初から動作が見える状態にする(Basecamp。Kennedy K4)。デプロイ結果は即座に通知(Vercel)。hover で文脈を出す(Linear)。見えない部分: コピー用のチップ、コメントを示す小さな三角、tooltip、お知らせ、オンボーディング(Kole K04)。
- 出典: Kole K04・K11・K15(16)、Raptis(18)、Kennedy K4(18)
- 確度: 多数一致

#### 10.4 エラーは「何が起きたか + 原因 + 次の行動」を、矛盾なく、欄の近くに書く
- なぜ: 「保存されました」と「接続できませんでした」が同居すると混乱する。送信後に条件を指摘されて入力が消える体験は離脱を招く。
- 値: SmartHR の構成は事象・原因・対処で、全部載せられないときの優先は原因・対処・事象。能動態の簡単な言葉で例を添える。日本語は欄の下(DADS)。「Incorrect password」だけにせず失敗理由を具体的に(Kennedy KS)。条件と入力例は事前に示す。赤いアイコンで一目でエラーと分かるようにし、別の場所へ飛ぶリンクに外へ出る印を付ける(Mizko #3)。
- 出典: SmartHR・DADS(07,19)、9re-pe(19)、Kennedy KS(18)、Mizko(17)
- 確度: 多数一致

#### 10.5 エラー画面の行動は 1 つに絞る
- なぜ: 迷わせない。選択肢を並べるより、運営が一番効くと思う道を先に示す。
- 値: 「Cancel / Try again / Contact / Exit」をやめ「Try again」だけにする。2 回失敗したら「サポートに連絡 / 後で再試行」を出す。
- 出典: Mizko #3(17)
- 確度: 一人の意見

#### 10.6 待ち時間は進捗を見せる。フィードバックがないことが嫌われる
- なぜ: 待たされること自体より、何も起きていないように見えることが嫌われる。
- 値: 進捗バーと終了予測、待ち中に Tips、バックグラウンド処理にして他の操作を許す(9re-pe)。単語ごとのストリーム、スケルトンのきらめき、思考の過程の表示(Kole K14)。依頼した処理は「{処理名}を受け付けました」と書き「予約しました」を使わない(SmartHR)。表示遅延と最小表示時間でちらつきを防ぐ(Vercel)。楽観的 UI: Gmail は削除したら即座に消す(Kole K15)。
- 出典: 9re-pe(19)、SmartHR(19)、Kole K14・K15(16)、Vercel(07)
- 確度: 多数一致

#### 10.7 実データの端の場合を先に考える
- なぜ: 端の場合を後で考えると、想定外の崩れに悩む。
- 値: 長い名前は省略。明るい画像の上の保存アイコンには円を敷いてコントラストを保証(Kole K02)。有効期限と CVV が切れて見えない(Rachel How)。日本語の長文と短文、固定幅ボタン(5.21)、固定高さ(4.17)、320px を含む複数幅、ライト / ダーク、空 / エラー(03)。
- 出典: Kole K02(16)、Rachel How(15)、03
- 確度: 多数一致

#### 10.8 次に何が起きるかを事前に言う。安心の一言を置く
- なぜ: 最小驚きの原則。不安は離脱になる。
- 値: 「まだ課金されません」と小さく書く(Rachel How)。無料キャンセルを前に出す(R2)。課金の有無、音声メッセージが自動投稿かなどを事前に言う(Raptis #27-28)。
- 出典: Rachel How(15,16)、Raptis(18)
- 確度: 多数一致

#### 10.9 作成の直後に次の一手を出し、スキップを用意する。フローは紙に箱で描く
- なぜ: 流れの途中で止まらせない。フローを描くと抜けが見つかる。
- 値: Notion はチームスペース作成直後にメンバー追加を促し、スキップも用意する。オンボーディングは名前とメール → 確認(止めるか、やさしい催促か、どちらも正解)→ チーム人数 → 個人とチームで分岐(Kole K03)。アレルギー選択にスキップと検索がなかった例(K05)。
- 出典: Kole K03・K05・K11(16)
- 確度: 一人の意見

#### 10.10 オンボーディングは操作の瞬間に、文脈ヘルプとして出す
- なぜ: 起動時のチュートリアルは飛ばされ、すぐ忘れられる。
- 値: その場の操作に紐づく pull 型の文脈ヘルプ。簡単に閉じられ、再度見つけられる。慣習(歯車 = 設定)は説明しない。最初の 1 操作に tooltip、次にチェックリスト。最初から 6 項目のモーダルは忘れられる(Kole K04)。
- 出典: NN/g(07)、Kole K04(16)
- 確度: 多数一致(割合や人数は NN/g の記事にない)

#### 10.11 無効状態を「薄い灰の塗り」だけに頼らない
- なぜ: 薄い灰の塗りのボタンは無効に見える。有効な副ボタンと区別がつかなくなる。
- 値: 無効は別の仕組みで示す【推論】。無効の行は薄くする(Kole K04)。
- 出典: Dannaway #2(18)、Kole K04(16)
- 確度: 要確認

## 11. アイコンと画像

#### 11.1 アイコンは 1 セットに統一する(線幅・角・塗り)
- なぜ: 塗り・線の太さ・スタイルがばらばらだと素人に見える。
- 値: 同じライブラリ(Phosphor・Feather・Lucide)から、線の太さと角で選び、SVG で取る。塗りと線を混ぜない(Schoger)。選択状態だけ塗りにするのは慣習。絵文字をアイコンにしない(Kole K08)。線幅は文字の太さに合わせる。Lucide は 24px グリッドで 2px が既定、小さいほど太く(≤16px で 2.25px)大きいほど細く(≥32px で 1.5px)(検索のみ、公式未確認)。
- 使わない場面: 領域が離れていれば違うスタイルも許される(ナビのアイコンと料理のアイコン)。
- 出典: Kole K05・K08(16)、Schoger(20)、Malewicz #5・#6(17)、Lucide(11【弱】)
- 確度: 多数一致(線幅の数値は要確認)

#### 11.2 アイコンの大きさは隣の文字の行高に合わせ、設計サイズで使う
- なぜ: 文字との釣り合いが取れる。拡大すると不格好になり、縮めると潰れる。
- 値: 行高 24px なら 24px(Kole K01)。Carbon は 16 / 20 / 24 / 32px で、16 と 20 は IBM Plex の 14 と 16px に釣り合うよう最適化。20px のアイコンは 14px・行高 20 の文字向け(react-magma【弱】)。小さいアイコンを拡大せず、円(背景色)の上に置いて大きく見せる(Refactoring UI、Schoger #6)。
- 出典: Kole K01(16)、Carbon(11)、Refactoring UI(18)
- 確度: 多数一致

#### 11.3 アイコンは隣の文字より重く見える。色を弱めるか、文字を濃くする
- なぜ: 塗りのアイコンは線の文字より重い。
- 値: アイコンの不透明度を下げる / 薄い色にする(Hobday #28、Refactoring UI、Schoger #12)。逆に文字を濃くし 4.5:1 を保つ(Dannaway #14)。メタ情報のアイコンは文字より軽く小さく(Bad About)。
- 出典: Hobday・Refactoring UI・Schoger・Dannaway(18)、Bad About(20)
- 確度: 多数一致

#### 11.4 アイコンだけに頼らない。操作系には常設のラベルを付ける
- なぜ: 普遍的に通じるのは home・print・虫眼鏡など少数。hover のみのラベルは操作コストが高くタッチで使えない。ラベルのないボタンは支援技術から見えない【弱】。
- 値: 探して 5 秒を超えたら通じていない(5 秒ルール。NN/g)。設備の有無のアイコンが初見で伝わるか確かめる(S/M/L と合わず失敗した例)。
- 割れ: Kole は有名なアイコン(家・しおり・人)はラベル不要、そうでなければ tooltip。Bokardo は「ラベルは常に勝つ」、Refactoring UI は「ラベルは最後の手段」。既定: 操作(ボタン・ナビ)はラベルを残し、繰り返す補助情報から説明文を削る。アイコンだけにするのは普遍の 4 種(home / print / search / close)か、tooltip と `aria-label` を付けた密なツールバー【推論】。
- 出典: NN/g(03)、Kole K05(16)、9re-pe(19)、Bokardo・Uxcel(03)
- 確度: 多数一致

#### 11.5 画像の上の文字は、重ねの層で読みやすさを保証する
- なぜ: 背景の明るさが場所で変わるので、文字だけでは読めない箇所が出る。
- 値(Kennedy の 5 法): ①全面オーバーレイ(黒約 35%)、②半透明の黒い箱 + 白文字(最も確実)、③背景ぼかし(暗めに)、④床フェード(中央 0% → 下端約 20% の黒 + 白文字 + 軽い影。光は上から来る前提)、⑤スクリム(楕円の放射グラデーション)。何もしないのは、暗くてエッジの少ない画像と白文字のときだけ。画面幅ごとに確認する。Kole は全面の暗幕でなく線形グラデーション、さらに進めるならグラデーションの上に段階的なぼかし。背景写真の彩度を落としてブランド色を乗算で重ねる(WSS)。
- 出典: Kennedy K2(18)、Kole K01(16)、Refactoring UI(18)、WSS・Learn UI 事例(20)
- 確度: 多数一致

#### 11.6 画像は階層と走査の助け。ただし重要な画像を情報の後ろに隠さない
- なぜ: 色の塊として目を止め、拾い読みしやすくなる。高価な宿の画像を情報の後ろに隠すのは損。
- 値: 文字は画像の焦点を邪魔しない位置に置き、背景は静かな画像にする(Kole K03)。
- 出典: Kole K01・K03(16)、Rachel How R2(16)
- 確度: 多数一致

#### 11.7 透明 PNG・アバター・ユーザー投稿画像は縁と容器で整える
- なぜ: 背景色と馴染まず、重なりで境界が消える。
- 値: 透明 PNG には背景色と同じ薄い縁と背景。ユーザー投稿画像は固定コンテナ+ごく薄い内側の影。重なる画像には背景色の縁を付けて隙間を作る(Raptis #30-31、Refactoring UI、Schoger #29)。円形の顔写真は彩度を落とす(WP Pusher)。
- 出典: Raptis・Refactoring UI・Schoger(18)、WP Pusher(20)
- 確度: 要確認(図解のみで根拠の説明が薄い)

#### 11.8 画像の読み込みは遅さの主因。カルーセルは隠す・操作が小さい・優先順位が弱い
- なぜ: 重い画像は体験を遅くし、カルーセルは重要な内容を見落とさせる。
- 値: 無限スクロールより「もっと見る」(利用者が制御でき、フッターに届く。Kole K02)。
- 出典: Kennedy K100 #8・#66(18)、Kole K02(16)
- 確度: 一人の意見

## 12. 動き

#### 12.1 既定は動きなし。付けるのは、理由を 1 つ言えるときだけ
- なぜ: 動くものは目で追われる。動きのための動きは、ナビを難しくする。
- 値: 効くのは、注意を向けさせる、原因と結果を示す(依存項目が現れる)、状態の連続性を示すとき。害になるのは、周辺視野の動き、繰り返し(2 回目は「うんざり」、3 回目は「腹立たしい」)、目的のない装飾、頻用要素の長い演出、読んでいる文章を動かす動き。原因と結果の関係は操作から 0.1 秒以内に始める。再生を飛ばせるようにする(NN/g)。
- 出典: NN/g(07)、Kole K02・K10(16)、Apple HIG(03,07)
- 確度: 多数一致

#### 12.2 頻度が高い操作ほど短く、あるいは無くす
- なぜ: 何十回も繰り返す操作に演出があると遅く感じる。
- 値: 毎日・何十回も使う業務 UI(コマンド・キーボード操作・リスト選択)は動きなしか 0〜70ms(リスト hover は 50ms)。Carbon: fast-01 70ms(ボタン・トグル)、fast-02 110ms、moderate-01 150ms、moderate-02 240ms、slow-01 400ms、slow-02 700ms。Atlassian: 0ms フォーカス、50ms リスト hover、100ms 押下とポップアップ退場、150ms 強調 hover とポップアップ入場、200ms モーダル退場、250ms モーダル入場、400ms ページ遷移、600ms オンボーディング・全画面。
- 出典: Carbon・Atlassian・Emil Kowalski・Apple(03,07)
- 確度: 多数一致(高頻度ほど動きなしを測った実験は見つからなかった)

#### 12.3 UI の動きは 100〜400ms、500ms を超えない
- なぜ: 500ms では「重荷」になる。入場は退場より少し長く。
- 値: NN/g は全体 100〜400ms、単純なフィードバック(チェック・トグル)約 100ms、モーダル 200〜300ms、400ms は大画面の大きな移動だけ、入場 300ms / 退場 200〜250ms。M3 は short1〜4 = 50 / 100 / 150 / 200ms、medium1〜4 = 250 / 300 / 350 / 400ms、long = 450〜600ms、extra-long = 700〜1000ms。Emil は 300ms 未満で、180ms のセレクトが 400ms より応答がよい。

| 文脈 | 値 | 出典 |
|---|---|---|
| ボタン・トグル・チェックの状態変化(色 / 不透明度) | 70〜110ms、ease-out | Carbon、NN/g |
| ドロップダウン・ポップオーバー・小さい展開 | 150ms | Carbon、Atlassian |
| モーダル・ドロワー・トースト | 入場 200〜250ms / 退場 150〜200ms | NN/g、Atlassian |
| ページ遷移・大きな領域の移動 | 300〜400ms(500ms を超えない) | NN/g、Atlassian |
| 初回・まれな場面(オンボーディング・達成) | 400〜600ms | Carbon expressive、Atlassian |

- 使わない場面: 読んでいる最中の本文・表は動かさない。
- 出典: NN/g・Carbon・Atlassian・M3(07)、Emil(03)
- 確度: 多数一致(NN/g は観察、数値は各 DS)

#### 12.4 イージング: 入場は ease-out、退場は ease-in、画面内の移動は ease-in-out
- なぜ: 入場は減速して着地し、退場は加速して去るのが自然。CSS 組み込みの easing は弱い。
- 値: Carbon productive の標準 `cubic-bezier(0.2, 0, 0.38, 0.9)`、入場 `(0, 0, 0.38, 0.9)`、退場 `(0.2, 0, 1, 0.9)`。expressive の標準 `(0.4, 0.14, 0.3, 1)`。M3 の standard / emphasized は `(0.2, 0, 0, 1)`、emphasized-decelerate は `(0.05, 0.7, 0.1, 1)`、emphasized-accelerate は `(0.3, 0, 0.8, 0.15)`。退場は入場より 50〜100ms 短く(Atlassian)。
- 出典: Carbon・M3・Atlassian・NN/g(07)、Emil(03)
- 確度: 多数一致

#### 12.5 実装の約束: 押下 `scale(0.97)`、入場は 0.9 以上から、`transition: all` を使わない
- なぜ: `scale(0)` から始めると不自然。layout を起こすプロパティのアニメは重い。
- 値: 押下 `scale(0.97)`、入場は `scale(0)` から始めず 0.9 以上(例 0.93)、`transform-origin` はトリガー基準。`transition: all` 禁止。`width` / `height` / `top` をアニメしない。1 遷移で動かすのは 1〜2 プロパティ。エラーやフォーカスを遅い入場の後ろに置かない。重ねた影をアニメしない。これらは grep で検査できる。
- 出典: Emil Kowalski(03。個人ブログ)、Vercel・Atlassian(07)
- 確度: 多数一致

#### 12.6 `prefers-reduced-motion` を必ず見る。動きだけで状態を伝えない
- なぜ: 前庭障害の利用者に、視差・カルーセル・スクロール乗っ取りは害になる。
- 値: 位置・拡大の動きを消し、不透明度の遷移は残す【推論】。WCAG 2.3.3(AAA)は操作で起きる動きを無効にできること。Apple は Reduce Motion のときは最小化または除去。
- 出典: WCAG・Apple HIG・NN/g(03,07)
- 確度: 実証あり(規格)

#### 12.7 スクロールの乗っ取り・視差は情報ページで使わない
- なぜ: 情報ページでは予想外で、表に固定高さのスクロールが入れ子になる。
- 値: 乗っ取りはほとんど使わない(Kole K02)。例外: 製品の最初の一目のため、スクロールで画像がダッシュボードに変わる。製品が下で初めて出る装飾は避ける(K10)。視差は大きな余白で(K12)。
- 出典: Kole K02・K10・K12(16)、WSS 事例(20)
- 確度: 多数一致

#### 12.8 ボタンにはほぼ必ず小さな動きを。hover で説明を出すなら文を増やさない
- なぜ: 反応が伝わる。hover で言葉の説明を見せれば、文も画像も増やさずに済む。
- 値: 名前札の hover は 500ms、stiffness 636、damping 24(Kole K13)。遅延 tooltip は 1000ms 以上の hover。検索アイコンは押すと広がる。コピーの確認は、チップが滑り上がる。
- 出典: Kole K01・K02・K13(16)
- 確度: 要確認(自動字幕の数値。スプリングの指針は一次未確認)

#### 12.9 動きで焦点を作る・導く。ただし焦点を競合させない
- なぜ: 動きは注意を引く力が強い。
- 値: スクロールで画面を切り替え、人物が現れる前に地を作ってから登場させる。大きなロゴを動かして焦点にしてから隅へ移す(Flux)。モーダルが広がる小さな驚き、下から出る = 一時的な操作、左から出る = 進行(Kole K10)。
- 出典: Flux #13・#15(17)、Kole K10(16)
- 確度: 一人の意見

#### 12.10 遊びの動きは、雰囲気を作る場面(LP・404)だけ
- なぜ: 製品の中では邪魔になる。
- 値: 星は回りながら出る、気球は画面外から飛んできてゆっくり上下する。装飾にはイージングを付ける。404 は利用者がそこにいるはずのない場所なので遊んでよい(Kole K12)。
- 使わない場面: 製品の画面。ブランド性の強い LP 向け。
- 出典: Kole K12(16)
- 確度: 一人の意見

#### 12.11 動きの時間は数トークンに絞る(100 / 150 / 250 / 400ms 程度)
- なぜ: DS は 6 段(Carbon)、8 段(Atlassian)、16 段(M3)と多いが、使う場面は少ない。
- 値: 例 100 / 150 / 250 / 400ms【推論】。
- 出典: Carbon・Atlassian・M3(07)
- 確度: 要確認

## 13. 文言

#### 13.1 ボタンは「動詞 + 目的語」で具体的に。「はい / いいえ」「送信」を避ける
- なぜ: 押すと何が起きるかを瞬時に示す。利用者は説明文を読まずボタンだけ見ることがある。
- 値: 「追加」でなく「カードを追加」、「予約中」でなく「今すぐ予約」(Rachel How)。ボタンのラベルは動詞の終止形(SmartHR)。「削除」「キャンセル」(kintone)。「Continue / Submit」より得られるものを書く(Kennedy KS)。見出しは次にすることを伝える。
- 出典: Rachel How(15,16)、SmartHR(19)、classmethod(19)、Kennedy KS(18)
- 確度: 多数一致

#### 13.2 操作語は 1 語 1 意味に固定する
- なぜ: 同じ操作が別の言葉で書かれると、利用者が言葉の読解に注意を使う。
- 値(SmartHR): 取り消し(実行済み)/ キャンセル(未実行)/ 中断(実行中)。追加(新規作成)。複製(別データ作成。「コピー」は貼り付けを伴う場合のみ)。解除(元の状態に戻す)。差し戻し(承認者が修正を求める)。書き出す(「エクスポート」は他ソフトの表記を指す場合のみ)。再読み込み(「更新」は保存に使うので避ける)。移動(「遷移」は使わない)。ボタンは「押す」(クリック / タップとは書かない)、リンクは「開く」、スイッチは「有効にする / 無効にする」。「使用」を基本に、役立つニュアンスを出すときだけ「利用」。「キャンセル」はキャンセル以外の意味で使わない。
- 使わない場面: 公文書や他ソフトの UI 表記をそのまま引く場合。
- 出典: SmartHR(19)
- 確度: 一人の意見(一社。最も具体的な表)

#### 13.3 見出しは「どんな問題を解くか / 誰か」を言う。最も目立つ面を「Welcome」とロゴの繰り返しで使い切らない
- なぜ: 一番大事な面を、ロゴで済む内容や重複する文言で使うのは浪費。
- 値: 「Trusted software development company since 1999」(誰か・信頼の根拠)が「Welcome to King Technology」より強い(Flux #16)。ナビに「Home」を入れない(ロゴが兼ねる)。Kole は見出し 7 語、小見出し 14 語を目安にする(英語の語数。日本語での換算は要確認)。
- 出典: Flux #12・#16(17)、Kole K03(16)
- 確度: 一人の意見

#### 13.4 友だちのような言葉にし、内輪の言葉・専門用語を避ける
- なぜ: 利用者の言葉で書けば、読解の負荷が下がる。
- 値: 「細部にこだわります」でなく「細部に汗をかく」(Kole K12)。Basecamp は社内用語を避ける。UX ライティングを学ぶ(Rachel How)。日本語の声の統一は 5.12。
- 出典: Kole K12(16)、Rachel How R2(16)、SmartHR(19)
- 確度: 一人の意見

#### 13.5 例で教える。抽象より具体例、ヘルプはその機能のそば
- なぜ: 抽象的な説明は読み飛ばされる。
- 値: 抽象的な副題より具体例の見出し(IFTTT)、初回にサンプルデータ、ヘルプはその機能のそば(Kennedy K4 Rule 4)。マイクロコピーは 3 文未満が最も処理されやすい(NN/g)。
- 出典: Kennedy K4(18)、NN/g(07)
- 確度: 一人の意見

#### 13.6 数・単位・期間を文言に添える
- なぜ: 判断に必要な情報が欠けると、利用者は別の画面で確かめることになる。
- 値: 価格は「〇〇円から / 1 泊」と書いて日付で変わることを示す(Rachel How R2)。「残り在庫 12 個」(1.10)。通貨と期間は小さく(WP Pusher)。前年比・傾向(Data School)。件数は「件」、人は「名」(5.14)。
- 出典: Rachel How R2(16)、photoshopvip(19)、WP Pusher・Data School(20)
- 確度: 多数一致

#### 13.7 文言は実際の内容で試す。文言を先に、実寸と階層で作ってから画像を選ぶ
- なぜ: ダミーの文字では分からない崩れが出る。低忠実度のワイヤーフレームは非デザイナーに伝わりにくいが、実物らしい文字なら階層から議論できる。
- 値: 画像の中の文字や数字は実コンテンツで試し、UX コピーは実際の内容で書く(Juxtopposed #19)。Type framing(Malewicz #8)。
- 出典: Juxtopposed(17)、Malewicz(17)
- 確度: 一人の意見

## 14. 確かめ方

#### 14.1 先に「利用者がこの画面でやること」を 1 行で書く。書けないなら要素を足す前に戻る
- なぜ: 出発点が決まれば足す要素が決まる。
- 値: 決済なら「支払い方法を選ぶ → 住所 → 注文を確認。確認が済むまで課金されない」(Rachel How R1)。
- 出典: Rachel How・Kole K02(15,16)、Priority guide(10)
- 確度: 多数一致

#### 14.2 批評は「目標が X なら、この設計は利用者に〜の影響が懸念される」の型で書く
- なぜ: 「あの配置はだめ」は意見、「素早い登録が目標なら、強調が違う要素に置かれ主要操作が見つけにくい」は理由。理由は好みでなく目標との関係で書く。
- 値: Discussing Design の枠は目標・文脈・原則・理由。フィードバックの依頼は「挨拶、背景、問題、提案、具体的な依頼」の順(Mizko #3)。
- 出典: NN/g(10)、Discussing Design(10【弱】)、Mizko(17)
- 確度: 多数一致

#### 14.3 各値に理由を 1 行書く(基準・比・下限・測定値のどれか)
- なぜ: 理由のない値は 4 種のどれにも入らない。そういう値は表にある値に丸める。
- 値: 例「本文 16px。DADS の基準値 16px 以上に合わせた。業務画面の密な表のみ 14px(DADS Dense)」。「見出し 1 段目 24px / 行高 150% / 字間 2%。本文 16px から約 1.5 倍(1.25 の 2 段上 ≒ 1.56 に丸め)」。数列外の値は計算メモを残す(Brown)。判断は注釈する(余白を 8 の何倍にしたか、コントラスト比、ボタンの状態。Malewicz)。
- 出典: 11、Hobday #4(18)、Malewicz #6・#11(17)
- 確度: 多数一致

#### 14.4 色と配置の理由は、決まった型で書き、書けない選択は置き直す
- なぜ: 理由が書けない配置・色は、慣習・課題・実測のどれにも結びついていない。
- 値: 色は「役割 / 根拠(既存資産・競合との区別・白に対する比)/ 検証(WCAG の比)/ やらないこと / 色以外の手がかり」の 5 つ。配置は「〔画面の仕事〕のために〔要素〕を〔位置〕に置く。理由は〔課題 / 頻度 / 慣習 / 実測〕。〔代案〕は〔失うもの〕のため採らない」。通る理由: 課題と頻度、実測(左半分に注視 80%)、プラットフォームの慣習、近接・共通領域・整列が示す関係、失敗の重さ。通らない理由: 「見やすい」「スッキリ」「バランスが良い」「モダン」「F / Z パターンだから」「親指が届く」「信頼感のある青」「温かみのあるベージュ」。
- 出典: 09、10
- 確度: 要確認(調査者が設計デザインシステムの記述から組んだ書式)

#### 14.5 コントラストを実測し、白黒にしても意味が残るかを見る
- なぜ: 色の合否は機械で見られる。
- 値: 文字 4.5:1、UI 部品 3:1(WCAG 2 の式)。ライトとダークをそれぞれ。色覚シミュレータは近似(Okabe-Ito)。満たさない色を使うなら理由を記録する(Roselli)。OKLCH の L で代用しない。
- 出典: WCAG・Roselli・Okabe-Ito(03,09)
- 確度: 実証あり

#### 14.6 実画面を複数の条件で見る(機械で拾えない崩れの検出)
- なぜ: 折り返しやトークン外の値は、コードを読んでも分からない。
- 値: 320px を含む複数幅、200% ズーム、400% リフロー、ライト / ダーク、日本語の長文 / 短文、空 / エラー / 読み込み。grep で書ける検査: 日本語 UI の 14px 未満の `font-size`、`transition: all`、500ms 超、`prefers-reduced-motion` の有無。スクイントテスト(1.5)。
- 出典: 03、07(推論の手順)
- 確度: 要確認

#### 14.7 初心者に見える兆候で自己点検する
- なぜ: 兆候はどれも検査できる。
- 値: フローの抜け、効果の使いすぎ、余白が詰まっている、部品の不統一、アイコンの不統一、重複(矢印・枠線)、反応のなさ(Kole K05)。ジュニア → ミドル → シニアの差は、色の使い方 → 階層 → 近接・余白 → 画像による印象 → 道具としての抑制(Showalter J2)。
- 出典: Kole K05(16)、Showalter J2(16)
- 確度: 一人の意見

#### 14.8 Malewicz の 6 段階で画面を自己査定する
- なぜ: 画面の水準を、検査できる特徴で言える。
- 値: Level 1〜2 は書体 7 または 4、背景 4 色、アイコン不統一、余白が混沌。Level 3 は書体 1 つ、濃淡が逆(暗い色が薄い色の上)。Level 4 は書体 1 つ・スタイル 3・背景 3 色・アイコン統一・構造が明快。Level 5 は階層ストリップ、細部(選択状態の印、アイコンの輪郭、余白が格子と実用に基づく)。Level 6 は「誰が使い、何が一番大事か」を問い、画面を並べ直して判断を注釈する。
- 出典: Malewicz #6(17)
- 確度: 一人の意見

#### 14.9 批評は決まった順で見る(4 人の実務者が一致)
- なぜ: 一度に全部を見ると見落とす。初期の項目が後ろの項目の原因になる。
- 値: ①利用者がやることを 1 行で書けるか ②最初に目に入るものが一番大事か(道具の枠が目立っていないか)③色の多さ、CTA の色の使い回し、コントラスト、意味色の誤用 ④近接・余白・端の揃い ⑤主従(主ボタンは 1 つか、リンクはリンクに見えるか)⑥次にすること・戻れる・現在地 ⑦部品の一貫性(角丸・アイコン・ボタンの大きさ)⑧状態(hover・押下・無効・focus・エラー・空・読み込み・成功)⑨端の場合 ⑩細部(44px、行間、影の強さ、線の濃さ)⑪動きは機能に仕えているか ⑫余計なもの(重複する矢印・枠線・カードの重ね・絵文字)。
- 出典: Kole・Rachel How・Showalter・Waterworth(16)
- 確度: 多数一致

#### 14.10 「綺麗」「使いやすい」「美しい」を分けて評価する
- なぜ: 綺麗は規則から外れていない状態で、画面 1 枚で判定できる。使いやすさは利用者・状況・目的が定義されて初めて測れる(ISO 9241-11)。美しさは主観。見た目が良いと操作しやすいと感じる錯覚(美的ユーザビリティ効果。黒須・鹿志村 1995)が欠陥を隠す。
- 値: 規約どおりでも入力手順が不自然なフォームがある。逆に、無骨でも熟練者がショートカットで一瞬で終える管理画面は使いやすい。画面に写らない設計(遷移元・権限による出し分け・エラー時・完了通知)が成否を分ける。
- 出典: kgsi(19)
- 確度: 一人の意見(引用元は学術文献)

#### 14.11 Laws of UX は法則名でなく結果を理由にする。証拠の強さは項目ごとに違う
- なぜ: 名前は参照であって論拠にならない。「近いので同じグループに見える」のように結果で書く。
- 値: 強い: ゲシュタルト(近接・共通領域・類似・連結)、Fitts(モバイルの親指は別モデルが要る)。中: Hick、Jakob、美しさ・使いやすさ効果、Peak-End、Von Restorff。弱: Miller の 7±2(現在は作業記憶を約 4 チャンクとする見解が主流で、「メニューは 7 個まで」の根拠にならない)、Doherty 400ms(1982 年の主張)、Parkinson・Pareto・Tesler・Occam・Postel(格言)。Choice Overload は再現が割れる。
- 出典: Laws of UX(18。評価は調査者の既知知識で未確認)
- 確度: 要確認

#### 14.12 評価の基準に Nielsen の 10 ヒューリスティクスとソシオメディア HIG 24 項目を使う
- なぜ: 理由を言うための共通の語彙になる。
- 値: HIG の 24 項目は、シンプルに、簡単に、メンタルモデル、シグニファイア、マッピング、一貫性、ユーザーの主導権、直接操作、モードレス、視覚ゲシュタルト、ユーザーの言葉、記憶に頼らない、コンストレイント、プリコンピュテーション、エラー回避、フィッツ、ヒック、複雑性保存、タスクコヒーレンス、メジャーなタスク優先、パースエージョン、ショートカット、オブジェクトベース、ビューはオブジェクトを表象する。
- 出典: ソシオメディア HIG(19)
- 確度: 多数一致

## 15. 直す順番(専門家の着手順)

リデザイン事例 15 件の共通の順序(20)。順序の根拠は、全体に効く修正を先に、見た目の仕上げを後にすること。

#### 15.1 まず範囲と「残すもの」を決める
- なぜ: 全部を変えない。うまくいっている部分とブランドの識別性を残す。リスクと範囲の拡大を避ける。
- 値: Resolute は構造を変えない、Transistor は共有テンプレートを壊さない、Linear は見た目に絞りナビの仕組みは後回し、Rachel How はブランドの識別性を残す。
- 出典: Resolute・Transistor・Linear(20)、Rachel How(15)
- 確度: 多数一致

#### 15.2 目的と利用者のすること、重要度を書き、スクイントテストで突き合わせる
- なぜ: 目標がないと「たまたま」しか満たせない。
- 値: Learn UI は先に目標を 3 つ決め、重要度の順(都市と時刻 > 未来の時刻 > ページ名 > 追加などの機能)に強弱を直した。
- 出典: Learn UI 事例 G(20)、Rachel How(15)
- 確度: 多数一致

#### 15.3 全体に効く小さな修正を、他ページへの影響を考えて先にやる
- なぜ: 局所の修正より波及が大きく、後の判断を楽にする。
- 値: 幅の上限(1127 → 960〜1024px)、基本文字サイズ(14 → 16px。余白・行間も増やす)、灰の固定パレット、ナビの現在地の示し方(Transistor)。
- 出典: Transistor 事例(20)
- 確度: 一人の意見(Schoger の事例)

#### 15.4 構造と整列: 不要な演出を外し、組み分けて位置を決め、走査線を作る
- なぜ: 構造が崩れたまま強弱を直しても効かない。
- 値: スクロールジャックの削除(WSS)、情報の組み分け、12 カラムなどでの整列、本文の字下げ(SneakedIn)。
- 出典: WSS・Bad About・SneakedIn(20)
- 確度: 多数一致

#### 15.5 強弱: 大きさ → 色 → 太さで階層を作り、補助を下げる。ラベルを外すか薄くする
- なぜ: 構造と整列が決まってからでないと、強弱の判断が崩れる。最頻の誤り(16.1)の直しにあたる。
- 値: 1.1〜1.10 を参照。
- 出典: Refactoring UI(18,20)、Schoger(20)
- 確度: 多数一致

#### 15.6 部品: ボタンの主従、入力欄の高さ・幅・ラベル、タグ・表・状態表示
- なぜ: 階層が決まったあとに部品を直すと、主従の基準で迷わない。
- 値: 入力と部品の高さは 40〜48px、枠は 2px、ラベルの大文字をやめる(Transistor)。9 章を参照。
- 出典: Resolute・Transistor・Spike.sh(20)
- 確度: 一人の意見

#### 15.7 仕上げ: 影・角丸・枠の整理、アイコンの統一、灰へのブランド色相、書体の変更
- なぜ: 見た目の質感を左右するが、構造と階層が決まる前にやると手戻りする。
- 値: 書体を最後に直す人が多い(Schoger)。Waterworth は早い段階で 1 つにそろえる。どちらも「階層を直す前に書体を整える」点は同じ【推論】。
- 出典: Bad About・WP Pusher・SneakedIn(20)、Waterworth(15)
- 確度: 多数一致

#### 15.8 検査: コントラストの実測、ライト / ダーク、モバイル、実データの端の場合、目標の再確認
- なぜ: 目標を満たしたかを最後に確かめないと、見た目の改善が目的とずれたままになる(Learn UI は最後に目標を満たしたか確認した)。
- 値: 14 章を参照。
- 出典: WP Pusher・WSS・Learn UI 事例(20)
- 確度: 多数一致

#### 15.9 詰まったら実在の製品を調べる(スワイプファイル)
- なぜ: 利用者が知っている型を使うことになり、何年やっていても有効。
- 値: Airbnb・Booking・Expedia を参照(Rachel How R2)。20 件のスワイプファイルと 28 日の学習(Kole K03)。pages.xyz、Fonts In Use、Dribbble、Mobbin。ワイヤーフレームを毎日描き、Uber を写す(Malewicz #5)。
- 使わない場面: UI キットは納期が短いときだけ。評価される作品では「有名キットそのまま」が没個性の合図(Malewicz)。実務は前者、個性が要る場面は後者。
- 出典: Rachel How(15,16)、Kole K03(16)、Mizko・Malewicz(17)、Kennedy(18)
- 確度: 多数一致

#### 15.10 1 回に 1 つ直す。余白 → 書体 → 色 → アイコンの順
- なぜ: 一度に全部直そうとすると見落とす。
- 値: Malewicz は、左右の余白をそろえて 20 などに固定 → 内側は 16 など外側より小さく → 行間をそろえる → 書体を 2 つのスタイルに絞る → 色 → アイコン。Flux の 6 段は ①不要なものを削る ②文字の可読性 ③色を意図的に(ブランド色 1・黒 1・白)④余白の一貫性(12 カラム、8px 倍数)⑤見た目の一貫性 ⑥伝わる画像。Waterworth の 4 段は 色を減らす → 書体をそろえ階層を直す → 余白と組み分け → 控えめにする。
- 割れ: 書体の順序(早い / 最後)と、色の順序(最初に減らす / 最後に足す)。既定: 階層を直す前に書体を整え、色は少なく最後に足す。理由: 書体と色が階層の見え方を変えるため、階層の判断の前に固定する。
- 出典: Malewicz #11(17)、Flux #12(17)、Waterworth(15)
- 確度: 一人の意見どうしの対立

#### 15.11 作る順序: 小さい画面から、要素を 1 つずつ足し、毎回よい状態を保つ
- なぜ: 小さい画面で作ってから広げるほうが崩れにくい。既存と同じ書き方に合わせてから調整すると、一貫性が勝つ。
- 値: コンポーネントを先に作り、1 か所変えれば全部変わるようにする(Rachel How R1)。最初の案で決めず、複数案を試し、離れて戻って見る(R2 の 1 時間の課題は 3 時間かかった)。
- 出典: Learn UI 事例 H(20)、Rachel How(16)
- 確度: 一人の意見

#### 15.12 個性は基本ができてから、1 点に絞って足す
- なぜ: 使用頻度が高い UI ほど表現を抑える(Hobday)。クラシカルは普遍的で退屈、表現的は刺激的で好みが割れる。
- 値: 良い設計は「使える・一貫・明快」、優れた設計は「挑む・予想外・言いたいことがある」(notbor.ing。13 組の対句。基本ができた後の方向づけとして読む【推論】)。ルールを破るには理由が要る(Hobday)。
- 出典: Hobday H-n(18)、Kole K02(15)、notbor.ing(20【弱】)
- 確度: 一人の意見

## 16. よくある誤り(頻度順)

頻度は事例 15 件前後のうち、その問題に実際に触れていた件数。調査者の数え方で、重複と解釈の揺れがある(20)。上位 3 つは他の誤りの原因にもなる(階層がないから色や枠で目立たせようとして 3・9 が起きる)。

#### 16.1 階層がない(全部が同じ強さ、主役が脇役より弱い) — 約 13 件
- なぜ: 利用者が先に見るべきものを先に見せられない。
- 値: 直し方は、主従を大きさ・太さ・色の濃さで付ける。主役を大きく、補助を小さく薄く。ラベルは外すか溶かすか薄く。目を細めて最初に見えるものを確かめる(1.1、1.2、1.5、1.10)。
- 出典: Bad About・SneakedIn・Learn UI・Refactoring UI・Rachel How(20)
- 確度: 多数一致

#### 16.2 余白が足りず詰まっている / 余白の値がばらばら — 約 10 件
- なぜ: 近さで組を作れず、読みやすさと「整って見える」の両方を失う。
- 値: 余白を倍にし、スケールから選ぶ。縦だけ増やしたら横も合わせる。区切りは枠でなく余白で(2.3、2.4、2.5)。
- 出典: WP Pusher・Resolute・Transistor・SneakedIn・Kennedy・Rachel How(20)
- 確度: 多数一致

#### 16.3 色が多い / 灰が場当たり / ブランド色の乱用 — 約 9 件
- なぜ: 色が多いと階層が崩れ、パレットが無限だと体系がない。
- 値: 灰は固定の 3(用途別)〜9 段に限定。ブランド色相を灰に少し混ぜる。主色は主操作などごく少数に。まず白黒で作り、色は最後(6.1〜6.4)。
- 出典: Bad About・Transistor・SneakedIn・Learn UI・Refactoring UI・Spike.sh・Data School・Rachel How(20)
- 確度: 多数一致

#### 16.4 整列がそろっていない(中央・左・右の混在、数値と文字、アイコン横の字下げ) — 約 7 件
- なぜ: 見えない軸ができず、拾い読みしにくい。
- 値: 左揃えを基本に走査線を作る。数値は右揃え。アイコンの分は本文を字下げ(3.1〜3.5)。
- 出典: Bad About・Resolute・Transistor・SneakedIn・Spike.sh(20)
- 確度: 多数一致

#### 16.5 書体が不適 / 多い / 既定のまま — 約 7 件
- なぜ: 見た目の質感を左右する。速さが要る画面は書体を読み込まない。
- 値: 書体は 1〜2。ロゴと合わせるか、良い UI 書体に。社内ツールはシステムフォント。替えたらサイズと太さも調整(4.1、4.2、5.7)。
- 出典: Bad About・WP Pusher・Resolute・WSS・SneakedIn・Kennedy(20)
- 確度: 多数一致

#### 16.6 クリックできるか・状態が分からない — 約 7 件
- なぜ: 期待と実際を一致させるため。ボタンに見えるラベル、削除に見える×のタグ、現在地の不明、リンクの見た目が例。
- 値: 押せるものにだけ矢印・下線・アイコン・塗りを。現在地は色の線や背景。状態は色 + 形の両方(6.9、9.3、9.17)。
- 出典: Resolute・WSS・Transistor・Learn UI・Spike.sh・Rachel How(20)
- 確度: 多数一致

#### 16.7 主操作が決まっていない / 意味ごとに色を変えて階層が壊れる — 約 6 件
- なぜ: 意味(赤 = 危険)より階層が先。誤操作も防ぐ。
- 値: 主操作は 1 つ(強い色)、副は薄い塗りか枠線、三次はテキストリンク。破壊的操作は主でなければ目立たせず離して置く(1.7、1.8、9.13)。
- 出典: Bad About・Resolute・Transistor・SneakedIn・OJS(20)
- 確度: 多数一致

#### 16.8 コントラスト不足(色背景に白文字、薄い灰) — 約 6 件
- なぜ: 読めないのは機能の欠落。
- 値: 明るい背景色なら濃い文字、アラートは淡い背景 + 濃い文字。比率を実測する。濃い背景では背景色相の淡色(6.8、6.15)。
- 出典: Bad About・WP Pusher・Transistor・SneakedIn・Linear・OJS(20)
- 確度: 実証あり(規格)

#### 16.9 区切りに枠・影・背景写真を使いすぎ — 約 6 件
- なぜ: 枠が多いと雑然とする。強い影は「覚えたての装飾」。
- 値: 枠をやめて背景色の差と余白で区切る。影は 2 層で薄く(8% 前後)、少し下にずらす。写真は彩度を落とし色を重ねる(2.5、7.2、7.6)。
- 出典: WP Pusher・Transistor・SneakedIn・WSS(20)
- 確度: 多数一致

#### 16.10 組み分け(近接)の不足 / 関連のないものが近い — 約 6 件
- なぜ: 近いものは関係があると見える。
- 値: 関連するものを寄せ、無関係なものを離す。ラベルは自分の入力の近くに(2.1、2.7)。
- 出典: Bad About・WP Pusher・Resolute・SneakedIn・Rachel How(20)
- 確度: 多数一致

#### 16.11 アイコンが不統一 / 重い / 大きすぎ — 約 5 件
- なぜ: 重いアイコンは同じ色でも文字より濃く見える。
- 値: 1 セットに統一。文字より軽く。拡大せず円に入れる(11.1〜11.3)。
- 出典: Bad About・Resolute・WSS・Transistor・SneakedIn(20)
- 確度: 多数一致

#### 16.12 フォームの設計(幅が広い、ラベルが placeholder、欄が多い、検証が遅い) — 約 5 件
- なぜ: 入力欄の長さは期待を作る。
- 値: 最大幅 960 前後、入力の長さを文字数の目安に。ラベルは欄の上。欄を減らす(8 前後)。blur で検証(3.10、9.4、9.6、9.8)。
- 出典: WP Pusher・Resolute・Baymard(20)
- 確度: 実証あり(Baymard)

#### 16.13 欠けている文脈(単位・期間・比較・現在地・戻る・安心の一言) — 約 5 件
- なぜ: 判断に必要な情報が欠けている。
- 値: 通貨・期間・前年比、戻るボタン、「まだ課金されません」を足す(10.8、13.6)。
- 出典: Data School・Learn UI・Rachel How(20)
- 確度: 多数一致

#### 16.14 慣習から外れた仕組み(スクロールジャック、表の入れ子スクロール、モバイルのキーボード) — 約 3 件
- なぜ: 予想外は摩擦になる。
- 値: 慣習に戻す。型に合った `inputmode`(8.1、9.8、12.7)。
- 出典: WSS・Baymard(20)
- 確度: 多数一致
