# 09 色の決め方と理由の書き方

調査日: 2026-10-26。記号: 【弱】=ブログ・二次情報・検索要約のみ。【推論】=調査者の推論。
「読了」=WebFetch で本文を読んだ。「検索のみ」=検索結果の要約だけ。出典は文末の URL。
03(視覚の基礎)と 07(ベストプラクティス)で扱った WCAG の数値、OKLCH の基本、Radix 12 段の割り当て、shadcn のペア命名、ダークモードの面の色は繰り返さない。ここは「何を・なぜ・どの順で決めるか」と「理由の書き方」。

## 結論

1. 色は「意味を運ぶ道具」で、装飾ではない。デザインシステムの文書も Few も、色は伝える目的があるときだけ足し、意味の違いに対応しない色の差は作らない、と同じことを言う。
2. パレットは役割で分ける(中立の階段 / アクセント1 / 状態色 / データ用)。アクセントの数に実証された最適値はない。1つが多数派の流儀で、これは設計の慣習であって研究の結論ではない。
3. 「ブランドや主題の心理的な意味」から色相を選ぶ根拠は弱い。赤の効果の追試は失敗し、メタ分析は「実質的な証拠なし」。色相は、競合との区別・既存の連想・利用者の慣習・コントラストの取りやすさから決め、理由もそう書く。
4. 知覚的に均一な空間(OKLCH、LCH、CIELAB、HCT)は、段階ごとのコントラストを予測可能にするための道具。保証にはならず、最終判定は WCAG 2 の比で行う。APCA は WCAG 3 に入っていない。
5. 色だけで意味を運ばない(WCAG 1.4.1、Level A)。赤と緑だけの区別は男性の約 1/12 に伝わらない。理由は「何を伝えるか → 色の役割 → 検証した数値」の順で書く。

## 2. 論点ごとの調査結果

### 2.1 主題・ブランドから色を導く

- 一次の調査研究は見つからなかった。手がかりは実務の記述のみ。
- Datawrapper は、カテゴリ用の色を「画家・映画のスチル・自然写真・パレット集」から取る、と書く 読了 (colorguide)。主題に属する実物から取る、という方法。
- OneSignal は、ブランドが紫なので、グレーを少し寒色寄りにした。「彩度のないグレーは理想的でない」 読了 https://onesignal.com/blog/11-shades-of-gray-a-color-system-story/ 【弱】(企業ブログ)。
- Linear は、再設計で「ブランドの青が色の計算に与える影響を減らし、より中立に」した 読了 https://linear.app/now/how-we-redesigned-the-linear-ui 。(検索結果は逆の要約を返した。読了した本文を採る。)
- SmartHR は「プロダクトに必要な最小限の色だけを定義し、役割に応じた名前を付ける」 読了(URL は https://smarthr.design/products/design-tokens/color/)。2021-02 に MAIN を青緑から青へ変えたが、理由はページに書かれていない。
- デジタル庁は、プライマリー色の選び方の基準として「主要背景に対して 4.5:1 以上」だけを示し、なぜ青かは書いていない 読了。
- 【推論】言える理由の型は「この主題の既存の連想」「競合との区別」「利用者の慣習」「コントラストが取れる色相」の4つ。「この色は信頼を感じさせる」は理由にならない(2.5)。

### 2.2 アクセントの数

- 実証研究は見つからなかった(03 でも未発見)。
- Radix は個数を指定せず、1つのブランド/アクセント scale を勧める。一方で「多くの場合、いずれ大半の scale が必要になる」と認める 読了。
- Refactoring UI は「アクセント色は、異なる意味を伝えるために少数、控えめに使う」。「パレットを絞らないと色体系がないのと同じ」 読了 https://refactoringui.com/previews/building-your-color-palette 。ここでの「アクセント」は状態用の色を指す(本書の用語)。
- Atlassian と Carbon は、主操作の色を1つに決め、他は控えめにする設計。
- 【推論】アクセント1つは慣習。理由は「操作できる所を1色に固定すれば、その色が出た所は押せると学習される」。2つ目のアクセントを足すなら、1つ目と別の意味(別の操作クラス)を持たせられるときだけ。
- 【弱】Vercel Geist は、主ボタンを最も暗いインク色にして青を限定的に使う、という第三者の要約がある(公式ページは `/geist/colors` で段階の用途だけ読了。この点は未確認)。

### 2.3 中立色に色相をつける(暖かいグレー/冷たいグレー)

- 事実: Tailwind v4 の 5 つのグレーは、500 段で slate=色相 257・彩度 0.046、gray=264・0.027、zinc=286・0.016、neutral=彩度 0、stone=58・0.013。つまり3つは冷たい側、stone は暖かい側(Tailwind のページは冷暖を言葉で説明していない。値からの読み取りは【推論】)。 読了 https://tailwindcss.com/docs/colors
- Radix: 中立にしたいなら gray、「自然な」調和にしたいならアクセントの色相に最も近いグレー(mauve / slate / sage / olive / sand)。差は「わずか」だが、全面がテキストのページでは大きく効く。ダークモードで彩度のあるグレーを背景にすると、カラフルな部品とぶつかることがある 読了。
- OneSignal: 色相を全段で一定に保ち、彩度は暗部をわずかに上げる 読了【弱】。
- 暖色=親しみ、寒色=冷静、という「伝わる印象」を実証した研究は見つけていない。【推論】印象の主張は書かず、「アクセントの色相と揃えるとまとまる(Radix)」という機能の理由で書く。

### 2.4 知覚的な色空間と段階の作り方

- Stripe: HSL は同じ L でも色相で明るさが違う(黄は青より明るく見える)ため、CIELAB で再構築した。ゴールは「予測できるアクセシビリティ」「明瞭で鮮やかな色相」「一貫した視覚的重み」。「5 段以上離れた2色は小さい文字で必ず十分なコントラストを持つ(アイコン/大きい文字は4段)」という規則を述べる。旧パレットは、基準を満たすまで暗くすると「暗く濁った」ので全面刷新した 読了 https://stripe.com/blog/accessible-color-systems
- Linear: HSL から LCH へ。テーマ入力が 98 変数から「基調色・アクセント・コントラスト」の3つに。コントラストを変数にして、高コントラストのテーマを自動生成 読了。
- Material: HCT(CAM16 + L*)。【弱】検索のみ: トーン差 40 で 3:1 以上、50 で 4.5:1 以上。HCT 固有の性質で WCAG 全般の規則ではない。公式 M3 ページは本文が取れなかった。
- Evil Martians: OKLCH は色相が一定で、LCH の「青が明度を変えると紫になる」問題がない。彩度の上限は色相と画面の色域で変わる。changelog に「アクセシビリティ判定には APCA を使え。OKLCH だけでは足りない」 読了 https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl 。Harmony は OKLCH + APCA で同じ明度グループの色が同等のコントラストを持つ設計 https://github.com/evilmartians/harmony 読了(アルゴリズムの説明はない)。
- 作り方の手順【推論】(上の各出典の合成):
  1. 色相ごとに L の目標値を先に決める(用途別。Radix は 1-2 背景、3-5 部品、6-8 線、9-10 ソリッド、11-12 文字)。
  2. C は色相ごとの色域の上限で切る。同じ C を全色相に当てはめない。
  3. 同じ段の色が同じ L なら、白/黒に対する比もほぼ揃う。確認は WCAG 2 の式で行う。

### 2.5 コントラストと色覚の多様性

- WCAG 2.2: 1.4.11 は UI 部品・意味のある図形に 3:1。非活性部品と、同じ情報が別の手段で伝わっている図は除外 読了 https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html 。1.4.1 は「色が唯一の視覚手段であってはならない」(Level A) 読了 https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html
- APCA: 2023-07 の WCAG 3 ドラフトから外れ、2026-04 の草案でもアルゴリズム未定。Roselli は WCAG 2 を基準にし、使うなら両方満たすか、満たさない色の理由を記録することを勧める 読了 https://adrianroselli.com/2026/04/wcag3-contrast-as-of-april-2026.html
- 有病率: 男性の約 1/12 が色覚異常、最多型は赤と緑が区別しにくい 読了 https://www.nei.nih.gov/learn-about-eye-health/eye-conditions-and-diseases/color-blindness 。Few は「男性約10%、女性1%」と書く(2008 年、数値が古い)。
- Okabe-Ito: 暖色と寒色を交互にする、同系の2色は明度か彩度に差をつける、黄と緑の間の色は黄・橙と混ざるので避ける、色だけで情報を伝えない(線種・記号・ハッチを足す)、凡例ではなく直接ラベル、赤文字は暗背景を避ける。シミュレーションは近似で、色覚異常の人は模擬より多くの色を区別できる 読了 https://jfly.uni-koeln.de/color/ 。8 色のコード値は検索のみ(black #000000, orange #E69F00, sky blue #56B4E9, bluish green #009E73, yellow #F0E442, blue #0072B2, vermillion #D55E00, reddish purple #CC79A7)。黄は白背景で薄い。
- デジタル庁: リンクの青と紫は慣習だが色覚の面で見分けにくく、紫に赤みを足して明度差を作った 読了。→ 慣習を守りつつ、明度差で補う実例。
- 赤/緑の意味は文化で逆転する。中国・日本・韓国の株価チャートでは赤が上昇(日本は媒体で不統一、2005 年の調査と 2024 の記事)。欧州データポータルは「状態を良/悪で色分けするのは、受け手がその連想を共有しているときだけ」 読了 https://data.europa.eu/apps/data-visualisation-guide/colour-connotations 。株価の数値は検索のみ【弱】。【推論】日本向けの上昇/下落の色は、既存の慣習と逆にしない、または色に頼らず矢印と符号を足す。

### 2.6 階層と注意: 色は最も希少な強調

- Few ルール3「伝達の目的があるときだけ色を使う。飾りに使わない」、ルール4「意味の違いに対応するときだけ別の色を使う」、ルール5「大半は柔らかい自然な色、注意が要る所だけ明るい/暗い色」 読了。
- Datawrapper「グレーはデータ可視化で最も重要な色」。色を減らす手: 位置で区別できるなら色を使わない、同系色の濃淡、強調以外はグレー、直接ラベル、小カテゴリは「その他」にまとめる。形・線種などの補助手段は3-4種までに 読了。
- Atlassian「濃い色ほど既定の面に対してコントラストが高く、注意を引く」 読了。
- 【推論】ここから導ける実装規則: 1画面で「彩度のある色」が占める面積と箇所の数に上限を置き、最重要の行動1つにアクセントを集中させる。数値の上限(例 60-30-10)は根拠が見つかっていない(03 の Gaps と同じ)。

### 2.7 データの色

- IBM Carbon: カテゴリカルは14色・固定順、既知の数なら短いプリセット。連続は単色、発散は2種類 読了。Carbon の当該ページには色覚と背景コントラストの記述がなかった。ほか(dataviz-a11y)は 404 で未読。
- Datawrapper: カテゴリは「自分だけで立つ」色、連続は段階が見分けられること、色覚シミュレータで確認。凡例は直接ラベルで減らす 読了。
- Few: 連続の値は、淡い色=小さい値から濃く鮮やかな色=大きい値へ。赤と緑を同じ表示に置かない 読了。
- Observable の色の指針は 429 エラーで未読(Gaps)。
- SmartHR のチャート: 多色 10 色、単色 6 段階、「その他」用の色を順序固定で使う 読了。
- 【推論】カテゴリが 7〜8 を超えたら、色の追加でなくグルーピング・強調・小さい複数の図に切り替える(Datawrapper の「12 や 15」の例が、色以外の手段へ移る目安として使える)。厳密な上限の出典は見つからなかった。

### 2.8 色の心理: 証拠と神話

- Elliot & Maier の赤と成績の研究(2007)は、赤を一瞬見せると課題成績が下がる、と報告した(d = -0.51〜-1.14)。追試は失敗が相次いだ。Gnambs(2020, Psychonomic Bulletin & Review)のメタ分析(22 論文、38 サンプル、67 効果量): アナグラムと知識課題で有意差なし、推論課題で小さな負の効果(d = -0.34、初報告の半分未満)、出版バイアス補正後は「赤が知的成績に及ぼす効果の証拠価値はなし」 読了 https://pmc.ncbi.nlm.nih.gov/articles/PMC7704521/
- Elliot 本人の 2015 年のレビュー: 理論は「発展の初期段階」、小サンプルの結果は「暫定的」、「大胆な理論的主張や決定的な実証の断定は時期尚早」、結果は「刺激的でメディア向き」なため結論が先走る 読了(本文 100,000 字まで) https://www.frontiersin.org/articles/10.3389/fpsyg.2015.00368/full
- 例外に近い堅い知見: Jonauskaite ら(2020, Psychological Science)は 30 か国 4,598 人で、色と感情の連想に共通パターン(平均 r = .88)と、言語・地理が近いほど似る地域差を見つけた。「色と感情の連想」が存在する根拠にはなるが、「色を見せると行動が変わる」根拠ではない。 検索のみ https://eprints.whiterose.ac.uk/id/eprint/169496/
- ブランド色の人格(Labrecque & Milne, "Exciting red and competent blue")は存在が確認できただけで、サンプルや再現性は未確認。検索のみ【弱】
- 結論【推論】: 「この色は信頼を生む/行動を促す」を設計理由にしない。使える理由は、(a)利用者がすでに持つ連想(赤=危険、慣習の青リンク)、(b)機能(コントラスト、区別)、(c)ブランドの既存資産。

### 2.9 ダークとライト

- 07 に面の色の指針がある。追加分: Android/Material の文書は、ダークテーマでは彩度を落とした淡いアクセント(200〜50 のトーン)を推奨し、500〜900 の飽和した色より扱いやすい、と述べる。検索のみ【弱】(一次ページは未読)。
- Carbon: ライトは白とグレー10 を交互に重ね、ダークは1段ずつ明るくして階層を作る 読了。
- Radix: 色の割り当ては同じで、段の値がモードごとに入れ替わる(AppBg を可変エイリアスにする) 読了。
- 【推論】ダークでは同じ色相でも L と C を別に決める(単純な反転でなく)。

## 3. 決め方の手順

色を決めるときは、次の順に問う。各問いで「だから(出典)」を1行書く。

**Q1. 画面の大半は何色か。(中立の階段)**
- 画面にある面・線・文字をすべて中立で作ってから、色を足す。(Refactoring UI: 「色はグレースケールで階層を作った後」 / Datawrapper: グレーを土台にする)
- 色相を付けるか: アクセントがあるなら、その色相に最も近い低彩度のグレーを選ぶ(Radix)。ダークでカラフルな部品が多いなら、無彩色寄りにする。理由欄には「アクセントとのまとまり」と書き、「温かい/冷たい印象」とは書かない(2.3)。
- 段は用途で先に割り当てる(Radix の 12 段、Geist の 100〜1000 段)。

**Q2. 利用者が1つの画面で最初に何をするか。→ それに1つのアクセントを割り当てる。**
- 主操作の色は1つに固定する。「この色=押せる」と学習させるため(Carbon: 青が主操作色、Primer: アクセント=操作/選択/フォーカス)。
- 色相の決め方、この順で:
  1. すでに資産があるか(ロゴ・既存ブランド)→ それを使う。
  2. 競合/隣接サービスと同じ色相でないか。
  3. 白/暗い面に対して 4.5:1 以上の段が作れる色相か(DADS はこれを基準に書く)。
  4. 状態色(赤・緑・黄)と混同しない色相か。赤系や緑系のアクセントは避ける(Atlassian: アクセントを状態に使わない)。
- 2つ目のアクセントを足す条件: 1つ目と別の意味を持つ操作クラスがあるときだけ。デフォルトは足さない【推論】。

**Q3. 状態を伝える必要があるか。→ 状態色を、色以外の手がかりとセットで置く。**
- 成功・警告・危険・情報の4つ、Radix の対応表から色相を取る。ターゲット層の連想を確認する(日本・中国向けの上昇/下落は逆になりうる: 2.5)。
- 必ずアイコン・文言・形を足す(WCAG 1.4.1、SmartHR、Atlassian「選択は色以外の手がかりと組み合わせる」)。
- 警告の黄色の面は、暗い文字と組み合わせる(SmartHR は WARNING_YELLOW を TEXT_BLACK と必ずセットにする)。

**Q4. データを描くか。→ 変数の種類で選ぶ。**
- 順序なし区分 → カテゴリカル。まず「色を使わず位置・ラベルで区別できないか」(Datawrapper)。色が要るなら Okabe-Ito か Carbon の固定順。
- 量(低→高)→ 単色の連続。明度で順序が分かること。
- 中心からの乖離 → 発散。中心は淡い色、両端は別の色相。赤/緑の組は使わない(Few ルール8)。
- 強調 → 注目させる1〜2系列だけ彩度・濃度を上げ、残りはグレー(Few ルール5、Datawrapper)。
- 色数が増えたら、グルーピング/小さい複数の図/直接ラベルに切り替える。

**Q5. 検証。**
- 文字は 4.5:1、UI 部品・図形は 3:1(WCAG 2.2)。比は WCAG 2 の式で測る。OKLCH の L は目安にすぎない(Evil Martians)。
- 色を白黒にしても意味が残るか。色覚シミュレータは近似(Okabe-Ito)。
- ライトとダークで、それぞれ検証する。ダークは単純な反転にしない。
- 満たさない色を使うなら、その理由を記録する(Roselli)。

**迷ったときの既定**【推論】
- 理由が書けない色は使わない。「理由」が心理的な印象だけの色(「落ち着くから」)は、機能の理由(区別・操作・状態)に書き換えられるかを確認し、書き換えられなければ削る。

## 4. 理由の書き方の例

デザインシステムの文書の型を分解すると、次の4要素が揃う。(a)役割(何を伝える色か)、(b)選んだ根拠(慣習・資産・数値)、(c)検証した事実(比・段差)、(d)使ってはいけない場面。

実際の記述(読了した出典):

1. **役割で説明する。** Atlassian「色の役割は色の意図を表す」「アクセントは、別の色に入れ替えても体験が変わらないはず」。→ 色名でなく用途を主語にする。
2. **数値で保証する。** Stripe「5 段以上離れた2色は、小さい文字で必ず十分なコントラストを持つ」。→ 規則と数をセットにする。
3. **慣習を採る理由と、その弱点への対処を書く。** DADS「リンクの青と紫は慣習で認知度が高いが、色覚の多様性の観点では見分けにくい。紫に赤みを加えて青との明度差を作った」。→ 採った理由 / 欠点 / 直し方。
4. **意味の共有を理由にする。** DADS「緑といえばサクセス、赤といえばエラー。視覚的な共通言語で、メンタルモデルに影響する」。
5. **最小性を宣言する。** SmartHR「プロダクトに必要な最小限の色だけを定義する」。
6. **色以外の手がかりを必須にする。** SmartHR「色だけで情報を示すことは避ける」、Atlassian「選択状態は色以外の手がかりを組み合わせる」。
7. **やらないことを書く。** Geist「重なる半透明の枠線は交点が見えるので、枠は1回だけ描く」、Carbon「トークンで値を変えれば、デザイン言語の変更を大規模に反映できる」。
8. **変更の履歴は理由を伴わせる。** 反例: SmartHR の 2021-02 の MAIN 変更(青緑→青)は、ページに理由がなく、お知らせへのリンクだけ。

エージェントが UI を作るときの書式案【推論】(上の4要素に合わせた):

```
色: --accent (oklch(0.55 0.18 255))
役割: 主操作と選択中の状態にだけ使う。画面に出る彩度の高い色はこれだけ。
根拠: ①既存ロゴの色相 ②競合A/Bは緑系で区別できる ③白に対して 6.1:1(文字として使える)
検証: 白背景の文字 6.1:1(AA 4.5:1 を満たす)、ダークでは L を 0.72 にして背景に対して 7.0:1
やらない: 状態(成功/危険)に使わない。装飾に使わない。
色以外の手がかり: 選択中は太字+左の線
```

禁止する書き方: 「信頼感のある青」「温かみのあるベージュ」「モダンな印象」。研究の裏づけが弱く(2.8)、検証もできない。

## 5. 弱い出典と推論の一覧

- 【弱】OneSignal(ブログ)、Vercel Geist の要約(第三者)、ダークの彩度低下(Android 文書の検索要約)、株価の色の個別数値、Labrecque & Milne(存在確認のみ)、Okabe-Ito のコード値(検索のみ)、Material のトーン差 40/50(検索のみ)。
- 【推論】アクセント1つの理由づけ、色相の選択順 Q2、カテゴリ 7〜8 を超えたら切り替える目安、ダークは L と C を別に決める、理由の書式案、色相付きグレーの言い方。
- 読めたが使わなかった: Apple HIG の色のページ(本文が取れず、モデルの一般知識しか返らなかったので不採用)。

## Gaps

- 一次の研究: 「アクセントは何色が最適か」、60-30-10 の根拠、暖色グレー/寒色グレーが利用者の印象や理解に与える影響。いずれも実証研究を見つけていない。
- Material 3 の公式ページ(HCT、ニュートラルの彩度)は本文が取れず、トーン差 40/50 は公式の確認ができていない。
- Carbon の dataviz アクセシビリティ、Observable の色の指針は未読(404 と 429)。Healey & Enns の「同時に区別できる色数」は一次の数値を取れていない。
- SmartHR・デジタル庁は、なぜその色相かの記述が見つからず、理由の書き方の手本としては限定的(SmartHR のコントラスト数値もページに無い)。Polaris は移転先のページが開けず未読。
- WCAG 3 は未確定。APCA の数値は使わない前提で、補助でも導入するなら、記録の方法を決める必要がある。
- 日本向けの上昇/下落の色は 2005 年の調査と 2024 の記事のみ。現行の取引所・証券会社のチャートを確認していない。
- Elliot 2015 のレビューは本文の後半 25,000 字を読んでいない。
